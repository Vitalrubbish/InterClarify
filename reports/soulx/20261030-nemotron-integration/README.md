# Nemotron＋SoulX独立组合探针

2026-10-30，按用户授权完成独立适配与两轮远端单卡检查。**组合链路已跑通：Nemotron独立持续识别并向SharedContext发布字符前缀，SoulX保留音频路径和原生五状态预测，四个音频视图均完成实时回放，最终r2退出码0。** 不新增1秒稳定等待，不加载或调用SenseVoice，不切换现役Agent。小样本只能证明适配能运行及来源／版本合同，不证明状态语义或整体质量达标。

## 1. 如何结合

实现与冻结范围见[适配设计](../../../docs/dev/SoulX-Duplug/nemotron_integration.md)、[前端实现说明](https://github.com/Vitalrubbish/InterClarify/blob/9fb5319/docs/scripts/runtime/nemotron_soulx_frontend.md)。Nemotron原始累计文字一返回，就由独立轮询线程发布来源事件和正文版本；不受SoulX门控、reset或complete暂停。Context同话轮固定`nemotron`来源，任何已交付字符前缀回写都会报错；源ID与原始文本保留。

SoulX仍每块编码音频，保留官方ASR门控前向及五状态预测。门控允许时选择保守观察上界不超出本块实际音频范围的已发布源版本，记录Context最新正文版本与**控制器真正消费的版本**；两者可以不同。没有可用前缀时记pending，继续声学路径，不伪装为静音。ASR回调的读取截止可能包含预取，因此只用作保守上界，不把名义160ms解码步当精确词对齐。

Nemotron原始字符只追加，SoulX归一化和分词仍可能回改末词token。适配器保存本controller generation的音频嵌入、文本token和当时实际状态，必要时有界重建KV；优先让旧词修正留在旧缓存位置，新增词仍在当前音频后输入。每块检查文本token串接能重建选定前缀；重放不发布新状态或重触发打断。原生完成分支只读已有前缀，不再整轮ASR。

内部reset保留连续音频和Nemotron会话，只有原始字符截止实际增长才再次消费；跨reset的旧尾词只在收到新字符后用于重建新控制缓存。Context不重复创建消息或清空历史。源前缀不可改写不意味着词已完整或识别正确；本轮原样发布词内增量，尚未实现给LLM的完整词视图。

## 4. 修复及仍未解决的边界

r1已经四视图退出0，但检查发现reset后可能重新注入没有增长的旧尾词；英语示例产生5次complete。r2要求源字符截止增长才消费，并分开旧词修正与新增词位置；英语示例complete为1次，FLEURS完整为2次。由于两轮包含时序与文本分配差异，不能将计数变化单独视为质量提升或纯粹归因于某一行修复。r1原始结果保留，最终数字只取r2。

仍需明确以下限制：

- **状态语义未验收。** r2的FLEURS完整在音频处理截止4.44／7.48秒出现complete，英文示例在3.80秒出现complete，而录音仍继续。没有逐时话轮金标，不能据出现token判断时机正确；不能因文字更连续就认为五状态已经等价适配。
- **Context最新不等于SoulX已消费。** EOF时FLEURS完整最新／消费版本为55／55，英文示例32／30，截断视图18／15。门控、实际可见时间和保守观察边界会使消费落后；对状态使用`consumed_asr_version`，不能把最新Context全文冒充模型输入。连续真实音频通常可继续消费，本轮没有伪造后续音频强行补齐。
- **EOF尾部不回填。** 截断视图的部分结果只在原生解码排空后出现，Context保持最后在线版本。若后续要做真实会话的“完成时交付尾词”，需要围绕实际音频进度和ASR未交付结果设计有界收尾，不把EOF或complete当最终文字已经就绪。
- **字符追加仍有词内token变化。** r2真实经历3次缓存重放；较长话轮受到256块／4096文本token上限约束，触限明确失败，尚未做长时压力及状态质量检查。
- **原始字符可读不等于LLM完整词可读。** Layer1／2未接入，词内增量仍需适当的完整词提交／输入边界，不能把当前原始事件直接宣称为稳定语义输入。

本轮4项新契约、6项SenseVoice前端回归、4项通用Context、5项既有Nemotron服务检查通过，共19项；另用CPU轻量模型替身独立核查`inter`扩展为`internet connection`时旧词缓存替换及新增词在当前音频后的实际输入顺序。替身不冒充模型评测。
