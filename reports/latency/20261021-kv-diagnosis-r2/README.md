# Issue 051：缓存分歧原因核查结果

## 结论

已查明049中同一150-token请求三次重复生成分歧的原因：**BF16在完整预填充和分段缓存计算下产生数值偏差，继承的重复惩罚使两个候选接近并列，贪心选择因此翻转。** 本例缓存token前缀、长度、绝对位置和attention mask核对通过，没有发现错位或串会话。结论限定于该复现输入，不宣称所有缓存边界或话轮行为均已验收。

原始最高logit在两路径均为`I`。实际加载的Qwen generation_config含`repetition_penalty=1.05`，`do_sample=False`仍会应用该惩罚。输入历史已出现`I`（token40），未出现`As`（token2121），故前者除以1.05，后者保持原值。

| 首正文候选 | 完整历史计算 | 跨请求缓存 |
| --- | ---: | ---: |
| `I` 原始logit | 14.4375 | 14.4375 |
| `As` 原始logit | 13.75 | 13.8125 |
| `I` 惩罚后实际分数 | 13.750000953674316 | 13.750000953674316 |
| `As` 惩罚后实际分数 | 13.75 | 13.8125 |
| 实际贪心选择 | `I` | `As` |

完整路径前两名仅差`9.5367e-7`；缓存使`As`原始logit增加0.0625（该量级下一个BF16表示步长），足以改变排序。首词改变后，自回归正文随之改变。诊断同时保留forward原始logits及`generate(output_scores=True)`返回的处理后分数，上表由实际生成器分数核验，而非只按公式推测。

## 对照证据

1. **实际服务复现**：按049探针的前五拍输入重新执行，完整路径与缓存路径各生成与旧记录完全相同的12个token；首控制均为`<|user finish talking|>`，首正文分别为`I`和`As`。
2. **缓存对齐**：实际保留140token，缓存登记ID与请求前140个ID完全相同。完整路径预填充150token；缓存路径只处理位置140–149的10token，mask总长150。下一步两路径都处理位置150，mask总长151，控制token相同。28层KV形状一致。
3. **独立拆分复现**：以同一150-token输入重算完整前缀，再分别以140单边界和101/113/128/140多边界拆分；固定共同finish token后，BF16两种拆分都再现惩罚后的首词翻转。无需历史生成分歧即可产生此现象。
4. **精度对照**：同一份已加载权重只扩展存储到FP32，保持参数值和输入，eager后端完整/拆分的首正文原始logits最大差异为`4.67e-5`及`5.27e-5`；重复惩罚后两路径均选`As`，前两名差距约0.03113。FP32重算使KV差异同步缩小，例如最后一层value平均绝对差由BF16 eager约0.20降至约`1.67e-5`（多边界）。
5. **后端对照**：BF16原后端为Qwen2SdpaAttention；单独切为eager后，完整/拆分依然出现惩罚后排序翻转，因此不能只归咎某一个SDPA内核或用更换attention后端保证解决。

上述对照支持低精度与计算分段引起的数值差异这一原因。PyTorch也说明不同计算形状的浮点运算不保证逐位一致，参见[官方数值精度说明](https://docs.pytorch.org/docs/stable/notes/numerical_accuracy.html)。这一说明仅作为机制背景，本项目结论依据本轮实际复现。

## 对实现和采用的影响

本次无需以“修复缓存错位”为由改写服务。保留当前BF16、权重、重复惩罚和600ms micro-turn；未修改线上生成行为。FP32仅用于原因诊断，不作为生产提速方案。

跨请求缓存可以继续作为性能候选，正确性评价应同时看前缀/位置的协议一致性、数值敏感性及完整对话行为；BF16下无法承诺逐token等同于每拍完整重算。不能将该数值解释替代暂停/插话/漏答回归，也不能因本例控制标记一致推断其他输入的控制标记不会变化。048的正式采用与更广在线验收继续跟踪，051仅完成这次生成分歧的原因诊断。

若未来要求与完整重算逐token严格一致，需要单独设计和测量更高精度、固定计算方式或歧义分数回退策略，收益及延迟都需重新验证。本轮不擅自引入这些机制，也不关闭重复惩罚以掩盖分歧。
