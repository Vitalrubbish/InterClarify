# TextTurn 全 keep 退化分析

2026-10-26，按用户要求分析现有 TT-010，不新增工作单。结论是：优先排查正例稀疏、按轨迹连续更新与梯度裁剪共同造成的优化偏置，其次是 pilot 来源和语义覆盖不足。三类总损失系数已经正确平衡，不能继续把当前结果简单归因于权重没有生效；具体梯度机制尚未得到实测确认。

## 首要怀疑：总系数平衡没有转化为平衡的参数更新

在本地conda中只读检查实际冻结pilot，使用当前`stage_loss_weights`和`trajectory_order`复现两个epoch，结果为：

| 项目 | pilot |
| --- | --- |
| 来源／完整轨迹 | 4／16 |
| keep／start／stop窗口 | 1870／16／8 |
| 三类各自有效权重总和 | 631.3333 |
| 单条start／stop有效权重 | 39.4583／78.9167 |
| 每轮参数更新 | 119次，累积16窗，末组按实际窗数 |
| 每轮仅含keep的更新 | 95次，占79.83% |
| 每轮含start或stop的更新 | 24次 |
| 最长连续仅keep更新 | 两轮均12次 |

实现只打乱轨迹之间的顺序，轨迹内部连续输入；每窗独立前向，未跨窗保留模型记忆。因此，时序完整并不要求优化器连续接收大量仅keep的更新。当前正例依赖少数高权重梯度纠正这些更新，每次更新又统一执行norm=1裁剪和AdamW。

推测的机制是：正例所在累积组若更容易触发裁剪，其权重放大不能按原倍数成为参数更新；大量低权重keep组仍能反复产生更新。AdamW的自适应缩放也使损失权重与最终位移不成简单正比。[PyTorch 2.11文档](https://docs.pytorch.org/docs/2.11/generated/torch.nn.utils.clip_grad_norm_.html)确认该裁剪作用于全部参数组成的总梯度向量。裁剪不会单独抹去同一组内某个类别的梯度方向，但会改变不同更新组的相对尺度。

这是当前优先验证的优化假设，**不是已经证明的根因**：现有训练未记录裁剪前范数、裁剪系数、逐类梯度或合法动作margin。全阶段等份目标本身不要求全keep；需要区分目标函数正确与有限训练过程是否有效。

## 第二个问题：窗口预算挤占了独立正例覆盖

完整来源组在2000窗pilot上限下只容纳4个来源。16个start仅覆盖8种不同用户正文；8个stop仅覆盖4种前缀：`Add`、`Please stop`、`Please stop speaking`、`Use a`。正常／打断变体重复使用同一用户表达，不能当作16种独立接话内容。两轮只提供48次正例样本呈现。

full也只有21来源／84个start／42个stop；按相同顺序复现，第一轮624次更新中501次仅含keep。直接放开pilot门槛进入full不保证消除相同机制。开发集200来源不能弥补训练的语义覆盖不足。

pilot全部16个start都在完整用户表达后的首个no-voice窗，前一窗虽已具有相同user_text却仍标keep。多数临近输入只有观察事件、版本或空窗计数等细节不同，单帧动作边界需要明确学习。该构造符合当前冻结合同，但正例太少时可能更难学会；不据此擅自修改标签、删帧或恢复固定等待。

## 次要因素与已检查的实现链路

训练在完整词表上做CE，评估则只比较Listen的keep/start或Speak的keep/stop。目标token的词表概率可以上升而合法动作排名仍不改变。因此，loss下降可能主要说明学会输出控制token，未说明学会何时start或stop。这不是标签位移错误，也不能单独解释全keep，适合作为后续受控诊断项。

检查`train_textturn.py`和真实pilot后确认：输入末尾动作被剥离后再取最后prompt位置logits，目标正是该动作；全部1894窗仅监督唯一末尾动作；未发现相同input_ids对应不同动作；正例长度123—718 token，未触及2048上限。训练和本次开发评估直接复用冻结input_ids，不经过Nemotron、TTS或外部输入适配。

评估直接对合法动作logits做argmax，不经过字符串解析或异常后默认keep。两轮预测无错误和截断行，故当前现象不能归因于解析回退。模型配置已绑定输入／输出权重，adapter配置启用`ensure_weight_tying`，新token保存与重载一致；这些证据降低了token注册或参数未保存的优先级，但不能替代逐动作梯度检查。

旧gate曾使全keep依靠两项误动作率为0获得0.4综合分并放行；这是验收缺陷，已经由1%正例下限修复。当前两轮被正确拒绝，gate不会改变训练梯度，因此修门槛本身不会修好模型。

## 建议的验证顺序

1. 先在远端对已保存的best和final检查点重评pilot全部24个正例及对应边界负例，记录每类召回、完整词表CE、正确动作相对keep的logit差。先区分训练本身未学会与开发泛化失败，不急于重训。
2. 在下一次获授权的训练中记录每类损失、各动作输出行梯度、裁剪前总范数及裁剪系数。若正例组持续严重裁剪而keep组没有，才有直接证据支持上述机制。
3. 再设计更新组织的最小对照：全部窗口保留、每条轨迹内部顺序不变，跨轨迹组织累积，减少仅keep的独立更新；同步核对归一化、总更新数和学习率日程。不能仅声明每个batch三类平衡而忽略24个正例与1870个keep的数量约束，也不默认复制正例。
4. 优化链路验证后再评估来源覆盖和完整词表／合法动作损失的影响，每次只改变一个因素。增加来源、改变窗口预算或监督合同均需用户明确授权；不通过放宽gate代替学习。
