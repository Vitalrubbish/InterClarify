# FDB提前start与后续stop的离线诊断

2026-10-25按用户要求，检查ASR最后更新前的start是否出现在语义相对完整的空观察位置，以及新增用户输入后是否及时stop；讨论UltraChat受控测试和960ms短暂占轮口径。本次仅分析既有trace及训练输入合同，没有启动模型、训练或新GPU作业，没有修改原评分、冻结数据或候选，也未新建issue。

结论：提前start的输入窗确实全部无新增ASR文本，但当前语义并非全部完整。后续没有stop是事实；将它直接解释为真实交互中的停止能力失败仍缺条件，当前FDB的Speak输入与训练合同存在明显差异。建议以UltraChat受控轨迹恢复主验收，FDB继续作外部行为诊断。

最新口径更新：用户随后明确不补语义标注，直接将ASR更新期间连续Speak超过960ms定义为抢话。以下此前关于补标的建议保留为诊断历史，不再作为该行为指标的实施前提。训练字段与助手正文前缀的区别、按新规则重评的结果见第5节。

## 1. 实际动作和观察覆盖

数据来自[已完成的同样本两周期测试](../20261025-fdb-action-only/README.md)，每周期包含接话50条、停顿50条。提前start按完整返回时刻严格早于本次在线ASR最后更新确定。

| 指标 | 480ms | 160ms |
| --- | --- | --- |
| 全部start／stop事件 | 85／0 | 93／0 |
| ASR最后更新前的start | 58 | 83 |
| 其中接话／停顿录音 | 23／35 | 37／46 |
| 输入窗原始user_delta为空，且观察为no-voice | 58/58 | 83/83 |
| start返回时，更高版本转写已经发布 | 13/58 | 37/83 |
| 其中在本次控制调用开始前／调用期间发布 | 11／2 | 30／7 |
| 新增转写发布后观察至少960ms，且后续Speak调用含有新文字，仍无stop | 54 | 81 |
| 后续控制未覆盖新转写，或960ms观察不足 | 4 | 2 |

这回答的是控制器可见ASR观察，不证明麦克风当时真正静音。尤其160ms的37次start，在完整返回时Context已有新文本；no-voice来自该请求固定快照中的窗口，不能外推为返回时仍无输入。固定快照与最新Context之间的版本滞后需要和语义判断分开解释。

本轮每条录音至多一次start，所有stop均为0。480ms的58次提前start中，57次在start后观察超过960ms且没有stop，1次仅观察477.86ms；160ms的83次均有超过960ms的持续状态观察。它们不等同“明确错误抢话”的数量。

新转写后960ms判断另有独立观察分母：480ms有3条未形成看到该转写的后续控制、1条时长不足；160ms有2条时长不足。这些截止不足不能填作成功停止或确定迟停，不改变原报告主指标的已判定分母。

## 2. 语义完整并非全部成立

查看全部141个提前start输入，共116个不同文本前缀，能直接找到未完成结构；无需把后续仍有录音当作其不完整的理由。以下是当前可见前缀的诊断性复核。

| 输入位置 | 当前前缀的关键片段 | 仅依据当前前缀的判断 |
| --- | --- | --- |
| 160ms，接话11，step24 | `If somebody in Idaho likes our website` | 只有if条件部分，主句尚未出现 |
| 160ms，接话107，step20 | `one of the reasons why` | 原因从句尚未完成 |
| 480ms，接话71，step48 | `is to get groc` | 当前ASR仍是词内片段 |
| 两周期，停顿97，step39／38 | `hasn't made you` | 缺少结果或补足语 |
| 两周期，接话115 | `I'm not excited for winter at all` | 已表达相对完整的态度，但不据此确定用户已经让轮 |
| 160ms，停顿15，step22 | `I hope your cat is healthy` | 已表达完整祝愿，但不据此确定用户已经让轮 |

相同接话11在480ms输入中已经具有条件句的主句，而160ms更早在条件部分start，说明频率变化可能暴露更早的空窗。既存在语义尚未完成时启动，也存在完整子句后的启动，不能把全部提前start都归为合理接话，亦不能只因之后继续说话便判其错误。

这里保存了8个绑定实际visible输入SHA256的单人诊断复核，用于反例与边界解释；没有对全部样本生成独立语义金标或整体语义正确率。原始完整前缀、首次后续新增文字及事件时刻只保留本地artifacts，不作为训练材料。

## 3. 不出现stop的解释受输入合同限制

读取实际冻结train／pilot，得到：

| 输入事实 | full train | pilot |
| --- | --- | --- |
| 总快照 | 10000 | 2000 |
| Speak快照 | 4253 | 783 |
| Speak中助手正文为空／生成状态为null | 0／0 | 0／0 |
| stop监督快照 | 160 | 160 |
| stop监督中助手正文为空／生成状态为null | 0／0 | 0／0 |

当前FDB恰好相反：Speak时助手正文始终为空、生成完成为null；start后历史仍为空，完整用户ASR前缀继续累积在同一个user_text。训练构造在start后把已完成用户轮移入history，清空当前用户正文，并逐步提供助手前缀；新用户输入随后成为新的当前用户段。差异不只有有没有模拟回答，还包括对话角色和轮次边界。

这套状态监控也没有回答自然结束路径：一次start之后，只要没有stop，夹具就把后续keep一直记为Speak，直到观察结束。连续Speak长度不能直接解释成真实助手输出或实际占轮时长，不能把夹具缺少自然结束与模型主动持续说话混为一谈。

stop的合同是用户打断系统，不是任意新增ASR都必须stop。后续新增内容可能是ASR词内补全、用户继续原话、附和或真正的打断，需要结合助手当前内容和当前语义判断。当前没有实际助手回答，也不具备完整的同分布Speak输入，因此可以确认状态一直未回退，不能仅据此确定真实打断机会已发生、或归因为模型停止能力失效。

此外，这160个stop监督仅有6种当前用户前缀，均围绕Stop／Wait／Please stop或pause，含标点和词段变体。已有UltraChat派生语音打断测试的v2结果为299正确、1未知，说明合适上下文和明确停止词下能触发stop；它不证明模型已学会所有自然续说场景。缺助手上下文是有证据的混杂因素，本次未做成对输入干预，不能宣称已证明它是唯一原因。

## 4. 960ms口径与下一步建议

建议按真实时间单列三种持续状态：start到stop完整返回之差≤960ms的短暂回退、超过960ms仍Speak的持续事件，以及观察不足的未知。不要用固定周期数替代：480ms／160ms的调度、合并及实际返回时刻不完全规则。

短暂回退可以从持续占轮指标中单列，但应保留原始start次数、起话时的语义合法性和回退耗时，不能从全部分母中删除后把误起话隐去。当前两个周期stop均为0，所以这次按960ms单列没有可剔除的短暂start→stop事件，也不会解释掉已有持续Speak。

同时分开两只时钟：start→stop衡量本次占轮持续多久；足以判定应让轮的新输入首次对控制器可见→stop衡量停止是否及时。用户在start数秒后才继续说、系统很快stop时，前者仍超过960ms，后者却可能正确；两者不能混成同一错误条件。首次新增ASR与明确打断依据的可见时刻也应分列。

建议下一步以UltraChat构造的受控事件轨迹做主验收：先给当前固定候选提供正确的history、用户轮边界和截至当时的助手回答前缀，标清完整表达、不完整停顿、普通续说、附和及明确打断；再用同一事件的真实ASR版本检验输入延迟影响。助手前缀是控制器已定义的输入，不要求TextTurn生成回答或引入真实TTS。

现有TT-004的接话语义锚点仍缺，原stop词汇覆盖也窄；不能直接重跑旧评分就称已经恢复可信验收。应先补当前输入依据和观察覆盖，固定候选与判定规则，FDB保留外部诊断。这里给出的是路线及评分建议，960ms只用于本次离线诊断，未改原验收门槛、测试标签、运行时或启动新试验。

## 5. 用户确认的960ms行为指标及角色标识澄清

训练代码`prompt_for`把结构化可见输入序列化到一个外层user消息中；内部`user_text`明确是当前用户内容，`assistant_visible`明确是助手当前已生成正文，`history`用role=user／assistant标识既往轮次。外层assistant消息位置是控制动作的输出位置。角色字段与ChatML边界始终存在，不存在把未区分身份的两串正文直接混合输入的问题。

此前所说助手前缀是assistant_visible中的正文前缀，不是身份标记。FDB保留这些字段名，但assistant_visible为空、生成状态为null、history为空；这属于内容与状态输入的差异，不能推导为模型无法识别哪个字段来自用户或助手，也不能仅凭字段值不同证明缺正文就是0 stop的原因。

按用户新规则，本次以首次至末次有效在线ASR转写更新的区间为观察范围。内部无更新的间歇仍属于该范围，不要求每一毫秒都有新字。每段连续Speak与该范围的交集实际时长严格>960ms记抢话，同条录音最多一次；恰好960ms不计，不累计不连续片段，末次ASR更新后的尾静音不计。状态边界取动作应用后真实记录时刻，不换算固定周期数。

| ASR更新期间连续Speak>960ms | 480ms | 160ms |
| --- | --- | --- |
| 接话子集 | 18/50，36% | 31/50，62% |
| 停顿子集 | 33/50，66% | 44/50，88% |
| 未知 | 0 | 0 |

这些是用户指定规则下的抢话比例，保留其定义和50条分母，不再以前缀语义是否完整补标决定。原报告连续3周期指标不覆盖或删除：两者时间范围和阈值不同。新结果仅离线重评已有200条trace，没有重新推理；原始逐段起止时刻、实际重叠毫秒及判定保留在`speak_overlap_960ms.json`。

该规则回答本次控制状态监控问题，依据已经齐备，无需先回到UltraChat或生成模拟回答才能计算。若后续要隔离助手正文对stop的因果影响，仍需独立的成对输入试验；本次没有据此重训、修改角色格式或启动新模型作业，也不将这个行为分数自动替代原四类完整验收。
