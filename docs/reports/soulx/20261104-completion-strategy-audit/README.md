# SoulX 原生 complete 行为审计

2026-11-04，NTF-038。只审查源码、官方资料及已有远端运行证据，未启动新 GPU 作业，未修改模型或前端行为。[逐帧复核结果](audit.json)记录本轮重新计算的来源计数与事件。

## 1. 判断

**当前原生 SoulX＋独立 X2 路线中，频繁提前 complete 直接出现在 SoulX 原生控制链路。** 原生控制链路包含 SoulX 状态模型、SenseVoice 教师、官方状态规则和 reset 历史，现有证据不能把责任全部归给模型权重。

当前没有发现把 X2 EOS 当 complete、把 WAIT 当静音、把 X2 正文写进状态 KV，或重复注入全文这类严重接入错误。已有预热真实权重等价性检查通过，但正式 FDB30 缺少完整单路对照，因此不能声称所有输入、调度和封装因素均已排除。

“complete 已可读”是当前局部语义判断；它既不证明用户不会续说，也不证明独立 ASR 的正文已齐。把它升级为不可撤销的整段完成信号，会放大误判。这是下游使用边界问题；当前尚未接入 LLM／TTS，没有真实播放证据证明已发生同等比例的抢话。

## 2. 当前实现与官方协议核对

冻结 SoulX 源码为 `a0b9063843df69619b087b95b74597b2176910b8`，本地子模块干净；`service/model.py` SHA256 与 `configs/native_soulx.json` 一致。原生配置保留 16kHz、160ms 主块、960ms 回看、40ms 前瞻、双语权重、英语 SenseVoice、`max_mistake_num=3`、`max_wait_num=8` 和远场阈值 0.02。英语教师选择符合[官方说明](https://github.com/Soul-AILab/SoulX-Duplug/tree/a0b9063843df69619b087b95b74597b2176910b8)。

| 文件／对象 | 核对内容 |
| --- | --- |
| `scripts/runtime/native_soulx_loader.py` | `load_native_controller()` 校验固定源码和资产，仅重定位资源；通过官方 `TurnModel` 加载，没有换教师 |
| `scripts/runtime/native_soulx.py` | `NativeSoulX` 通过 AST 增加观测，保留原生 infer、ASR 修订、状态反馈、服务规则和 reset；记录 raw／规则后／有效状态 |
| `scripts/runtime/independent_x2.py` | `IndependentX2.step()` 每 80ms 执行 LISTEN／DECODE；`ClosedText` 仅提交真实 EOS 闭合组，不接收 SoulX 状态；英语标签固定为 en |
| `scripts/runtime/dual_audio.py` | `PCMLedger` 保留同源 PCM；`DualAudioFrontend` 等两路完成再发布；reset 后从控制实际主块截止恢复供音，X2 缓存与正文保持 |
| `scripts/runtime/shared_context.py` | 联合提交当前状态和已闭合正文；分别保存两路真实坐标，未把 ASR 覆盖或 EOS 转成全文完成 |

X2 的 EOS 结束一次发射组，随后继续听音，不是用户话轮结束。该用法符合[X2 官方 LISTEN／DECODE 协议](https://github.com/X-Square-Robot/X2Streaming-ASR)。联合提交保证快照一致，不能修复状态本身的提前判断或 ASR 尚未发射的词。

NTF-018／019 预热原生对照比较了音频、教师识别、LLM 输入与 logits、服务结果、reset 和缓冲轨迹。它支持观测封装在该固定音频上的等价性；对照两臂使用相同恢复供音策略，不等于已对未经改造的官方网络送音策略做完正式 FDB30 对照。reset 还会重新初始化内部音频与语义历史，不能把跨 generation 的控制文本当作连续全文。

正式日志的非严格加载重试只列出额外的 `embed_tokens_func.weight`，未列出缺失键；它与官方源码中 embedding 别名注册顺序相符，现有证据不支持“关键状态权重没加载”这一解释，但没有逐张量另做权重等价性验证。

## 3. 当前 FDB30 的重新归因

原始运行 `ntf019-dual-20261103-r2`，固定 30 条、3180 个已发布批次；29 条完整，`candor_turn_taking-83` 超时后只有部分轨迹。保留失败样本及固定分母；不把后来取消 800ms 停止线当成历史运行成功。

### 3.1 模型与规则分别计数

| 来源 | 已发布帧中的次数 |
| --- | ---: |
| 原始 argmax 为 complete，服务接纳 | 32 |
| 原始 argmax 为 nonidle，被官方规则改为 complete，服务接纳 | 16 |
| 最终有效 complete 合计 | 48 |
| 原始 nonidle 被规则改为 incomplete | 73 |
| 全部规则改写 | 89 |
| 服务因等待兜底返回 speak，但五状态仍非 complete | 23 |

按 generation 重建连续空增量计数，89 个改写帧都满足“三次原始 nonidle、无 SenseVoice 新文字”，未发现重建不符。16 次新增 complete 均在该计数为 3 时触发。规则比较 complete 与 incomplete 两个 logits 后二选一，**不要求声学静音，也不要求 complete 是全词表 argmax**。详见[冻结官方规则](https://github.com/Soul-AILab/SoulX-Duplug/blob/a0b9063843df69619b087b95b74597b2176910b8/service/model.py#L682-L719)。

因此，48 次不是 48 次模型直接预测；16／48 也只是当前轨迹中的直接规则来源占比，不是“关闭规则后能减少三分之一误判”的因果效果。规则输出进入下一步历史，complete 还触发 reset，关闭规则必须完整重放。23 次等待兜底也不能混入 complete 来源；若要复现官方系统的回答动作，单看五状态 complete 会漏掉这条服务路径。当前项目选择将其保留为诊断，不自动变成正式回答许可。

### 3.2 接话 10 条：7 条原始模型提前，规则另增加 2 条

提前定义为状态的**实际观察截止**早于每条 FDB `[TURN-TAKING]` 区间起点；同时复核联合发布墙钟。两种坐标下，下面的样本来源分组相同，但事件数不同。

| 提前来源 | 样本数 | ID |
| --- | ---: | --- |
| 仅出现原始模型提前 complete | 4 | 102、17、56、91 |
| 原始模型与规则均出现提前 complete | 3 | 3、39、54 |
| 仅规则产生提前 complete | 2 | 51、83（失败样本的已发布部分） |
| 已发布轨迹未出现提前 complete | 1 | 76 |

原始模型涉及 7／10，规则涉及 5／10，二者重叠 3 条，合计 9／10。**这是既有轨迹来源拆分，不是关闭规则后的 7／10 对照结果。** 原始预测本身已能解释多数提前样本，独立 X2 正文没有进入状态模型。

### 3.3 有区分度的具体事件

| 样本 | 观察截止／发布时刻 | 标注边界 | 来源与可见内容 |
| --- | --- | --- | --- |
| 接话 17 | 0.80／1.029s | 5.32s | 原始 complete；两路都只识别到 `oh okay`，之后 X2 仍追加完整问题；下一次有效 nonidle 于 1.457s 发布 |
| 接话 51 | 3.04／3.247s | 7.82s | 原始 nonidle，经空增量规则改为 complete；SenseVoice 只到 `yeah I didnt know California`，之后继续说 |
| 接话 54 | 1.44／1.659s | 6.21s | 原始 complete；控制文本为 `Im Baer`，X2 正文仍为空，之后才追加毕业和搬家内容 |
| 接话 56 | 2.56／2.774s | 4.02s | 原始 complete；控制文本到 `at this point`，X2 后续追加 `think i'm too far gone`；提示局部完整前缀与整段结束并非同一边界 |

例 17 说明部分提前事件有局部自然句末；例 51 直接证明规则可以覆盖持续 nonidle；例 54 说明控制器并未获得 X2 后来较完整的正文。SenseVoice 错词或 reset 后短窗口识别可能参与误判，但没有真实参考词级对齐，不能把 X2 转写直接当作声音真值。

停顿任务的 11 个标注区间中，有 3 个区间出现有效 complete，涉及 Candor 16、161、40；**这三次均为原始模型 complete**，不是当前帧规则强制产生。三条随后均重新检出 nonidle。关闭空增量规则不能被假定为可以消除所有停顿误判。

原报告还有 48 次 complete 中 38 次之后继续追加 X2 正文，涉及 25 条。该现象混合用户续说和 ASR 延迟发射，不能全部称作漏尾词。本轮没有获得强制对齐或新增播放证据，不重新估计尾词缺失率。

## 4. 官方结果与我们的评价边界

官方论文的 complete 表示当前语义完成、可以交接；状态受当前文字和先前状态条件化。论文也承认极短块英语识别存在波动。其表 2 英语停顿 TOR 为 0.352、中文为 0.038，表明官方系统在英语停顿上的误接话风险本就明显；这些是**完整系统**指标，不能与我们 3／11 的状态事件直接对比，也不能用官方接话 TOR 0.933 推导出状态只提前 6.7%。见[论文第 3、5.2、6.3 节和表 2](https://arxiv.org/html/2603.14877v1)。

官方 dialogue-system 分支的 `clients/vad_client.py` 将 nonidle 返回为打断信号、speak 返回为交接文本；`app.py` 随 nonidle 调用 `session.interrupt()`，随 speak 启动响应流水线。因此官方系统持续处理后续语音并取消先前输出。我们的前端保留状态，但尚未接下游，当前 9／10 只能表示相对整段标注的提前事件覆盖，不能称作 90% 实际抢话率。参见[官方客户端](https://github.com/Soul-AILab/SoulX-Duplug/blob/dialogue-system/dialogue_system/clients/vad_client.py)与[输出取消代码](https://github.com/Soul-AILab/SoulX-Duplug/blob/dialogue-system/dialogue_system/app.py)。

现有设计已要求下游按共同快照处理续说和输出取消；当前以已提交的有效 complete 与正文作为普通回答边界。若实现时把一次 complete 当最终正文锁存后停止听音，或者没有在准备阶段和播放阶段落实取消，那才会构成额外的严重使用错误。慢消费者漏掉单帧状态、重复消费 complete 与消费后正文变化，仍需在未来接入阶段验收。

具体案例、官方 FDB 回放与在线演示的差别、取消后历史整理及 CPU 行为核查，见[后续运行时分析](../../../dev/SoulX-Duplug/completion_runtime_analysis.md)。其中说明性首音时刻与本报告实测状态时刻分别标注，不构成完整系统重测。

另一个现有问题是固定批次数结束不保证控制路覆盖真实 EOF：29 条成功样本中 26 条仍有约 5.3—320ms 控制主块残余。它会影响尾部／边界后 complete 的检出，不能解释前面数秒已出现的提前 complete，也不能用它证明模型结束能力已全面验证。

## 5. 最小后续验证建议

本轮结论足以定位现象发生在何处，若要判断各部分的因果责任，建议后续建立独立工作单，在同一远端环境、固定输入和单作业资源限制下完成：

1. 对同一 FDB30 完整重放原生单路、原生＋X2 两臂，分别对齐实际观察坐标和发布墙钟；同时明确官方连续送音与本项目 reset 后恢复供音的差别。
2. 只关闭“三次 nonidle 无文字”的强制分支，其他路径保持，完整重跑以覆盖 KV／reset 历史变化；不能离线删帧冒充消融。
3. 对 17／51／54／56 和三条停顿案例核查真实音频及词级时标，区分局部自然句末、控制教师误识别和持续语音中强制结束。
4. 真正接入后再测生成取消、首个可听音频、续说后的停播及正文利用，使用 FDB 官方系统评分；前端事件计数单独保留。

不建议继续靠更换并行正文 ASR 修复状态；当前 X2 正文没有进入状态模型，改善其 WER 不会自动修复 SenseVoice 教师与官方规则。也不建议直接用另一段固定静音时长覆盖原输出后宣称修好了模型。

## 6. 复核与证据

既有逐批协议审计仍只有超时样本的 `fixed_case_incomplete` 未通过，其余 29 条通过；这是记录完整性结论，不是语义质量通过。工作单完成后归档；正式实现及当前研究合同保持。
