# 工程实施计划

更新：2026-10-22。状态：设计已更新；当前先计划 X2-Turn 接入与 FDB 测试；Layer 0 实现和训练留作后续，均尚未执行。研究范围以 [research_design.md](research_design.md) 为准，执行状态见 [issue 索引](issue/README.md)。

## 1. 第一步的目标与边界

按用户最终决定，第一步只接入 X2-Turn 流式 ASR 与用户侧状态 token，经唯一仲裁器对接后续 LLM/TTS，再用 FDB 对话音频测试。当前不实现、采集数据或训练 Layer 0。系统 backchannel 保留在总计划，未来 Layer 0 只预测附和时机并开展专项训练。

该决定取代此前 Layer 0 基础话轮分类及本轮尚未提交的“立即训练附和”安排，阶段与职责见 [091](issue/archive/091_x2_turn_and_system_backchannel_scope.md)。保留既有 DuplexCascade special token 设计，运行时可以直接解释 X2-Turn 原生状态，不为拼写差异转换或重训。

| 模块 | 本阶段职责 | 输出 |
| --- | --- | --- |
| X2-Turn 前端 | 持续转写，预测用户语音/话轮状态 | 转写、原生状态、分数与对应位置 |
| Layer 0（后续） | 只判断系统此时是否适合简短附和；当前不实现 | 发出附和或继续等待的决策 |
| Layer 1 | 表达普通回答、附和、澄清；后续负责思考请求 | 待表达内容，不重复预测用户状态 |
| Layer 2 | 后续接入的异步澄清思考 | 结构化思考结果 |
| 唯一仲裁器 | 协调用户状态、系统附和建议及待表达内容 | 单一 TTS 路径上的提交/停止动作 |

用户 backchannel 与 system backchannel 方向不同。X2-Turn 输出用户附和，不等于系统应该跟着附和。Layer 0 不重新学习 complete/incomplete、用户附和或用户打断，不承担主动澄清价值判断，不自行播放音频。

主动澄清专项 benchmark 仍按研究方案第 5.6 节执行；系统附和是总计划中的后续能力，届时单独训练和评测，不把附和发声计成主动澄清。

## 2. 当前底座与接入缺口

当前已实现底座仍为 X-Talk `ca9b23c134b390107601bc98954ab16276d86db9`、Nemotron EN160、Kokoro `af_heart`、600ms micro-turn、300/1200ms TTS 分段及会话 KV 复用，见 [运行配置](runtime_baseline.md)。这是现役配置，不代表 X2-Turn 或系统附和已经部署。

双工路径通过 `duplex_control/service.py` 替换旧 `TurnDetectorManager/TurnTakingManager`，`DuplexRuntimeAdapter` 仍执行 DuplexCascade 生成的控制 token。实施时在该统一路径接入新的前端事件和附和建议，不能恢复第二套能独立开始/停止 TTS 的管理器。保留旧模型真实生成历史，其旧控制 token 在新模式只作诊断，不能同时执行。

当前小模型/训练及旧 X2 资产已按 089 清理；不能假定旧模型目录或 conda 环境仍存在。084 重新核查所需资产和环境，不恢复整个旧栈。

## 3. X2-Turn 前端与下游接口

X2-Turn 为本阶段采用的状态 ASR，先冻结权重、tokenizer、推理代码与流式 delay。此前 SoulX-Duplug、XTurnix、Smart Turn 等调研保留在 [候选记录](layer0_candidates.md)，作为来源和必要对照，不再并列等待选型；它们不成为 Layer 0 系统附和模型的替代品。

### 3.1 输入与输出合同

前端按真实到达顺序接收音频，输出当前累计转写、本次增量、原生状态及分数、状态对应的文本位置/音频截止点、会话/话轮/观察 ID、转写版本与结果到达时间。LLM 消费持续文本与状态；版本、计时及原始分数主要由运行时维护，不全部堆入自然语言 prompt。

原生状态包括 idle、noidle、incomplete/接口 speaking、complete/接口 turn_end、backchannel；发布接口另有 uncertain 回退，具体以冻结版本为准。它们描述用户状态，仲裁器结合实际播放状态解释接话和停止，不强造 DuplexCascade 的一一类别对应。

文本持续送给 Layer 1，不等 complete 才传送。接话事件到达时可立即调度空闲的 Layer 1，避免再等待固定 600ms micro-turn；正在推理则在明确边界消费新观察，不逐帧取消重算。是否立即发声由仲裁器和冻结策略决定，complete 不是无条件抢话命令。Layer 2 返回仍按研究方案原有注入规则处理。

### 3.2 时序、历史与质量

80ms 状态帧间隔、配置 delay、推理/排队时长、实际首音频和实际停声分别记录，不能混作一个延迟。当前已核查实时接口以追加转写和帧输出为主，未见 Qwen3-ASR 式替换历史文本协议；版本字段仍保留以便适配器和未来后端追溯。

X2-Turn 不再输出过去修订，不表示后续状态永远不变。新一帧可取消未提交的接话候选，不能抹去已执行错误动作。按真实观察记录文本、状态、预测、仲裁和已播前缀；完整音频离线两遍推理不能作为在线到达时序证据。

分别评估转写 WER/关键内容、用户状态、实际控制。话轮分类的 88.49% 不等于 ASR 词准确率。当前一步只验证英文基础链路；中文模型能力不代表已完成中文运行验收。

## 4. 后续保留：Layer 0 系统附和时机预测

本节仅保留总计划中的职责边界，当前不创建预测器、训练入口或附和播放支路，不作为第一步验收条件。

### 4.1 输入与职责

使用截至当前的语音特征/韵律、转写和 X2-Turn 状态、必要对话历史及系统实际播放记录，判断用户仍持有话轮时是否存在适合简短附和的机会。具体模态及上下文长度在开发集实验后冻结，不能预设只看 complete 或停顿就足够。

未来训练输出为“发出系统附和”或“继续等待”，可附分数。原生决策与具体协议 token 编码分开，编码名称在后续 086 实施时冻结，不把用户 backchannel token 改成系统附和 token。Layer 0 不选择完整回答或澄清，也不负责措辞生成。附和正文从 Layer 1 表达路径提供，短语候选或生成方式在后续细化，不增加独立播放器。

### 4.2 事件与仲裁

建议携带来源、观察版本、音频截止点、机会 ID 和有效窗口。每会话推理有界，重复建议合并为同一机会，旧版本或窗口过期不得触发迟到附和。推理失败单列，不伪装成模型预测无需附和。

同一仲裁器协调附和、轮后回答、主动澄清和用户停止请求。系统已有内容在播放时，不叠加附和音轨；普通回答或澄清已提交后，不能再执行旧附和。系统附和不标记成用户让出话轮，不结束当前用户表达，也不关闭 ASR/Layer 1 持续观察。用户实际打断时能停止当前附和。

记录预测机会、采纳/放弃及原因、待表达附和、TTS 请求与实际发声。未播内容可取消；已经听到的附和进入真实历史，不撤销、不删去。各类控制与请求 token 均不送进 TTS。

## 5. 后续保留：Layer 0 训练计划

系统附和训练保留为后续工作，不以 X2-Turn 的状态准确率是否足够为条件；当前不启动。以下规模与模型为规划参考，实施前重新细化数据、标注和预算，不构成当前采集或训练任务。

### 5.1 数据、标签与划分

优先核查可取得的双人对话音频及说话人/听者声道。将听者原有简短附和定位为候选窗口，再人工审核是否适合让系统表达；原始人类附和不是无条件金标，缺少人类附和也不能自动作为负例。预测器输入只包含用户音频前缀和此前已知历史，不能混入目标听者附和的未来音频。

先规划 200 个独立开发/试标机会，覆盖合理附和、应等待、正在提供关键条件、即将交接、长叙述、用户附和以及系统已有输出等情形。标注事件有效窗口与继续等待，允许争议/不确定。不得因一句“嗯”短就把它当系统正例；用户附和、系统回答和主动澄清分别标识。

试标后规划 2,000—5,000 个经审核训练事件，最终规模依据数据可用性和正负类覆盖确定，另留未参与调参的测试对话。按原对话、说话人分组，重叠窗口及增强不跨集合，不把多个窗口算成独立对话。数据与第 5.7 节主动澄清专项分别计数。

FDB ICC 及其他评测音频、其源对话和增强版本不用于训练或阈值选择。来源/许可、原对话 ID 和片段指纹核查后冻结清单，无法排除重叠的数据不加入训练。标签不能以未来续说倒推当前唯一动作。

### 5.2 模型、训练和开发检查

初始方案为现成语音编码器上的小型时机分类头；比较声学输入和附加文本/用户状态的价值，必要时开放末端层。参数规模、特征与学习率在 086 的数据/资源预检后冻结，不默认训练 4B 的 X2-Turn。首轮最多 3 个配置、各最多 3 epoch、固定种子，micro-batch 1—4、worker≤2，保留最佳/最终两个 checkpoint。

因果输入窗口必须在当时音频可用点结束，禁止编码完整录音后切分特征。长历史保留原始事实与截断记录；状态输入使用真实 X2-Turn 预测，不能只用完美标签训练后宣称线上可用。

文本特征加入原标点、去末尾标点、去全部标点及延后标点对照，保留在线转写时序；固定词序列的敏感性和不同 ASR 的识别/时间差分别统计。开发集选择阈值后冻结，再做正式 FDB。

验收重点是机会级 precision/recall、事件匹配、重复/迟到附和、应等待时误发声、实际延迟与失败覆盖；不能只看窗口分类 accuracy 或通过全程沉默降低误触发。具体窗口容差、目标门槛和抽检数在试标后、正式测试前冻结。

## 6. FDB 对话音频测试计划

当前评测 X2-Turn 转写、用户状态及基础接话/停播，与主动澄清专项 benchmark 分开。系统附和及联合执行留到 Layer 0 后续完成后评测；当前不以其效果验收。保留已有回放/等长音频/官方对齐工具，不把历史结果直接当新系统基线。

| 数据 | 数量 | 当前用途 |
| --- | ---: | --- |
| v1.0 candor_pause_handling | 216 | 用户停顿时是否错误抢话，区分合法短附和与普通回答 |
| v1.0 synthetic_pause_handling | 137 | 受控停顿及不完整表达处理 |
| v1.0 candor_turn_taking | 119 | 普通接话、漏接话、提前接话与时延 |
| v1.0 synthetic_user_interruption | 200 | 用户打断时停止，包括停止系统附和 |
| v1.0 icc_backchannel（后续） | 55 | Layer 0 实现后用于系统附和 Freq/JSD/TOR 与时机诊断；当前不要求发出附和 |
| v1.5 user_backchannel | 99 | 用户附和时是否误停，不作为系统附和标签 |
| v1.5 user_interruption | 200 | 真正打断与用户附和的控制区别 |

当前 v1.0 四项 672 例，v1.5 两项 299 场景；后续加 ICC 55 例时 v1.0 为 727 例。clean/overlap 成对回放是 598 次输入，不算 598 个独立场景。上游数量先对远端清单核实，缺失单列。v1.0 沿用固定评分提交 `3e799c45a045256f47d5f1c9cda90157e2d2ec9e`，v1.5 单独固定版本。

### 6.1 回放与对照

先在原四类各取 5 例（20 例）及 v1.5 各类 5 例冒烟；若复用历史 25 例，ICC 5 例仅作输入/协议诊断，不验收系统附和；只修复传输/格式/日志，阈值变更在独立开发集完成。标注、未来音频、完整转写和隐藏 current_turn_text 不进入在线模型。参考系统播放只根据此前已知对话安排，不按标注制造重叠机会。

控制诊断采用冻结参考播放，保证各条件同一机会；自由生成的系统测试另报实际播放覆盖，无播放时不能把没停播算正确或失败。当前对照为旧输入/控制链路与 X2-Turn 输入/原生状态控制，保持表达模型、TTS 和输入相同，保留输入/控制变化的限制。后续评测 Layer 0 时再用同一 X2-Turn、附和关闭/开启作对照，不放进本轮。

正式 output.wav 与输入等长，额外 5 秒尾窗只诊断，不计官方结果。逐段记录 output_kind=system_backchannel/answer/clarification，保留已播内容。官方评分按原脚本给出，同时用类型和人工抽检解释附和与抢话，不能修改官方定义后混称原指标。

### 6.2 评分与验收

后续系统附和评测报 ICC 官方 Freq/JSD 和 TOR，另报独立标注事件上的机会命中、误触发、重复、迟到与内容/类型抽检。频率越高不自动越好，JSD 接近不能证明每次附和合理。没有单次时机金标时明确覆盖限制，不伪造逐帧标签。

基础话轮分别报 Pause TOR、Smooth TOR/Latency、Interruption TOR/Latency、实际停止时延及有效播放机会。条件延迟与漏答/失败覆盖同时给出，负值保留原始值，未答延迟 null。GPT 内容评分维持既有暂缓决定，附和的人工审核另列；不将任务收益或实际恢复成本加入本阶段。

当前协议完成条件为：唯一仲裁/播放器，X2-Turn 用户状态来源明确，文本与状态对应位置可追溯，已播记录完整，全部样本有成功/失败记录，延迟口径和资源峰值可追溯。附和建议/取消在后续阶段验收。能力是否达到试标后冻结目标单独结论，不以作业退出 0 等同能力通过。

## 8. 远端资源与环境

本地沿用 conda interclarify-dev。当前远端按 X2-Turn 前端依赖建立隔离 conda，附和训练环境后续建立，X2-Turn 新版推理依赖不覆盖现役 ASR/TTS/评分环境；冻结可复现版本。旧 X2 环境已清理，重新预检安装。

| 阶段 | 上限 | 时间/并发 |
| --- | --- | --- |
| 资产与数据预检 | 4 CPU、8GiB RAM，必要时单 GPU | 1 小时，单作业 |
| X2-Turn 独立接入 | 1×24GiB GPU、8 CPU、32GiB RAM | 4 小时，单会话 |
| Layer 0 附和训练（后续预算） | 1×24GiB GPU、8 CPU、32GiB RAM、worker≤2 | 每配置 4 小时，最多 3 配置串行 |
| 联合回放/评分 | 最多 2×24GiB GPU、16 CPU、64GiB RAM | 8 小时，单会话；停服务后评分 |

模型实际峰值预检后确定共存方式，不自动加卡/增加工作数。共享权重/音频只读引用，每次独立 run_id，新增输出≤30GiB、单文件≤8GiB、启动可用盘≥50GiB；checkpoint 另列预算。资源触限有序退出，保留失败与退出码，不删除其他项目。

当前 ASR前端→表达模型→TTS 按需串行预热，附和服务后续加入，记录真实 ready。输出保留源码/权重/输入哈希、配置、资源采样、运行/评分退出码。大音频与 trace 留远端，Git 收简明报告；结束确认无遗留作业。
