# 工程实施计划

更新：2026-10-22。状态：第一步计划已制定，模型接入、训练和远端测试尚未执行。研究范围以 [research_design.md](research_design.md) 为准，执行状态见 [issue 索引](issue/README.md)。

## 1. 第一步的目标与边界

先实现独立的 Layer 0，验证基础话轮分类与控制，再用 FDB 对话音频检查暂停、接话、用户打断和用户附和。本阶段交付可独立回放的分类器、单一仲裁器中的接入点、远端运行入口及结果报告。

Layer 0 只判断基础话轮状态，不判断主动澄清是否值得发生。Layer 1 的外部状态适配和思考请求训练、Layer 2 接入及主动澄清专项 benchmark 留给后续步骤。系统 backchannel 保持关闭；用户附和分类不触发系统附和。不增设 Layer 3 或独立修订层。

分为两个验收层次：先用真实流式音频验证 Layer 0 本身，再接入当前表达模型检查实际播放控制。后者是过渡工程对照；当前 Layer 1 尚未适配外部状态，不能因此宣布整个新架构完成。

## 2. 当前底座与需要解决的接入问题

当前配置固定 X-Talk `ca9b23c134b390107601bc98954ab16276d86db9`，Nemotron EN 160ms ASR、80ms 音频传输、Kokoro `af_heart`、600ms micro-turn、300/1200ms TTS 分段及会话 KV 复用，见 [运行配置](runtime_baseline.md)。第一步先覆盖现有英文音频链路；模型支持中文不代表中文链路已经验收。

本地源码检查发现两个可复用部分和一个接入缺口：

- `xtalk/src/xtalk/models/turn_detector/xturnix.py` 已有 XTurnix 客户端，接收累计 ASR、暂停事件、系统状态和已播文本，处理文本修订及状态切换。
- `xtalk/src/xtalk/duplex_control/protocol.py` 已有五类状态及官方 token 映射；本项目已有 FDB 回放、音频等长处理、词级对齐和时序评分工具。
- `duplex_control/service.py` 在双工模式下替换了原有 `TurnDetectorManager` 和 `TurnTakingManager`，当前 `DuplexRuntimeAdapter` 直接执行 DuplexCascade 生成的控制 token。因此，仅在配置里增加 `turn_detector` 不会完成 Layer 0 接入；同时恢复旧管理器会造成控制路径竞争。

实施时在现有双工路径接入分类结果，由现有仲裁位置统一决定执行。不得启动两个能独立停止或开始 TTS 的管理器。当前 `_speaking` 标志与真实播放进度也需区分，模型已生成文本不代表用户已经听到。

**采用决定：先复用 XTurnix-PT 和现有客户端，增加 Smart Turn 的声学结束检测对照；先在独立开发数据上比较，再确定单模型或组合。当前没有核实到能直接满足本项目全部五类语义、在线协议和资源预算的现成方案，因此同步准备补充训练方案。** 不能把二分类结束检测器称为完整话轮控制器，也不能将 XTurnix 的所有 `speaking + keep` 直接标成用户附和。

## 4. Layer 0 的输入、输出与执行协议

### 4.1 输入与调用时序

输入包含截至当前的用户音频、VAD 状态、带版本的累计/增量 ASR、历史对话和真实系统播放状态。系统文本以已经确认播放的部分为依据；尚未播放的候选正文单独标记，不冒充用户已知内容。静音、ASR 暂无新文字、话轮结束是不同信号。

音频按现有 80ms 分块接收，ASR 沿用 160ms。Layer 0 在新 ASR、真实语音暂停及播放状态变化时调度；音频模型按其输入要求积累前缀，不对每个小分块反复运行完整模型。Layer 1 仍按 600ms micro-turn 消费最新外部状态；用户打断的停止建议可直接送入同一个仲裁器，不等待 Layer 1 完成生成。

每会话最多一个 Layer 0 推理在途，后续输入合并到最新待处理快照，完整事件历史仍保留。结果携带观察版本；ASR 被修订、播放对象已切换或结果已经过期时，不再用旧结果启动或停止新响应。先记录失败，再等待新观察；超时不能伪装成模型预测的继续倾听。

### 4.2 五类状态及 token

沿用现有官方词表，不新增同义 token。下表为输出语义合同；具体阈值在独立开发集冻结。

| 状态 | 含义 | 控制 token | 仲裁器的基础处理 |
| --- | --- | --- | --- |
| `USER_SPEAKING` | 用户正在持续表达，尚未让出话轮 | `<\|user is talking\|>` | 普通轮后回答继续等待；不能据此一律阻断将来的主动澄清 |
| `USER_YIELDED` | 当前证据支持用户让出话轮 | `<\|user finish talking\|>` | 存在待表达内容时可提交普通回答；不自行生成正文 |
| `USER_PAUSING` | 用户暂停，但当前仍应等待其继续表达 | `<\|user is thinking\|>` | 继续等待；这是可观察的话轮判断，不断言心理状态 |
| `USER_INTERRUPTING` | 系统播放期间，用户表达要求系统让出话轮 | `<\|user interruption\|>` | 停止对应响应的后续播放及未提交内容，记录已播前缀 |
| `USER_BACKCHANNEL` | 用户附和且没有取得话轮的意图 | `<\|user backchannel\|>` | 保持当前播放，不生成系统附和 |

`<|no voice|>` 只属于既有输入协议，不列为第六个预测类别。空输入、无有效证据、模型失败作为输出有效性或运行状态记录；不为凑齐五类而伪造语义标签。

适配 XTurnix 时，`listening + start` 是让出话轮的候选证据；`listening + keep` 需结合当前语音活动区分持续表达与暂停；`speaking + stop` 是用户打断候选。`speaking + keep` 只支持继续播放的动作，不能单凭该动作确认附和。若开发集不能验证五类映射，进入第 5 节训练分支，完整五类能力保持未通过。

每次输出记录 `session_id`、`observation_id`、`asr_version`、`response_id`、分类状态、token、原始模型分数、后端、输入音频截止点、输入构造/结果到达时间及有效性。组合模型保留各自证据，不把未校准的分数当成统一置信度。相同状态可重复观察，启动与停止动作按响应 ID 去重。

### 4.3 外部状态与单一执行权

Layer 0 状态作为带 `source=layer0` 的外部事件保留，不写成 Layer 1 自己生成的历史 token。控制 token 在运行时转换和过滤，不送进 TTS。

先提供影子模式：Layer 0 只记录结果，当前链路仍作为对照。启用 Layer 0 执行模式后，基础控制只采纳 Layer 0；旧 Layer 1 生成的同类 token 仍原样记入其真实生成历史并标记为诊断，不能作为第二条执行指令。当前 Layer 1 的文字作为过渡候选提交到统一仲裁器，是否真的能充分响应需单独报告。

首阶段不通过伪造助手控制 token、强制续写或偷偷改变模型历史来完成外部状态适配。Layer 0 有效，但旧 Layer 1 没有产生正文时，应报告“控制正确、表达缺失”。后续 Layer 1 训练另立工作单。

## 5. 没有合适现成方案时的训练准备

触发条件为：候选缺少必要语义输出；暂停/结束或附和/插话在独立开发集上达不到冻结门槛；或者在线推理不满足资源与时延预算。优先补足缺失能力，不立即从零训练大模型。

### 5.1 数据与标注

第一批制作 200 个独立开发观察事件，暂停/结束和附和/插话各覆盖至少 50 个事件，包含短停顿、长思考停顿、犹豫、自我修正、短促真实打断及较长附和。至少两名标注者独立判断争议样本，保留不可确定及其原因。该批数据属于 Layer 0 工程开发，不占用研究方案第 5.7 节的主动澄清试标额度。

如需训练，先规划 2,000—5,000 个经审核的事件，另留独立开发集；同一对话、说话人及其增强窗口按组划分，不把重叠窗口计成独立对话。语音片段必须配套系统是否在播、已播文本和当时可见 ASR。训练用在线 ASR 视图覆盖延迟、缺标点与修订，不仅使用离线完美转写。

数据来源优先核查 Smart Turn 开放训练集、项目既有基础话轮数据及可获得授权的双人对话。结束二分类数据只监督对应任务，不能自动产生附和/插话标签。短词、时长和重叠都只能是线索，不能机械标注；同一句“嗯/okay”必须包含附和与夺取话轮的上下文对照。

**FDB 全部评测音频及其所属源对话不用于训练或阈值选择。** 使用 Candor 等源语料时，按原始对话/说话人 ID 排除 FDB 对应来源，并补充音频片段指纹检查；无法完成来源核查的数据不加入训练。现成权重的预训练来源无法完全核验时，报告潜在重叠，不能宣称评测完全未见。

标注只依据当前可见前缀与播放历史。后续续说可辅助离线定位事件，但不能把未来发生了什么当成当前唯一标签。含糊事件保留不确定性，不强迫模型预测人类此时也无法确定的状态。

### 5.2 模型与训练顺序

1. 暂停/结束不足：优先以 Smart Turn 初始化，先冻结编码器训练分类头，再视独立开发集结果开放末端层。
2. 附和/插话不足：以截至当前的语音表示、ASR/已播文本表示及播放状态训练小型分类头；必要时对 XTurnix 进行小范围参数适配。先验证单模态对照，再决定是否融合。
3. 最终导出统一五类协议；训练可采用条件分类头，对不适用类别掩码。模型失败和无证据不作为伪语义监督。

使用交叉熵与开发集校准，单列误接话、误停、漏停。首轮预算：固定种子，最多 3 个候选配置、每配置最多 3 个 epoch，micro-batch 1—4，按显存预检确定累积步数，保留最佳及最终两个 checkpoint。先小样本验证标签和收敛，资源或数据不足时记录缺口，不启动无界搜索。

预训练编码器可能在输入窗口内双向注意，因此训练和推理窗口都必须在当前观察点结束；禁止先对完整录音编码再切分特征。保存代码、数据划分、权重和训练配置摘要，以及每类覆盖和失败记录。

## 6. FDB 对话音频测试计划

### 6.1 版本、任务与范围

FDB 用作基础话轮工程测试，与主动澄清 benchmark 分开。v1.0 优先复用远端已有数据和评分提交 `3e799c45a045256f47d5f1c9cda90157e2d2ec9e`；先核对清单，不能只按当前上游 README 假定远端文件齐全。v1.5 用户附和/插话补充数据使用单独清单与固定版本。

| 数据 | 上游数量 | 主要检查 | 口径 |
| --- | --- | --- | --- |
| v1.0 `candor_pause_handling` | 216 | 自然停顿时是否误接话 | 分类事件诊断；实际音频按官方 Pause TOR，越低越好 |
| v1.0 `synthetic_pause_handling` | 137 | 受控停顿处理 | 单独报告，不与自然停顿混成一个分数 |
| v1.0 `candor_turn_taking` | 119 | 用户让出话轮后的接话、漏接与时延 | 官方 TOR 越高越好；报告原始提前接话与条件延迟 |
| v1.0 `synthetic_user_interruption` | 200 | 用户打断时停播、打断结束后接话 | 官方 TOR/响应延迟，加项目实际停止时延 |
| v1.5 `user_backchannel` | 99 | 用户附和时是否误停 | 与下一行成对设计，先做分类/控制诊断 |
| v1.5 `user_interruption` | 200 | 附和之外的真实打断，检查漏停 | 冻结同一参考播放条件，按版本单列 |

数量依据 [FDB 官方数据说明](https://github.com/DanielLin94144/Full-Duplex-Bench/blob/main/v1_v1.5/dataset/README.md)。前四项合计 672 例，v1.5 补充 299 例。v1.5 的 clean/overlap 成对回放算 299 个场景、598 次输入，不算 598 个独立场景；与 v1.0 不合并成独立样本总分。

v1.0 `icc_backchannel` 的 55 例主要用于系统附和评价，与 Layer 0 判断用户附和不同；可沿用历史五类各 5 例中的相关样本检查协议，但不以生成附和的频率/JSD 验收当前系统。v1.5 的旁人谈话与背景语音不列入本阶段核心任务。

### 6.2 回放方式与因果约束

先冻结模型和阈值，再运行历史 25 例及 v1.5 每类 5 例做音频链路冒烟检查。这里仅修复传输、格式与记录问题；需要根据标签调整策略时，记录为工程开发使用，并重新冻结配置。正式全量不反复调参择优。

第一层为分类器回放：从 `input.wav` 按真实时间逐块发送，使用在线 ASR；完整转写、暂停/结束/插话标注只交给评分进程。分类器不可读取整段长度、未来音频、未来 ASR 或根据标注注入的静音。快速离线推理只能另报吞吐，不能作为在线时延。

用户打断和附和需要系统正在说话的上下文。分类器测试使用各候选相同、预先冻结的参考系统音频，经同一播放状态接口回传当前已播前缀。参考回复依据已公开的前序对话生成，不读取当前插话的隐藏文本；播放时序不根据事件标注安排。原数据中的 `context_text` 需确认确为前序已知信息，`current_turn_text` 和 `timestamps` 不给在线模型。无法恢复此前可见上下文时保留缺失标记，不补写理想历史。

v1.5 对同一场景分别回放 clean/overlap 输入，保持相同参考播放。独立评分后才用标注检查事件时系统是否正在播放；没有实际重叠机会的样本保留，单报不适用及原因，不当作附和正确或打断失败。参考播放模式只验证分类和控制，不冒充自由生成的完整 FDB 官方成绩。

第二层为当前系统回放：由当前表达模型自由生成，经同一 TTS 链路播放，用相同输入比较旧链路与 Layer 0 控制。没有在插话时播放的样本，不进入“应停播”分母；仍进入全量覆盖统计及适用的官方响应指标。停止建议、停止请求、最后实际播放音频分别记录，不能把收到停止事件当作已经停声。

正式 `output.wav` 与原始输入等长。现有 5 秒尾窗只用于诊断和排出 ASR 尾部，不进入官方评分；单列仅尾窗回答与完全未答。该固定回放不含用户对系统新行为的反馈，不据此估算任务收益或恢复成本。

### 6.3 指标与对照

| 层次 | 指标与分母 |
| --- | --- |
| 五类分类 | 在经复核且适用的观察事件上报告混淆矩阵、每类 precision/recall/F1、macro-F1；另列未覆盖、无效和争议样本，不用插值标签伪造逐帧准确率 |
| 暂停/结束 | 误接话率＝未让出话轮事件中错误启动数/适用事件数；漏接话率＝明确让出话轮后预算内未启动数/适用事件数 |
| 附和/插话 | 误停率＝附和事件中实际错误停播数/附和时确有播放的事件数；漏停率＝真实打断后预算内未停数/打断时确有播放的事件数；同列覆盖率 |
| 在线时延 | 音频到达、ASR 可见、模型推理、仲裁、实际首音频和实际停声分别计时；报告 p50/p95、超时和缺失，不只报告平均值 |
| 官方音频评分 | 分别报告 Pause TOR、Smooth TOR/Latency、Interruption TOR/Latency；分类 token 的启动率不能替代音频 TOR |

FDB 的原始标注不是完整五类逐帧金标。缺少类别真值时只报告任务事件指标；五类完整结果依靠独立人工复核事件集，标注版本与覆盖数量一并公布。用户插话的“响应延迟”与“停声延迟”分别计算。

当前工具对部分官方延迟将负值归零，报告同时保留原始负值及提前接话数量；未接话延迟为 null，不填零。GPT 相关性评分沿用当前暂缓决定，只做官方词级对齐与时序评分，不能把 TOR 解释为回答内容正确。

最小对照为同条件旧链路、VAD 固定静音阈值基线、XTurnix-PT、Smart Turn 的暂停/结束结果，以及最终完整 Layer 0。每个候选只报告其支持的任务，训练分支触发后补充训练前后对照。分类器对照共享音频、ASR 事件流和参考播放；全链路对照另行使用相同冻结组件重放。

历史完整两轴报告为 59/119、160/200 有效接话，见 [r4 报告](../reports/fdb/20261021-full-two-axes-r4/README.md)。历史使用旧候选和旧快照，仅供定位问题；本轮重跑匹配基线后再判断改善。历史已使用的 FDB 样本明确标为已接触的工程测试，不能宣传成全新盲测。

### 6.4 进入测试与完成的判据

先通过接口和独立开发集，再进行完整 FDB；避免只优化接话率造成暂停误插话，或一律继续播放造成漏停。以下为首轮开发目标，不是已验证性能或研究结论，变更须在完整 FDB 前记录并冻结：

- 独立开发集五类 macro-F1 目标 ≥0.85，每类 recall ≥0.80；误接话率、用户附和误停率各 ≤5%，真实打断检出率 ≥90%。同时给出实际数量及区间，小样本不作稳定性能保证。
- Layer 0 单次推理加排队 p95 目标 <200ms；超过 600ms 的结果必须明确过期处理。实际停声 p95 目标 ≤1 秒，并保留由输入音频、ASR 延迟和播放缓冲构成的分解。不得通过排除失败样本满足目标。
- 全量回放每例有成功或失败记录，所有预期输出有身份与时长核验；单一执行者、控制 token 不入 TTS、已播内容不撤销等协议要求全部满足。
- 若现成方案只能通过动作测试而缺少完整五类证据，转入补充训练；若训练后仍不满足目标，报告瓶颈和未通过项，不能以作业退出 0 宣布能力验收通过。

## 8. 远端运行与资源预算

本地使用已有 conda `interclarify-dev` 整理接口及文档。远端分类器/训练使用独立 conda 环境 `interclarify-layer0`，具体 Python 和依赖在模型预检后锁定；不照搬上游 venv 步骤。当前 ASR、TTS 与 FDB 评分环境只读复用。

| 阶段 | 初始资源上限 | 时间与并发 |
| --- | --- | --- |
| 资产/数据预检 | 4 CPU、8GiB RAM，必要时单 GPU 健康检查 | 1 小时；单作业、单会话 |
| 分类器回放/开发检查 | 最多 1×24GiB GPU、8 CPU、32GiB RAM | 每次 4 小时；单作业、单推理在途 |
| 条件训练 | 1×24GiB GPU、8 CPU、32GiB RAM | 每配置 4 小时硬限，最多 3 配置串行；DataLoader worker ≤2 |
| 全链路回放与评分 | 最多 2×24GiB GPU、16 CPU、64GiB RAM | 每作业 8 小时；单会话串行，结束服务后再评分 |

以上为计划上限，不是显存适配已通过。模型、ASR/TTS及评分预检测峰值；若无法在两卡上共存，先减小 XTurnix 服务预分配与缓存，在预算内分阶段运行。需要新增资源时先记录证据和预算修订，不静默增加工作数。

每次新运行根采用 `/hpc_stor03/sjtu_home/xuan.zhang/interclarify-layer0-<date>-<run_id>/`。共享数据和权重只读引用；新增输出上限 30GiB，启动要求至少 50GiB 可用盘，单文件上限 8GiB，训练 checkpoint 额外预算在训练清单中列明。监测 RAM、VRAM、输出目录和文件系统配额，达到上限有序退出；不扫描或删除其他项目。

ASR→TTS→表达模型→Layer 0 按阶段串行预热，不以启动进程代替 ready。作业保留提交 ID、源码/权重/输入摘要、实际配置、资源峰值、逐阶段退出码与失败样本。音频、完整 trace、权重留远端；Git 只收简明报告及必要摘要。退出时关闭本作业进程并确认无遗留活动作业。
