# InterClarify 分阶段工程落地方案

## 1. 文档目的

本文把 [research_design.md](research_design.md) 中的研究构想转换为可以执行、验收和停止的工程计划。工程顺序固定为：

1. 先复现 DuplexCascade 官方推理框架，保存可比较的原版基线；
2. 用最小实现快速验证“话轮内主动澄清”是否存在可研究、可交互的现象；
3. 现象成立后再完善训练数据、训练方法和系统测试；
4. 最后开展正式对照实验和真人评测。

这里的“复现”首先指官方权重下的推理与交互能力复现，不要求在项目开始时重建论文的完整合成数据和训练流程。只有推理基线和澄清可行性都成立，才考虑训练 Layer 2 决策器。

## 2. MVP 范围与工程原则

### 2.1 当前研究范围

MVP 只选择一个可程序核验结果的任务域。默认采用**日程安排中的日期和时间选择**，因为它容易构造会改变最终动作的歧义，也能用日历槽位和最终事件进行核验。如果快速验证表明该域缺少自然的句中澄清机会，再根据阶段门禁决定是否更换为联系人选择；同一轮实验不混合多个任务域。

系统研究对象是 Layer 2 的澄清判断与交互闭环：

- 当前前缀是否存在会改变任务结果的解释分歧；
- 分歧是否仍未解决，用户是否可能马上自行说明；
- 当前是否适合接话；
- 能否生成一个具体、简短、可回答的问题；
- 收到回答后能否恢复同一个任务。

Layer 0/1、流式 ASR、TTS、用户插话停播和常规回答是参考系统能力。MVP 不重新训练完整语音系统，也不建设通用任务编排平台。

### 2.2 必须保持的控制边界

- Layer 0 只产生 `SILENCE` 或低强度 `BACKCHANNEL`。
- Layer 1 负责常规 `SILENCE` / `ANSWER`，并可请求 Layer 2。
- Layer 2 只产生 `NO_OVERRIDE` 或澄清问题；识别到歧义也可以选择等待。
- 只设一个输出仲裁器。有效输出优先级为 Layer 2、Layer 1、Layer 0。
- 只设一个 TTS 播放所有者。其他模块提交播放意图，不能直接操作音频设备。
- 已经播放给用户的音频不可撤销。高优先级输出只能取消或替换尚未提交播放的片段。
- 当前研究设计未启用 Layer 3。为兼容项目约束，可预留修订接口；若后续启用，Layer 3 只能提交带版本号、且仅针对未提交片段的修订补丁，不能直接播放或修改已播内容。
- 在线策略只能读取决策时刻以前到达的音频、ASR 前缀和修订事件。隐藏目标、完整转写、未来音频和最终真值只能用于构建数据或评价。

### 2.3 统一完成定义

一个阶段只有同时具备以下四项才算完成：

1. 可运行产物：脚本、配置或服务入口可在全新 conda 环境中执行；
2. 可追溯产物：依赖、模型、数据、提示词和配置都有版本记录；
3. 可检查证据：日志、结果表或试听样本能支持验收结论；
4. 对应文档：实现文件在 `docs/` 下有同路径说明，记录功能、主要类和核心方法。

## 3. 总体阶段与门禁

| 阶段 | 核心目标 | 主要产物 | 继续条件 |
| --- | --- | --- | --- |
| P0 工程准备 | 固定范围、环境和记录格式 | conda 环境、配置、运行清单 | 本地和集群环境可重复创建 |
| P1 DuplexCascade 复现 | 跑通官方权重和原版双工链路 | 原版服务、事件日志、FDB 基线 | 原版可稳定交互，关键事件可观察 |
| P2 快速可行性验证 | 最小代价确认现象和交互闭环 | 小样本语音、规则/提示策略、试交互报告 | 存在足够的可问窗口，提问后可以恢复任务 |
| P3 数据与评测基础设施 | 形成可训练、可审计的数据资产 | 回放器、标注格式、切分和检查工具 | 数据无未来泄漏，正负轨迹覆盖充分 |
| P4 决策方法与可选训练 | 固定 Layer 2 方法并完成对照 | 各策略实现、可选 LoRA、消融结果 | 主方法在固定底座上有稳定收益 |
| P5 系统测试与正式评价 | 验证通用能力和论文主张 | FDB 对照、真人实验、最终报告 | 结果支持或清楚限定研究主张 |

P1 和 P2 是项目最早的两个强制门禁。P2 未通过前，不开展大规模数据生产、LoRA 训练或正式真人实验。

## 4. P0：工程准备

### 4.1 目标

建立能在本地开发机和远端 8×RTX 4090 集群重复使用的基础环境，并提前固定所有实验必须记录的信息。

### 4.2 工作项

1. 创建独立 conda 环境，固定 Python、PyTorch、CUDA 和音频依赖版本。
2. 登记 DuplexCascade 仓库提交、模型权重修订、许可证或 Hugging Face 访问条件。
3. 检查音频输入输出设备、采样率、声道、缓冲区和回声消除条件。
4. 建立统一配置层，区分本地开发、离线回放和集群实验配置。
5. 定义一次实验的清单：代码提交、模型修订、配置摘要、随机种子、设备、开始结束时间和输出目录。
6. 为集群准备环境创建和任务提交脚本；实际集群运行前在 `docs/jobs/` 中建立对应任务单。

### 4.3 交付物

- `environment.yml` 或等价的锁定环境文件；
- 模型和第三方依赖清单；
- 本地、回放、集群三类配置模板；
- 最小运行说明和实验清单格式。

### 4.4 验收门槛

- 新 conda 环境能够导入核心依赖并识别预期 GPU；
- 模型权重可访问，或已经明确记录无法访问的条件和替代时间表；
- 同一次离线输入在相同配置下产生结构一致的日志。

## 5. P1：复现 DuplexCascade 推理框架

### 5.1 复现边界

本阶段使用 DuplexCascade 官方推理代码和已发布权重，优先保留其原有 ASR、LLM、TTS、micro-turn、backchannel 和用户插话停播路径。暂不修改模型权重，也不添加 InterClarify 决策逻辑。

若官方 ASR/TTS 因语言、许可或实时性能无法服务目标域，可以替换，但必须先保存官方组合的结果；替换后的底座由所有后续策略共用，不能为某个对照单独调整。

### 5.2 实现顺序

#### P1.1 官方离线样例

- 拉取并固定官方代码提交；
- 完成模型访问和权重校验；
- 固定最小输入并运行原版推理路径；固定的 DuplexCascade 提交只有实时 `server.py` 入口，没有独立离线样例，因此以薄适配器注入固定输入，并保留官方 ASR、控制模型与 TTS 行为；
- 保存输入、配置、原始输出、GPU 峰值显存和实时因子。

上述离线输入适配是对官方发布内容的执行补充，不改变模型权重、控制决策或服务所有权。权重下载与 GPU 验证均在服务器端进行。

P1.1 的代码、配置和任务单通过本项目 GitHub `main` 分支传到服务器；服务器先从 GitHub 更新干净工作树，再在共享存储下载官方代码和模型资产。模型文件不进入 Git，也不通过本地开发机中转。

#### P1.2 实时双工链路

- 分离 ASR、控制模型和 TTS 服务；
- 接入麦克风和扬声器，验证系统发声时仍接收用户音频；
- 验证静音、backchannel、常规回答、用户打断停播和继续倾听；
- 连续运行一组脚本化场景，观察崩溃、队列堆积和音频设备抢占。

#### P1.3 统一事件日志

至少记录以下事件：

```text
audio_chunk_received
asr_partial / asr_revision / asr_final
micro_turn_tick
layer0_decision / layer1_decision
tts_requested / tts_ready
playback_committed / playback_started / playback_stopped / playback_finished
user_barge_in
```

每条事件包含单调时钟时间、会话 ID、话轮 ID、输入前缀版本、来源模块和必要载荷。日志中的文本需要区分“模型生成”“已提交 TTS”“已经播放”三种状态。

#### P1.4 Full-Duplex-Bench 基线

- 先完成评测适配器的 smoke run，再运行资源允许的 FDB v1/v1.5 项；
- 优先保存停顿处理、backchannel、顺畅接话、用户打断和重叠语音指标；
- 固定数据版本、判分脚本和音频后端；
- 报告本地复现绝对值，不以复现论文原始数值作为硬性成功标准。

### 5.3 P1 验收门槛

进入 P2 前必须确认：

- 官方或明确记录的等价底座可以完成端到端 ASR–LLM–TTS；
- 系统发声时仍能接收用户音频，并能在用户插话时停止未完成播放；
- backchannel 和常规回答可以在日志中区分；
- 同一条输入能够从音频、ASR 前缀、控制决策追踪到播放事件；
- 已得到一份可作为后续回归参照的 FDB 结果；若完整 FDB 暂时不可运行，至少保存适配器 smoke 结果和明确的阻塞项。

### 5.4 失败处理

- 权重不可访问：先完成日志、回放和接口桩，不声称完成底座复现；取得访问后优先补齐。
- 实时音频不稳定：先用预录音频和虚拟播放时钟复现控制路径，再单独修复设备链路。
- 指标与论文差距较大：固定环境并定位 ASR、TTS、音频后端和评测适配差异；不为追平数值延迟 P2 的现象验证，只要底座行为可用且差异被完整记录。

## 6. P2：快速可行性验证

### 6.1 本阶段只回答三个问题

1. 真实的流式语音前缀中，是否存在数量足够且人能识别的“有后果、尚未解决、可问可接、可恢复”窗口？
2. 最小 Layer 2 策略能否比单纯 ASR 不确定性更准确地选择这些窗口？
3. 用户回答澄清问题后，系统能否把答案并回原任务并完成正确动作？

本阶段不追求模型最优，也不生产正式训练集。目标是尽快得到 go / revise / stop 结论。

### 6.2 最小数据

围绕日程时间选择准备约 30–50 条探索性任务轨迹，覆盖四类情形：

- 持续存在、会改变最终日历事件的歧义；
- 用户在后续短语中自行消歧；
- ASR 先识别错误、之后修订；
- 表面不确定但不会改变最终动作。

优先从真实语音数据中筛选，缺口再用定向录音补充。所有音频按原速流入实际 ASR，保存当时可见的部分转写和修订；人工完整转写只作为离线审计材料。探索集不能直接包装为最终测试集。

### 6.3 最小 Layer 2

第一版使用规则和提示词，不训练模型。每次调用接收：

```text
session_id
turn_id
prefix_version
visible_asr_prefix
asr_revision_summary
task_state_visible_to_system
speech_state: SPEAKING | PAUSING | ENDED
request_time
```

输出固定为：

```text
decision: NO_OVERRIDE | CLARIFY
question: string | null
candidate_interpretations: list
consequence_difference: string | null
self_resolution_risk: low | medium | high
prefix_version
```

只有 `decision=CLARIFY`、问题非空、请求版本仍有效且用户没有自行消歧时，仲裁器才接受覆盖。问题限制为一句，直接指出会改变结果的差异，例如“你说的是周二上午还是周四上午？”。

### 6.4 最小异步与播放控制

建立一个单写者状态机：

```text
LISTENING -> CANDIDATE_PENDING -> CLARIFYING -> WAITING_FOR_REPLY
          -> ANSWERING -> LISTENING
```

- Layer 2 请求绑定 `prefix_version`；关键 ASR 修订、用户自行消歧或任务改变会使旧请求失效。
- Layer 1 等待 Layer 2 时继续原有行为，慢速语义调用不能阻塞 micro-turn。
- 有效澄清到达后，只取消未提交的 Layer 1 音频。
- 用户在系统发声时插话，播放控制停止后续音频并返回倾听状态。
- 系统问完后让出话轮；用户回复被解析为对原任务状态的补丁，随后恢复该任务。

### 6.5 快速评测

依次完成三种低成本检查：

1. **盲前缀审计**：评审者只能听到决策时刻以前的音频，判断有无后果分歧、问题相关性、可回答性和时机得体性。
2. **脚本化用户或模拟器闭环**：给用户端隐藏目标，检查确认、否定和补充能否进入原任务并得到正确最终事件。
3. **小规模真人试交互**：覆盖持续歧义、自行消歧和无需澄清场景，记录是否听清、是否被抢话、是否重复叙述以及是否完成任务。该试验只用于修改设计，不作为论文正式结论。

### 6.6 Go / revise / stop 门禁

快速验证结束时形成一页决策报告，至少给出以下证据：

- 探索集中正例和三类关键负例的数量；
- 两名评审者对部分样本的分歧情况；
- 规则/提示策略、句末策略和不确定性策略的触发混淆；
- 闭环任务正确率、澄清后恢复率、错误插话和用户重复次数；
- 典型成功与失败录音。

采用以下工程门槛决定是否扩大投入：

- **Go**：至少找到 15 个经审计的可澄清窗口；负例不只来自单一模板；小规模交互中大多数澄清能被听懂、回答并恢复原任务；错误插话没有压倒潜在收益。
- **Revise**：现象存在但窗口稀少、问题难回答或时机普遍偏差。优先修改任务域、停顿条件或问题形式，再做一次同规模验证。
- **Stop / 缩小主张**：两轮验证后仍主要观察到用户自然自我消歧，或澄清后无法稳定恢复任务。此时停止大规模训练，把研究改为句末澄清或失败边界分析。

“大多数”和“错误插话没有压倒收益”在正式实验前要根据 pilot 分布写成数值化预注册标准；本阶段不根据几十条探索样本制造论文级显著性结论。

## 7. P3：数据与评测基础设施

P2 通过后再开始本阶段。目标是把探索性材料转成可扩展、无未来泄漏且能复现实验的正式数据流程。

### 7.1 数据对象

每个会话至少包含：

- 原始音频和音频元数据；
- 隐藏任务目标、候选实体和最终动作真值；
- 带时间戳的 ASR partial、revision 和 final 事件；
- 每个决策窗口当时可见的前缀快照；
- 候选解释及其对应的任务结果；
- 分歧出现、持续和消失时间；
- 用户是否自行消歧、ASR 是否自行修订；
- 允许的动作标签和评审理由；
- 系统干预后的用户响应、任务状态补丁与最终结果。

### 7.2 标注流程

1. 程序从流式日志生成候选窗口，不让标注者手工寻找全部时间点。
2. 标注者先看前缀视图，标记分歧、后果、可回答性和时机。
3. 另一视图显示完整未干预轨迹，只用于记录用户是否自行消歧，不能反写“系统当时理应知道”。
4. 部分样本由两人独立标注，保留原始分歧并计算一致性。
5. 程序检查时间戳单调、前缀无未来文本、候选结果确实不同、版本引用存在。
6. 按说话人和场景划分 train/dev/test，同一录音及其变体只能出现在一个集合。

### 7.3 回放器

离线回放器必须按原始时间重新发出音频块和 ASR 事件，并提供两种时钟：

- 实时时钟：测量实际延迟、队列积压和打断位置；
- 虚拟时钟：快速重复策略和数据检查。

所有策略读取同一事件流。原录音后半段只表示“系统未干预时用户如何继续”，不能当作插话后的真实反应。

### 7.4 P3 验收门槛

- 随机抽样无法从在线特征看到未来转写或隐藏真值；
- 数据包含持续歧义、自行消歧、ASR 修订和无后果分歧；
- train/dev/test 在说话人、录音和模板族上无交叉；
- 任一评测决策能回溯到原始音频、前缀版本、策略配置和判分记录；
- 标注指南经数十例校准后稳定，再决定正式数据规模。

## 8. P4：决策方法、对照与可选训练

### 8.1 固定对照

在同一底座、音频、ASR、TTS 和任务设置上实现：

1. 原版 DuplexCascade：不主动澄清；
2. Wait-until-end：只在句末考虑澄清；
3. Uncertainty-trigger：根据识别不确定性询问；
4. Direct-LLM：每个固定窗口直接判断是否提问；
5. InterClarify：使用结果分歧、自行消歧风险和接话线索；
6. 若最终采用按需调用，再比较逐窗口强模型和同等调用预算的触发策略。

### 8.2 先提示，后训练

开发顺序固定为：

1. 规则基线；
2. 结构化提示的强模型基线；
3. 根据开发集误差分析判断是否需要训练；
4. 只有提示方案在质量、延迟或成本上无法满足要求时，才训练决策器或 LoRA。

训练目标只覆盖关键分歧识别、接话时机、`NO_OVERRIDE` 判断和短问题生成。冻结 ASR、TTS 和原版控制模型。先进行单卡或少卡短跑，记录峰值显存、每步时间和吞吐，再决定 8×4090 的数据并行或分片方式。4090 不按统一 192 GB 显存规划，也不默认依赖 NVLink。

若需要复现 DuplexCascade 论文的训练流程，将其作为独立子里程碑，不阻塞 InterClarify 主实验；数据合成、LoRA、词嵌入和输出头训练需单独记录。

### 8.3 消融与误差分析

至少移除以下信号各做一次消融：

- 是否改变任务结果的语义分歧；
- 用户即将自行消歧的线索；
- 说话、停顿和句末状态；
- ASR revision 和前缀版本有效性检查。

错误按以下类别归档：误把 ASR 错误当语义歧义、抢在自我消歧之前提问、问题没有指出差异、问题过长、过时覆盖、播放冲突、用户回答未并回任务、恢复后执行错误。

### 8.4 P4 验收门槛

- 所有策略使用完全相同的在线输入和底座；
- InterClarify 在开发集上改善问题相关性或闭环任务结果，同时没有不可接受地增加错误插话；
- 所有 Layer 2 输出都通过版本有效性检查；
- 训练方案若未超过结构化提示基线，则保留提示方案作为最终方法，不因已投入算力而强行使用训练模型。

## 9. P5：系统测试与正式评价

### 9.1 测试层次

#### 单元级检查

- 前缀版本递增与旧结果失效；
- 仲裁优先级和空输出处理；
- 播放提交边界；
- 用户插话后的停播；
- 澄清回复到原任务状态的合并；
- 数据切分和未来信息泄漏检查。

#### 确定性集成场景

- Layer 2 提前返回、晚于 Layer 1 返回和超时；
- ASR 在 Layer 2 计算期间关键修订；
- 用户在澄清问题中途插话；
- 用户确认、否定、补充新值或改变任务；
- 连续两个候选窗口只允许一个有效澄清；
- TTS 已生成但未提交、已提交但未播放、正在播放三种覆盖边界。

#### 音频与实时回归

- 网络和模型延迟抖动；
- 长会话队列积压；
- 麦克风回声、噪声和重叠语音；
- 进程重启和服务超时后的安全降级；
- 原版与最终版本的 FDB 对照。

### 9.2 正式研究评价

分别报告，不合并成未经验证的总分：

- 时机得体性、问题相关性、可回答性、真人接话顺畅度；
- 最终任务正确率和澄清后恢复原任务比例；
- 插话次数、用户重复或修复轮数、完成时间；
- 重叠插话、话轮内停顿接话和句末澄清的分组结果；
- 持续歧义、自行消歧、ASR 修订、无后果分歧的分组结果；
- 模型调用次数、端到端延迟、峰值显存和成本。

真人对照实验在收集前固定主要指标、排除条件、样本选择和分析方法。参与者顺序需要平衡，同一参与者不能重复获知同一题目的隐藏目标。静态回放和 LLM 裁判不能替代真人互动证据。

### 9.3 最终门槛

- 最终系统与原版 DuplexCascade 使用同一 FDB 版本和判分脚本；
- 通用双工能力的绝对值和差值都完整报告；
- 若 FDB 退化，能定位到触发、仲裁、播放、ASR 或 TTS 中的具体责任模块；
- 论文主张只覆盖有证据支持的任务域、插话类型和运行条件；
- 按需 Layer 2 只有在质量和延迟比较都支持时才作为贡献。

## 10. 核心模块与接口边界

### 10.1 建议运行时模块

| 模块 | 职责 | 禁止行为 |
| --- | --- | --- |
| `StreamingASR` | 产生 partial、revision、final 和版本 | 不读取任务真值 |
| `MicroTurnClock` | 以固定起点 0.6 秒触发决策 | 不直接决定输出 |
| `Layer01Adapter` | 映射 DuplexCascade 控制 token 和文本 | 不等待 Layer 2 阻塞主循环 |
| `ClarificationTrigger` | 决定是否发起 Layer 2 请求 | 不直接播放 |
| `Layer2Policy` | 判断等待/澄清并生成短问题 | 不使用未来输入 |
| `ResultValidator` | 检查版本、任务和自行消歧状态 | 不改写已播内容 |
| `OutputArbiter` | 单点选择 L2/L1/L0 输出 | 不拥有多个播放通道 |
| `PlaybackController` | 唯一管理 TTS 队列、提交和停播 | 不撤销已播音频 |
| `TaskStateReducer` | 把澄清回答合并回同一任务 | 不另开无关任务 |
| `EventRecorder` | 保存时间线、配置和结果 | 不把离线真值注入在线模块 |

### 10.2 版本有效性规则

Layer 2 结果满足以下全部条件才可覆盖：

```text
result.session_id == current.session_id
result.turn_id == current.turn_id
result.prefix_version == current.valid_request_version
task_state has not materially changed
ambiguity is not already resolved
question is non-empty and passes output constraints
target audio segment is not committed
```

任一条件不满足都记录 `layer2_result_stale` 或具体拒绝原因，然后回到 Layer 1/0 的正常路径。

## 13. 风险与收缩策略

| 风险 | 最早暴露阶段 | 应对方式 |
| --- | --- | --- |
| 官方模型或权重访问受限 | P0/P1 | 保存条件与版本，先完成接口和日志，访问恢复后补齐 |
| 4090 显存或互联不满足训练设想 | P4 | 先短跑，缩小 batch、梯度累积、checkpointing，必要时分片 |
| 真实句中澄清机会太少 | P2 | 调整单一任务域或收缩为句末澄清/边界研究 |
| 用户普遍在系统发问前自行消歧 | P2/P3 | 加强等待建模，把自我消歧作为主要负例 |
| ASR 修订能力不足 | P1/P3 | 明确限制或更换统一底座，所有方法共享相同 ASR |
| Layer 2 延迟导致过时覆盖 | P2/P4 | 版本失效、调用预算、超时和轻量触发 |
| 澄清问题正确但任务无法恢复 | P2 | 优先修复状态合并闭环，暂停扩大数据与训练 |
| InterClarify 损害通用双工能力 | P4/P5 | 用 FDB 和事件日志定位触发、仲裁或播放责任 |

## 14. 推荐近期执行清单

按依赖顺序执行以下工作：

1. 建立 conda 环境、第三方依赖清单和模型访问记录；
2. 固定 DuplexCascade 官方提交与权重修订，跑通离线示例；
3. 跑通实时 ASR–LLM–TTS 和用户插话停播；
4. 接入统一事件日志和 FDB 适配器，保存原版基线；
5. 构造日程时间域的 30–50 条探索轨迹；
6. 实现规则/提示版 Layer 2、版本检查、单一仲裁器和单一播放控制；
7. 完成盲前缀审计、脚本化闭环和小规模真人试交互；
8. 形成 go / revise / stop 报告；
9. 只有得到 go 结论后，才扩展正式数据、训练和完整测试。

这一路径把最昂贵的数据生产和训练放在两个早期事实得到确认之后：DuplexCascade 底座确实可复现，以及话轮内澄清确实能在目标域中带来可观察的交互价值。
