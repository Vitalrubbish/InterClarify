# FDB原始ASR轨迹的稳定等待分析

对应`scripts/analysis/analyze_fdb_asr_stability.py`。只读既有FDB实录的ASR轨迹，不调用模型、修改源run或执行评分；本地与远端均使用既有conda。`collect`阶段远端CPU线程1、地址空间2GiB、外层180秒，读取总预算1GiB，单文件32MiB；按最终报告选取SoulX的672条来源，不选取助手已播声音的回转写。压缩副本和每条源文件摘要写入ParaThink独立分析目录。

`Ledger`按照锁定官方源码重建音频账本：51200样本窗口初始填充、25600样本话轮填充、2560样本处理块、640样本前瞻和reset后被丢弃的旧前瞻。根据`controller_raw`与`controller_state`回放已发生的状态分支，区分窗口调用和完成／等待兜底的整段调用，并逐次检查重建音频长度与`asr_begin.audio_samples`一致。这只是源码和日志的离线重建，不执行状态预测；不以仅有`available_end_sample`声称完整真实覆盖。非连续片段及不能重建的样本明确排除和报告。

只纳入原始输入范围内已处理包的ASR返回，不将8秒追加静音作为新确认。按同样本、generation和真实音频起点分组；窗口自然移出不算同词改写，短组不判稳定。复用`analyze_asr_stability.analyze_group()`的词前缀端点、末次变化和三次新增音频确认定义，直接使用ASR源头结果，Context正文冻结不增加一致票。英文比较忽略大小写和标点，不构成精确字符稳定保证。

完成分支的音频可能没有包含最近idle块，导致同起点整段调用的截止倒退。此时显式切分证据epoch，不能把短音频结果当作扩大音频后的新票；epoch之后不再声称之前前缀永远不会变化。`confirmation_policies()`分别统计2／3次证据条件下，从首次假设到确认，以及最终形态已出现后额外等待的实际返回时间；尾部缺证据单列，不填0。

FDB确认额外要求实际ASR调用编号连续且覆盖截止严格增长，由`final_evidence()`统一检查；中间发生窗口移位后再回到同起点、或重复解码同一音频，必须重建连续确认窗口，不能拼凑确认票。这比最初开发轨迹分析的“同起点有效票累计”更严格。

`analyze()`验证压缩摘要、逐样本重建，汇总所有样本及各FDB子集。输出包括失败分母、短组、排除原因、时间和额外ASR更新数、两次／三次确认后仍被改写的反例。前缀端点相关，不能当作独立词准确率；至少3次后续证据不足的尾部不填0。详细数据写入`artifacts`，报告仅保存中文汇总。

每次调用还检查`available_end_sample`匹配当前处理包，整段调用数量与服务`speak`分支一致。`common_cohort()`在同一批满足三次确认的端点上比较2／3次等待，防止不同覆盖分母使较严格策略的尾部分位数反而看似更低。

“稳定后再给LLM”的新增等待在固定已有轨迹上回看估计，不会变更实际运行的调用调度，因此不等于新稳定策略已接入后的端到端实验。Context原子写入开销、等待稳定开销及LLM输入边界等待须分别报告；最终回答延迟不能简单加上所有词的等待时间。
