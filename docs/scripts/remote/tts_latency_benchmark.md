# TTS 固定文本组件基准

`tts_latency_benchmark.py` 使用固定服务的 `/tts/ws` 协议，显式传入唯一 session ID 来关联服务端时间线。原 smoke 客户端不暴露这一 ID；因此这里复用其同一服务协议，直接记录二进制帧接收时间，避免把客户端内部缓冲计入服务生成。不是新的产品运行时或播放器。

`run_case` 按预定到达时间推送 JSONL 的文本增量，同时接收 PCM；整句与增量分开重复和汇总。`PlaybackEstimate` 以接收时刻估算立即启动的虚拟缓冲、断流次数与时长，不驱动声卡。`pcm_onset` 使用 10ms RMS 阈值估计波形起点，`summarize` 对有效、失败、无音频和有声样本分别计数；首 PCM 与有声时间保留不同指标，失败不填零。每例保留 WAV、时间线、配置和异常。`analyze_server_trace` 仅计算同一服务进程内的完整 span，并标出缺项；不跨进程相减，不自动断言主要瓶颈或切换优化。

CLI 的 `--prepare-corpus` 生成 30 条短答/澄清及 5 条边界文本，每条有固定增量与时间表。`--output` 必须为新目录。`--repeats` 至少 3，额外 warmup 单列。`--reference` 是服务器可见的固定音色路径，启动消息显式传入；本地摘要与服务器路径是否对应需在任务单核对。`--server-trace` 可选合并同一主机可读的 JSONL，仍保留各自时钟域。失败退出非零，报告照常写出。

`first_pcm_stages` 以服务首次 command 入队至首个非空 PCM 入队为本进程区间，按 prefill、step、codec、音色准备的完整 CPU span 分割；重叠区间单列，其他时间明确标为未归因，不把嵌套 span 相加。它不是首文本至可听首音指标，也不能把未归因时间直接认定为排队或文本等待。只有补全缺项并对照后才能进入 TTS-004 的优化选择。

无音频同时输出数量与比例；首包样本数保留分布。连接与 started 等待均有超时，空网络包不算首 PCM，非完整 PCM16 样本视作协议失败。

`manifest` 记录本仓库、显式提供的 X-Talk/MOSS 路径之提交与工作树状态、客户端 conda/dependency 版本、实验环境变量和补丁摘要。服务 trace 另记实际 TTS 环境、加载文件摘要和原始音色摘要；模型 revision 仍须核对锁文件，不能用客户端包版本代替服务端版本。
