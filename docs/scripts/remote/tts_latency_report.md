# TTS 延迟报告生成器

`tts_latency_report.py` 使用标准库读取原基线与同卡筛选结果，生成中文 Markdown 和 JSON 摘要，不调用模型、不修改运行时。`summarize_run` 按输入模式、轮次和文本汇总首 PCM、波形有声估计、倍率与模拟欠载；失败/无音频保留分母，正式响应与预热按 ID 分开。

`trace_checks` 在同一进程/响应内核对 token 接收、实际消费、结束余量，提取 worker 接受文本至 prefill 的门槛等待、前 1/5/10/50 帧耗时和 Dynamo 图增量。没有事件时标为缺测，不能把缺测当通过；token 完整性不代表语音无漏词。`compare_runs` 只比较相同文本/模式/轮次，batch4 另核对 PCM SHA256；prefill 候选改变条件，不要求其音频与 control 相同。

`build_report` 记录作业完成标志、源码、GPU、配置和日志诊断，按候选列出收益与失败。未完成的 arm 标为待完成，不把局部结果写成最终验收；即使指标改善，也保留人工试听、真实播放器和 FDB 未验收的边界。`render_markdown` 生成完整报告，不从已有模板填入假定收益。

CLI 为 `--baseline` 原基线根、`--screen` 同卡筛选根、`--output` 报告目录。输出 `tts_latency_optimization_report.md` 与 `tts_latency_results.json`，可重复生成本任务报告；原始 WAV/JSONL 保留在远端对应 run 根。报告仅使用可复核文件，不依赖日志里自称“通过”。

基线若未开启重编译日志，其计数为缺测而非零；日志中的 `recompile_limit` 回退单列。sparse 是人为构造的压力流，不代表实际 LLM 的发生频率。报告解释低文本供应速率下首 PCM 与持续供音可能分离，不把提前 prefill 等同为解决全部首音问题。

可选读取 `screen/intelligibility/summary.json` 或 `--intelligibility` 指定的离线 ASR 诊断，按输入模式呈现词错误与整句匹配；不混合不同模式作质量排名，缺测明确保留，人工试听状态仍为未完成。

`complete` 表示所有计划的作业/候选都有终态（包含失败），`all_runs_successful` 才表示所有运行均无失败；二者都不代表质量验收通过。预热失败的候选单列错误原因，不以“缺少正式结果”为由隐藏失败。

`--early-retest` 单独读取首轮 inference tensor 生命周期修复后的双臂复测。原失败保留，复测仅对同一新卡的 batch4/early 作配对，不跨卡借用原 control。所有计划必须有终态后报告才标作完成，实际响应数不为失败候选补零。

早期编译复测另记录 PCM 一致数、生成音频长度和前 N 帧 p50；若随机采样下音频发生变化，不能把全部有声时刻改善归为后端执行，也不能宣称逐 token 无损。前 N 帧成本提供独立的执行开销证据。

报告开头自动给出实测要点，明确批次收益的长句集中性、前 N 帧执行成本、小门槛筛选规模、deadline 正式新图与 ASR 唯一音频数。对正式区间仍有新图的候选逐轮展开，不把完整分布剔除异常后重新命名为“热态”。音频/墙钟倍率明确包含输入等待。

Markdown 只保留预热次数/最大值等简洁诊断，完整日志序列和错误上下文仍在 JSON；报告明确可听首音预算未达、整体延迟未验收，不以候选小集合结果替代目标完成。可用保存的 JSON 调用 `render_markdown` 重现文档，不需要再次运行模型。
