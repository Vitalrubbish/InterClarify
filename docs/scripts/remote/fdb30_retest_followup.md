# FDB30 复测顺序衔接

对应 `scripts/remote/fdb30_retest_followup.py`，用于NTF-054。只负责跟踪已经提交的smoke作业、检查证据，再顺序提交正式推理和评分；不加载模型、不调整推理配置。

`audit_run()`按NTF-057核对样本数、完整预热、明确的一致性检查取消记录、四进程CPU预算、控制执行线程、complete跳过事件及实际播放录音，不再要求原生对照通过。校验使用原前端conda的CPU进程，不在登录节点调用GPU。

`Campaign`持有独立state.json和排他文件锁，恢复时沿用已保存job ID；提交前要求用户GPU队列为空，并拒绝覆盖已有输出。每30秒检查一次，最多新增正式推理和评分两个作业。已知作业仍在队列时不提交下一阶段；作业离队且退出码为0后才审计或推进。任何缺失、错误、超时均保存failed状态，不自动挑样本或重跑。

正式推理沿用冻结模型源码与现有三卡入口，12CPU／64GiB、7200秒、每卡22GiB、输出2GiB。评分独占单卡、4CPU／32GiB、3600秒，仅TOR／延迟；退出码写在submit_logs的独立文件。衔接进程使用远端base conda，绑定一个CPU、2GiB地址空间、最长12小时，没有GPU作业资源申请。

脚本源码摘要、模型源码提交、各阶段job ID、命令和审计结果路径写入state.json。NTF-057将源码提交改由`--source-commit`显式传入，要求与干净源码目录及已保存状态一致，避免继续使用历史65d15e6。只有三个阶段和正式录音审计均成功才记为complete。

只读`vc list`失败时最多重试3次，依次等待5／15／30秒，每次查询45秒超时，累计查询次数最多4次；错误、重试次数和输出保存在状态中，成功后清除当前错误。持续失败则停止，不能当作空队列推进。提交操作不自动重试，避免结果不确定时重复提交。
