## 2. Candor TOR=1 与 synthetic TOR=0 的原因

Pause Handling 的 TOR 越低越好。官方脚本不读取 `pause.json` 来限定判分窗口，而是检查整个 `output.json`：没有词为 0；有词时，只要从首词到末词的跨度达到 1 秒，或短于 1 秒但词数超过 3，就记为 1。因此它不能区分“停顿内抢话”“恢复说话后才播出的迟到回答”和录音尾部截断；分析需要回到时间线。

### 2.1 输入节奏与截断确实不同

| 样本 | Candor 标注停顿长度（秒） | synthetic 标注停顿长度（秒） | synthetic 实际结果 |
| --- | --- | --- | --- |
| 1 | 0.68 / 0.79 | 0.16 | 无 TTS，输出转写空 |
| 10 | 0.97 / 1.48 | 0.88 | 7.903s 启动 TTS，8.618s 首 PCM，输入长 8.864s，输出转写空 |
| 100 | 0.69 / 0.98 | 0.16 | 无 TTS，输出转写空 |
| 101 | 0.99 / 1.08 | 1.42 | 有声学停顿释放，但无 TTS，输出转写空 |
| 102 | 1.18 / 0.78 | 0.08 | 无 TTS，输出转写空 |

Candor 五条均有被对齐器识别出的完整发言；synthetic 五条 `output.json.chunks` 全空。因此 synthetic 的 0.0 首先是“没有被评分器识别出的发言”，不等于模型正确识别了所有句内停顿。样本 10 已有一次潜在抢答决策，只是输出太晚；样本 101 的停顿甚至长于 Candor 的多数停顿，不能把两组差异完全归因于 600ms 阈值。

回放器 `_run_fdb` 在输入发完后只短暂等待，最终 `normalize_wav_duration` 把输出裁成输入长度。Candor 输入长约 7.36–28.80s，早期停顿之后有充分时间录到误答；synthetic 输入约 7.49–9.50s，停顿靠后且输出易被截断。应保持官方评分输入口径，同时在独立诊断录音中保留更长尾部，报告潜在抢答决策数和真正可听输出。

### 2.2 更关键的实现问题：停顿释放后，可见 ASR 会长期停滞

Candor/1 的时间线：

1. 约 2.434s 后端 VAD 发 speech end，约 2.5s ASR 释放 `I never like I know like a lot of people.`。
2. 2.786s 已收到用户恢复说话的 VAD start。
3. 到约 11.1s 才有下一次 ASR 文本更新；两次可见更新相距 **8.56s**。这期间模型反复收到空增量，wire 输入为 `<|no voice|>`。
4. 3.709s 开始 TTS，4.457s 首 PCM，4.88s 对齐首词；用户早已恢复说话。回答还误解成“不喜欢与人相处”，而实际后续是讨论美妆/育儿视频。

Candor/100 在首次释放后约 **6.24s** 没有可见更新，下一段之后又停滞约 **20.92s**；/102 首次释放后约 **4.32s** 没有更新。/10 同样有约 **5.16s** 空档。这些空档与用户实际持续说话不符。

代码链条能解释该风险：`ASRService.recognize(is_final=True)` 将整个当前转写（含原本不稳定的尾部、句末标点）写入 `committed_ids`；随后继续沿用同一 Qwen 流状态。`advance_committed` 遇到任何已交付 token 的回改就返回旧文本，等待原前缀重新一致。把字符串比较改成 token 比较消除了部分格式问题，但**没有消除 final 后下一段继续解码时的前缀冲突**。原始 `services/asr.log` 有 11 条该警告；下一次 `is_final=True` 又绕过提交检查发布全文，形成“中间冻结、到下个停顿才一大段跳出”的观测模式。

证据强度：可见文本停滞与恢复发声已经由时间线确认；token 提交冲突是代码和服务警告共同支持的强假设。现有日志没有逐请求 raw/committed token 与 session 关联，仍需远端定向复现来排除 Qwen `finish_streaming_transcribe` 状态复用本身的影响，并精确确定冲突位置。不能把全部空档都当作已逐条证明的同一种内部原因。

声学 pause 只触发 ASR 释放；`DuplexRuntimeAdapter._append_user` 不把 `speech_state` 作为显式语义端点传入模型，回答仍由模型的 `<|user finish talking|>` 决定。故“600ms VAD 直接强制接话”和“阶段 A 不含 TurnSense，所以必须等阶段 B 才能修”均不成立。Layer 1 本来就负责常规话轮和停顿处理；修复 ASR 可见性属于阶段 A，无须接入 Layer 2。

## 3. 两类延迟的逐段分解

定义：STT 从 `turn_taking.json[0].timestamp[0]` 开始，UI 从 `interrupt.json[0].timestamp[1]` 即插话结束开始；终点为对齐首词。STT 只有实际接话的 4 条进入延迟均值，沉默的样本 1 单独作为失败；UI 为 5 条。以下均为秒。

| 段 | STT 平均 | UI 平均 | 解释 |
| --- | ---: | ---: | --- |
| 标注锚点 → 最新完整 ASR | 0.375 | 0.509 | VAD 静音等待、ASR flush 和标注差异的合计 |
| 完整 ASR → 产生回答的 micro-turn 请求 | 0.938 | 1.042 | 节拍相位等待，随后模型还等待一拍空输入 |
| 该请求 → 模型首 token | 0.034 | 0.061 | 当前短上下文下的模型与服务耗时 |
| 模型首 token → TTSStarted | 0.024 | 0.022 | 控制 token 后的首段文本与 TTS 会话启动 |
| TTSStarted → 首 PCM chunk | 0.732 | 0.738 | 当前 MOSS 文本积累、prefill、音频生成等合计 |
| 首 chunk → 对齐首词 | 0.455 | 0.477 | 音频起始静音/发音、播放交付及对齐器差异的合计 |

### 3.1 插话停播另有一个约 3 秒的问题

| UI 样本 | 插话开始→客户端 stop_tts |
| --- | ---: |
| 1 | 3.092 |
| 10 | 2.268 |
| 100 | 3.465 |
| 101 | 3.895 |
| 102 | 2.606 |
| 平均 | **3.065** |

这不是表中 2.848s 的指标。后者是插话结束后开始新回答；这里测的是旧回答多久才停止。原始 timeline 的 stop request→TTSStopped 只有亚毫秒量级，客户端收到 stop 的交付也很快，因此主要等待发生在**发出停播决策之前**。新发声必须先经 ASR 600ms 分块、提交窗口、micro-turn 消费和模型判断才触发 interruption token。VAD start 只恢复 ASR，不直接停播，以避免把用户附和全部当作打断。修复输入交付与衡量“首个可见插话词→interruption token”应优先于优化停止函数。

### 3.2 现有汇总中容易误读的量

`summarize_timeline.llm_to_tts_started_seconds` 取整个会话最早 `llm.first_chunk`，不是匹配回答 request_id 的首 token；其中包含倾听和多拍等待。UI 的 `first_audio_seconds` 又是第一个问题的旧答案首音频，不能代表插话后的新答案首音频。`TTSStarted` 表示交付窗口打开，也不是已经有 PCM；首个 `response.update` 是播放文本确认，也不是音频首词。以上量必须按 request_id/response_id 匹配后分别报告。

## 4. 修复优先级与远端复核条件

1. **先修 ASR pause/resume 后的文本停滞。** 记录每会话 raw token、committed token、首次冲突下标及是否 final；用 Candor/1、100、102 回放复现。优先验证“每个声学片段建立新的解码/提交状态，外部拼接已释放前缀”的方案，避免拿不稳定尾部锁死后续流；必须检查词尾、复述、片段重叠和是否丢音，不能仅换一种前缀字符串比较。实现前先更新 ASR 文档及契约，再在远端 conda 环境做小规模 A/B。
2. **修观测与验收口径。** 匹配回答请求测首 token；分别报告 UI 停播、新回答首 PCM、对齐首词；保留官方等长 WAV，再另存长尾诊断录音。synthetic 潜在抢答和 STT/1 持续沉默不能被 PASS 或 TOR=0 掩盖。STT/1 完整转写已进入模型，但 17 拍全部输出 talking，属于真实模型/输入历史问题，不是等待 TTS。
3. **减少节拍叠加，但先确认协议效果。** ASR 和 micro-turn 均为 600ms，实际经常在 micro-turn 刚读完后才交付新 ASR；相位错开损失约半秒，再等一拍无词约 0.6s。远端先对比相位对齐/缩短窗口，保持一条串行 LLM 流，检查 pause TOR、backchannel 抗误打断、UI 停播及回答质量，不能只比较 STT 延迟。
4. **针对 MOSS 首包继续剖析。** 当前首包仍约 0.74s，占总延迟约四分之一；稳态吞吐提升到约 2.25 倍实时不代表首包已足够快。需服务端区分文本积累、参考音色/模型 prefill、首 codec 包和客户端交付。chunk→首词约 0.46–0.48s 不能全部归咎于 TTS 算力，先通过 PCM 能量起点与人工试听区分静音和对齐偏差。
5. **最后再考虑模型服务吞吐优化。** 当前回答请求首 token 34–61ms，不是本批次秒级延迟主因。源码每拍重建全历史 prompt、重新 generate，没有跨请求 KV cache，较长 micro-turn 解码也会阻塞下一次读取；这是长会话潜在瓶颈，但不能用它替代本批次已有的分段证据。

以上修复保留阶段 A 的模型 token 决策边界、单一 TTS 播放所有权，不引入 Layer 2/3，不撤回已经播放的内容。当前未运行新模型实验，修复收益须由远端同样本 A/B 验证。
