# 英文实时 TTS 最终选型报告

## 结论

**推荐 Pocket TTS 3.3.0 / Alba 作为下一步英文实时主线的接入对象。Kokoro 82M / af_heart 是本轮人工综合评分第一名，保留为音质优先、允许整句或分段完整合成时的对照选择。** 当前不自动切换或并行运行两套播放路径，也不宣称已完成现役 MOSS 的替换。

这项推荐沿用本项目英文、低延迟、持续供音的目标，把原生音频帧流与资源占用纳入工程取舍。它不等于 Pocket 的听感胜过 Kokoro：Kokoro 的人工均分更高，首可听 p95 也更低；Pocket 的优势是本轮 CPU 条件下较低的首可听中位延迟，以及每 80ms 原生输出音频块。

## 评价来源与统计方法

用户完成了 [综合评分 JSON](../reports/tts_selection/20261018/listening_scores.json)：6 条固定英文文本，每条对匿名 A/B/C/D 各给一个 1–5 的综合分数，共 24 个有效评分，没有缺失。每段只使用用户填写的这个分数，没有重新拆分自然度、清晰度或自动生成替代评价。

按 [匿名映射](../reports/tts_selection/20261018/model_key.json) 解盲：**A=MOSS，B=Kokoro，C=Pocket，D=Kyutai**。已逐项核对文本、标签与 24 段音频哈希。原始 JSON 按字节归档，SHA256 为 `6dfc7d11178b70d59462144cb3d9b70c60902bc2c8bed58dfa0128fca1963b97`；[统计 JSON](../reports/tts_selection/20261018/listening_score_summary.json) 保留完整精度、类别均值和来源哈希。

人工综合分采用六条等权算术平均；三种场景各两条，因而不存在类别样本数不均衡。延迟、实时因子和主观分数分别展示，不把毫秒、算力与 1–5 分主观评分混成一个缺乏依据的加权总分。

## 与远端性能证据合并判断

以下为每系统 60 条正式请求的实测；不是仅对六条试听样本测延迟。首包与首可听代理单位为 ms，均列 p50 / p95。RTF 为生成墙钟/音频时长，越小越好。

| 系统与计算设备 | 人工均分 | 首音频包 | 首可听代理 | RTF p50 | 60 条累计模拟断流 |
| --- | --- | --- | --- | --- | --- |
| Pocket，Xeon Gold 6330 / 2 CPU 线程 | 4.37 | 156 / 226 | **352 / 535** | 0.452 | 0.594s |
| Kokoro，RTX 4090 | **4.48** | **122 / 138** | 439 / **461** | **0.026** | 0s |
| Kyutai 1.6B，RTX 4090 | 3.90 | 737 / 759 | 812 / 1128 | 0.426 | 0s |
| 现役 MOSS 配置，RTX 4090 | 4.07 | 561 / 62880 | 1809 / 63405 | 1.611 | 172.320s |

**Pocket：推荐英文实时主线。** 本轮综合分达到 4.37，CPU 上总体供音快于实时；首可听中位数比 Kokoro 约早 87ms。每包中位时长 80ms，适合持续交付音频并由原有播放队列提交。代价是人工均分低约 0.12，首可听 p95 比 Kokoro 慢约 75ms，还有少量模拟断流。因此推荐基于实时输出方式与资源安排，并不声称 Pocket 全面优于 Kokoro。

**Kokoro：听感和完整文本吞吐优先的选择。** 人工评分最高，GPU 上 RTF 约 0.026，首可听尾部延迟也很好。如果只需已经形成的短句尽快发声，Kokoro 有充分实测优势。不过原生 `KPipeline` 先完成文本段合成，首块音频时长中位 4.45 秒；本轮不是帧级增量声学生成。选择它作为实时主线需要接受分段等待，并另测断句和跨段韵律。当前不因此新增独立的并行播放通道。

**Kyutai：不选作本轮默认。** 本轮听感均分和首可听延迟均落后于 Pocket；虽然无模拟断流，未体现足够收益来覆盖这两项差距。官方增量文本接口可作为未来严格双向流式需求的研究对照；本轮没有验证该能力的端到端优势。

**MOSS：不推荐维持当前配置作为英文低延迟主线。** 人工均分第三，长尾编译等待与供音不足实时同时存在；一条正式请求只返回 80ms 音频，未检测到持续非静音，首可听统计仅 59/60。包装作业在 60 条测量写出后退出 127，原始异常保留；不把该作业记为验收通过。上述结论针对本次配置，不能推广成 MOSS 模型家族的性能上限。

## 结论适用边界与下一步

1. 人工评分针对本轮具体音色和六条文本，只有一名评价者。不同音色、说话人和文本分布可能改变偏好；未测 CosyVoice3、Magpie、Qwen3-TTS、VibeVoice 的方案不纳入最终排名。
2. 试听使用合并后的原始 WAV，保留开头静音，但不复现网络到达造成的供音断流。人工综合分衡量这些试听文件的整体听感，断流另外由时间线评价。
3. 首可听代理是按实际分块到达模拟播放、以持续非静音检测得到的值，未测扬声器或第一个可理解单词。测试统一在完整文本可用后提交；没有包含 ASR、LLM、真实用户网络和设备缓冲。
4. Pocket 的已测 Python 接口接收完整字符串。本轮的推荐不证明它能直接接收持续到来的 LLM token，也不证明取消后能立刻释放生成资源。帧级音频输出、增量文本输入和打断取消必须分别验收。
5. 下一步若执行接入，使用 X-Talk 原有 TTS 扩展点，保持唯一 TTS 播放所有权；先验收短句/文本段交付、预热、持续供音、取消与有效插话后的停播、旧响应音频隔离、顺序会话和 FDB 回归。已播放内容不可撤销，Layer 边界与仲裁规则不变。本次工作止于最终选型报告，没有修改产品运行时。

性能口径、预热与执行异常的完整记录见 [实测说明](tts_selection_results.md) 和 [原始分组报告](../reports/tts_selection/20261018/report.md)。
