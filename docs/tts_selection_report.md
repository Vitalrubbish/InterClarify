# InterClarify 英文实时 TTS 技术选型报告

编制日期：2026-10-20。主要依据为 2026-10-18 四系统性能测量及匿名人工试听，补充 2026-10-19 Kokoro 接入、分段连续性修复与复听记录。本文整理已有证据，不启动新测试，不变更组件或研究范围。

## 1. 选型结论

当前英文主线采用 **Kokoro 82M / af_heart**，与 Nemotron EN160 配合。Kokoro 在本轮单人匿名试听中综合均分最高，为 **4.48/5**；RTX 4090 上完整文本提交条件下，首音频包 P50/P95 为 **122/138ms**，首可听代理为 **439/461ms**，实时因子（RTF）中位数为 **0.026**，60 条请求累计模拟断流为零。

其取舍是以快速的文本段合成获得低延迟发声，并在客户端处理真实 LLM 增量的分段等待和跨段韵律。Kokoro 本轮原生输出不是帧级声学生成，完整文本条件下的 439ms 不能直接作为 ASR→LLM→TTS 的端到端延迟。

用户于 2026-10-18 确定 Kokoro 路线，取代此前偏重 CPU 与原生音频帧输出的 Pocket 推荐。2026-10-19 的接入和连续性修复已完成，最新版音频经用户复听通过；全链路双工能力和正式 FDB 验收仍由独立任务推进。本文保留原始测量和失败，不以组件接入通过代替系统验收。

## 2. 选型要求

| 要求 | 项目需要与评价方式 |
| --- | --- |
| 英文听感 | 覆盖短澄清、日程确认、长回答；同文本匿名试听，记录评价者、音色与样本量，避免将单人偏好写成普遍结论。 |
| 尽快开始发声 | 分别记录首 PCM、持续非静音代理和实际播放；完整文本与真实增量输入分别测量。 |
| 持续供音 | 记录 RTF、分块到达和模拟断流，不能仅以首包快判断长回答是否顺畅。 |
| 适应 LLM 增量 | 明确文本提交条件、首段等待、长度上限、句界及 finish 刷新；检查碎词、句中切分与跨段韵律。 |
| 正确表达任务内容 | 检查日期、时间、确认和澄清的读法；文本读全与传输完成分别验收，不用非空音频替代语义正确性。 |
| 打断与隔离 | 沿用 X-Talk 唯一播放所有权；取消后隔离旧响应音频，区分停止播放和底层计算释放。已播放内容不可撤销。 |
| 可部署与复核 | 远端独立 conda 环境，记录模型、音色、设备、预热和退出状态；控制测试资源与并发。 |

原测量没有定义统一的延迟硬门槛或主观分数合格线，本文按同文本证据及实际接入需求做取舍，不补写事后门槛。候选的计算设备和输出方式不同，不能解释为同算力模型排名。

### 3.2 性能测试与人工试听

四系统各提交相同的 **60 条完整英文文本**：短澄清、日程确认、长回答各 20 条，共 240 条正式请求。每系统另外执行首次请求和三条预热，不纳入正式分位数。客户端与服务位于计算节点，包含本机回环 HTTP／原生 WebSocket 交付，未包含 ASR、LLM、用户公网、浏览器缓冲或声卡。GPU 为同型号独占卡；Pocket 虽由 GPU 队列容器承载，推理实际只用 CPU。

人工试听从三类各取两条，共 **六条同文本 × 四系统＝24 段音频**，一名评价者对匿名 A/B/C/D 各给一个 1–5 综合分，可填小数。合并后的 WAV 保留原始音量与开头静音，但不能复现网络包迟到造成的断流。不同系统使用不同音色，没有统一克隆说话人。

本次未实测 CosyVoice3、Magpie、Qwen3-TTS、VibeVoice 或云 API，因此不纳入排名。性能口径依据[历史实测说明](https://github.com/Vitalrubbish/InterClarify/blob/3be4fc44d42d1163a7882eed116423e1f86b56a1/docs/tts_selection_results.md)，数据依据[原始分组报告](https://github.com/Vitalrubbish/InterClarify/blob/3be4fc44d42d1163a7882eed116423e1f86b56a1/reports/tts_selection/20261018/report.md)。历史说明中的 Pocket 推荐代表当时判断，当前路线以本文为准。

## 4. 延迟、供音速度与稳定性

### 4.1 指标定义

- **首音频包延迟**：请求提交至第一个非空、可解码 PCM 块；容器头或控制消息不算音频。
- **首可听代理延迟**：以 10ms RMS 窗口检测连续 30ms 高于 −45dBFS 的非静音，映射到保留包到达等待的顺序播放时钟。计入开头静音和迟到等待，不等于扬声器实测或第一个可理解词。
- **RTF**：生成墙钟时间除以输出音频时长，越小越好；RTF＜1 表示该请求总体生成快于实时，不保证包间永不缺音。
- **累计模拟断流**：首包即可播放、不额外预缓冲时，因音频供给跟不上播放而等待的时长总和。产品缓冲会改变首音与断流的取舍。
- **传输完成**：结束协议正常且音频非空，不代表文本读全、持续非静音或听感合格。

### 4.4 预热与执行异常

首次请求首包约为 Kokoro 2.220 秒、Pocket 0.184 秒、Kyutai 15.683 秒、MOSS 70.720 秒。各服务就绪口径不同：MOSS 健康检查早于惰性加载，其首次请求包含加载成本，其他服务在启动时先加载模型，因此这组数值不能直接横向排名。

MOSS 三条短句预热没有覆盖全部动态形状，正式请求仍出现约一分钟的编译等待，已保留在 P95 中；不能将其解释成所有形状充分预热后的稳态指标。60 条测量写出后包装脚本退出 127，核验确认测量完整、无传输错误，故保留数据并披露异常，整个作业不计通过。Kyutai 类似的旧包装失败轮已排除，采用冻结入口重跑且退出 0 的 `kyutai-r2`。MOSS 缺 flash-attn、Pocket 线程 tensor 不兼容等启动失败没有正式样本，不混入主表。完整执行来源见[运行登记](https://github.com/Vitalrubbish/InterClarify/blob/3be4fc44d42d1163a7882eed116423e1f86b56a1/reports/tts_selection/20261018/run_registry.json)。

## 6. 流式输出方式与后续接入证据

### 6.1 三种“流式”需要区分

完整文本提交后分块返回音频、原生帧级生成音频、持续接收 LLM 新文本，是不同能力。2026-10-18 测试统一在完整文本可用后提交，没有验证真实 LLM 增量输入下的端到端优势。

Kokoro 首块音频时长中位数为 **4.45 秒**，P95 为 11.261 秒，说明本轮先合成文本段再交付；其他三系统首块时长中位数为 **80ms**。这是包中包含的音频时长，不能与首包等待时间混淆。Pocket 本轮 Python 接口接收完整字符串；Kyutai 的双向增量接口价值仍需专门实验，不能从本轮完整文本测试推定其接入优势。

### 6.2 Kokoro 分段接入与复听

2026-10-21：[Issue 047](issue/047_tts_first_segment_latency.md)已实现首段300ms与独立后续段1200ms的候选配置，当前按[Issue 049](issue/049_latency_decomposition_validation.md)远端对照验证；旧600ms方案作为基线保留。该候选的性能及听感结论待实测，不沿用旧r3复听作为通过依据。

后续沿 X-Talk 原有接口聚合真实文本增量，由唯一播放管理路径提交 PCM，取消后隔离旧代际音频。2026-10-19 已验收分段策略为 12/160 字符，首段等待 600ms、后续段最多 1,200ms 等待句界；句界、finish 或长度上限可提前提交。到期交付完整词，残词继续等待，因而无词边界时不承诺 600ms 内提交。TTS 合成副本对明确时间语境中的合法 HH:MM 转成英文读法，不修改模型正文或历史。

2026-10-19 r3 的三条例子中，首可听代理分别为长回答 **0.425 秒**、时间澄清 **0.592 秒**、短确认 **0.893 秒**。它们属于不同输入时序与分段策略下的集成诊断，不能并入 60 条横向基准。长回答从六段改为四个完整句子，三处段边界低能量间隔约 0.26/0.20/0.21 秒；用户复听确认最新版效果很好，相关组件任务已归档。

正常三例及 12 字符/600ms 供给诊断没有队列断流；3 字符/600ms 的慢供给仍有约 3.887 秒队列缺口。客户端取消代际与原生播放链路检查通过，但不能据此声称 GPU 计算可立即停止。上述测试和复听通过不代表整条 ASR→LLM→TTS 双工链路或声卡测量通过。来源：[r3 连续性与复听报告](../reports/tts_continuity/20261019-r3/README.md)、[客户端分段说明](scripts/remote/verify_english_components.md)、[组件任务](issue/archive/003_kokoro_playback_integration.md)。

## 7. 最终取舍与适用边界

| 系统 | 最终处理 | 主要理由与代价 |
| --- | --- | --- |
| Kokoro 82M／af_heart | 当前英文主线 | 本轮听感均分最高、首可听 P95 较低、吞吐充足；需要文本段聚合及跨段韵律处理，后续组件接入与复听已通过。 |
| Pocket TTS／Alba | 保留历史比较，不作为当前接入目标 | CPU 首可听中位数最低、原生音频帧输出；本轮均分略低、P95 略高、有少量模拟断流，未验证真实增量文本接入。 |
| Kyutai TTS 1.6B | 当前不采用 | 本轮听感及首可听延迟未形成综合优势；双向增量接口未在本轮证明端到端收益。 |
| 当时现役 MOSS 配置 | 不维持为当前英文低延迟主线 | 长尾编译等待与总体供音慢于实时同时存在；一条无持续非静音、包装作业失败，结论限于该配置。 |

选型以既有用户决定及测量证据为依据，当前不重开候选比较。后续关注真实 LLM 输出下的首段等待、长回答连续性、数字读法、有效插话停播及过期音频隔离；由 [全链路验收任务](issue/archive/008_full_chain_fdb_acceptance.md)评价实际对话质量和延迟。TTS 已完成组件接入不代表控制模型会在适当时刻回复。
