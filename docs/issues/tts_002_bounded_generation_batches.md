# TTS-002：降低 TTS 生成批次帧数并保持连续供音

状态：4 帧组件筛选完成；规模、试听与集成验收待补。日期：2026-10-17。分支：`feature/tts-latency-optimization`。

## 问题

当前一次文本推送可能生成全部待处理帧后才解码和交付，批次大小缺少上限。保留批量策略，适当降低每批帧数，兼顾首音和语音连贯性。

## 依赖

按顺序在 [TTS-001](tts_001_latency_instrumentation.md) 完成后执行；单项无收益时记录结论并沿用原配置。

## 共同约束

遵循 [TTS-001 的范围与实验协议](tts_001_latency_instrumentation.md)：固定模型与输入链路，保留单一播放所有权，使用远端 conda 环境进行 GPU 测试；每项单变量对照，同时验证首音、断流和自然度。

## 处理方案与验收

### 设计

区分三个参数，避免将其中一个的效果误归给另一个：

- **生成批次上限**：同一次模型推进最多生成多少音频帧，随后允许解码、入队和取消检查。这是本步主要变量。
- **codec 解码块**：现有首块 1 帧、后续逐步增至 6 帧。第一轮保持现状，不能把它当成“首包要等六帧”。
- **播放启动缓冲**：播放器已有的供音缓冲，第一轮保持现状并观测欠载，不另建播放队列。

在不改变原文本 token 序列的前提下，让 start、push、finish 的内部生成路径支持有界批次。超出本批上限的文本保留在原会话待处理状态，由同一 worker 按顺序继续推进，不等待新文本 push 才处理已有余量，也不提前结束文本。

保持跨批模型 KV、重复惩罚历史和每轮唯一 codec streaming 上下文；批次边界不执行模型重置、codec 重置或人为插入静音。实际解码和发送可聚合已生成帧，不要求每帧独立网络发送。EOS、取消和真实结束时处理不足一批的尾部，取消时丢弃尚未提交的旧响应数据。

### 对照配置

先比较原路径与生成上限 4 帧，再根据结果比较 2、6 帧；这些都是候选值，不预先写成产品默认值。12.5Hz 下，2/4/6 帧分别代表约 160/320/480ms 音频，不代表其生成墙钟时长，也不保证解码器每次返回相同长度 PCM。

如果生成批次优化被 codec 聚合抵消，再单独对比 codec 后续块上限 4 与现有 6；若播放欠载，再单独评估现有播放器的启动缓冲。两项都不能和生成上限同时改变。新增定时刷新只在观察到不足批次长期滞留后规划，优先使用原 worker 的结束和余量推进逻辑。

### 完成条件

固定输入与采样条件下，生成 token/音频帧顺序与原路径一致；PCM 比较允许因解码块不同出现数值差异，但不得有漏词、重复、截断或明显接缝。首音改善须在重复测量中稳定可见，供音欠载和自然度不退化。若最小批次欠载，选择稍大的批次；若候选均无收益，保留原配置并记录瓶颈，不为了更小帧数强行合入。

## 2026-10-17 实现进展

显式服务包装器以惰性帧迭代器保持原 token 顺序，每批至多 2/4/6 帧并自动推进余量；start/push/end_text 复用原调用链，finish 保持原单帧 drain，codec 状态不重置。已测余量、短文本、EOS 和取消。尚未选择产品批次值，待首音、连续供音、真实取消和试听验收。

实现与检查记录见 [远端任务单](../tts_latency_remote_tasks.md)。默认关闭路径的本地准备不替代依赖 issue 的实验门禁；远端仍按 001 → 002 → 003 → 004 执行。

## 本轮结果归档

batch4 的 18 个配对全部 PCM 相同，token 顺序与消费完整。整句组首包平均提前 0.548 秒，中位数只提前 0.011 秒，收益集中于长句；尚未比较 2/6 帧，也未改产品默认批次。

完整配置、失败与复测、阶段指标和下一步见 [TTS 优化报告](../tts_latency_optimization_report.md)。本轮所有 GPU 作业已结束；以上组件结果不等于完整产品验收。
