# TTS-004：依据实测优化 TTS 剩余瓶颈

状态：阶段分解与优化报告已完成；额外模型/codec/KV 优化未实施。日期：2026-10-17。分支：`feature/tts-latency-optimization`。

## 问题

完成批次和开头编译优化后，剩余延迟的主要来源可能改变，需要依据新的阶段分解选择后续优化，避免同时调整多个变量。

## 依赖

按顺序在 [TTS-003](tts_003_early_frame_compilation.md) 完成后执行；单项无收益时记录结论并沿用原配置。

## 共同约束

遵循 [TTS-001 的范围与实验协议](tts_001_latency_instrumentation.md)：固定模型与输入链路，保留单一播放所有权，使用远端 conda 环境进行 GPU 测试；每项单变量对照，同时验证首音、断流和自然度。

## 处理方案与验收

完成前两项优化后重新分解延迟，只实施仍占主要等待且有明确实验依据的路径。以下为条件分支，不要求全部实施。

| 主要瓶颈 | 计划动作 | 质量和正确性约束 |
| --- | --- | --- |
| 等待文本门槛 | 先修正真实文本结束交付；门槛调整作为后续单变量实验 | 不伪造结束、不丢文本；降低模型 delay 门槛需独立验证漏词、韵律与接续，不默认作为无损修复 |
| 固定提示 prefill | 测提示长度、缓存命中和预处理；验证完全相同固定前缀的 KV 复用可行性 | 缓存键包含模型、音色、提示及位置语义；隔离可变 KV，避免跨会话污染 |
| codec 解码/拷贝 | 测首块与后续块开销；减少重复转换和拷贝，必要时编译 codec | 保留每轮连续 codec 状态；小块/大块各自验收接缝、延迟与欠载 |
| backbone decode | 优先尝试单 token step 编译，再依据失败原因研究静态 cache 或图捕获 | 单独测 prefill 与 decode，检查 KV 长度、取消、长会话显存和重编译 |
| 排队或播放缓冲 | 复核 worker 积压及现有播放器供音策略 | 保持唯一播放所有者，不绕过取消与提交边界 |

每个分支先形成微基准，再回到同一文本流测试。只有在首音或连续供音改善且无质量退化时保留；量化、多模型并发、替换推理引擎与更换 TTS 不纳入本计划。

## 2026-10-17 实现进展

基准新增同进程首次入队至首 PCM 的 CPU span 分割，重叠与未归因等待单列，缺失事件显式报告。不把 nested span 相加或跨进程相减。尚无新阶段占比，故未选择或实施 KV、codec、backbone 优化；不预判瓶颈和收益。

实现与检查记录见 [远端任务单](../tts_latency_remote_tasks.md)。默认关闭路径的本地准备不替代依赖 issue 的实验门禁；远端仍按 001 → 002 → 003 → 004 执行。

## 本轮结果归档

报告按同进程阶段分解，并保留文本等待、编译长尾与首 PCM/有声起点差别。本轮没有证据支持直接切换额外 backbone/codec/KV 路径，未增加该类实现；可听首音预算仍未达到，后续首先扩大候选验证和组合实验。

完整配置、失败与复测、阶段指标和下一步见 [TTS 优化报告](../tts_latency_optimization_report.md)。本轮所有 GPU 作业已结束；以上组件结果不等于完整产品验收。
