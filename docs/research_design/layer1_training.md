# 合并表达层的训练数据与成本研究

更新：2026-11-03。对应 NTF-037。用户已确认将 Layer 0 系统附和能力并入 Layer 1；本文给出数据与预算建议，不表示协议已冻结、语料已生成或训练已启动。正式回答仍须在 Layer 1 合法输入边界实际读到当前话轮已联合提交的有效 `user_complete`，不恢复额外交接等待。本文只研究基础交互能力，不把它等同于两项 thinking 流研究已经完成。

## 1. 训练对象与比较口径

首阶段建议冻结 SoulX、X2、TTS 和 Layer 2，只训练合并后的 Layer 1：读取外部用户状态，决定等待、系统附和或正式表达，并在取消后使用新输入恢复。系统附和包括时机与措辞，不新增独立 Layer 0 模型。Layer 1 不重新预测或覆写 SoulX 五状态，`user_backchannel` 也不表示系统应当附和。

两种“输出状态 token”必须分开：

| 方案 | 模型学习的内容 | 与现阶段路线的关系 |
| --- | --- | --- |
| A：外部用户状态＋Layer 1 表达决策 | SoulX 判断用户状态；Layer 1 根据 Context 决定自己的表达行为 | 建议先实施的训练对象 |
| B1：外部用户状态＋LLM 输出自身动作 | Layer 1 输出表示等待、系统附和、正式表达的内部动作，再生成正文 | A 的一种协议实现，不等于替代控制器 |
| B2：LLM 自行预测用户状态 | 去掉 SoulX，由表达 LLM 根据连续观察预测用户状态并生成表达 | 另立架构对照；音频输入能力和调度需要另行设计 |

以下成本以当前 Qwen2-7B/DuplexCascade 为表达底座示例，不默认替换基座。外部控制器是已有 Qwen3-0.6B SoulX，不能将其历史预训练成本算作 A 的新增训练成本，却将 B2 的预训练算作免费。

## 2. 历史现象如何转成训练问题

[NTF-019 报告](../reports/soulx/20261103-ntf019-fdb30/README.md)明确指出，早于 FDB 整段边界的 complete 不直接等于实际抢话。48 次 complete 快照中有 38 次之后继续追加正文；这是固定诊断集的前端现象，不能用来估计部署概率，更不能将 FDB 内容用作训练材料。

旧半双工实验的保留计数见 Git 提交 `e80c05b`：672 条、2036 次回复启动、1368 次取消。取消原因混合且缺少完整逐请求播放记录，因此 67.2% 不能解释为 complete 误判率或首音前取消率。被选取保留的逐事件案例确有 `soulx_nonidle` 取消且 `played_samples=0`；这些只能确认机制存在，不能外推占比。不恢复已经按用户指令清理的旧产物。

必须区分三个时间点：complete 实际被 Layer 1 读取、后续有效 nonidle 被输出运行时消费、第一份音频实际播出。首音前取消可以阻止用户听见旧回复，但模型可能已生成文本，也已消耗计算。TTS 加速可能使同样的控制轨迹出现可听抢话，因此不能通过增加合成延迟获得“正确等待”。

训练核心是对真实、含噪的控制轨迹作因果响应，并正确恢复，不是监督模型预知以后会被取消。运行时负责撤销输出资格、停止和丢弃迟到结果；这些动作不能靠 SFT 替代。

## 3. 数据单位与可见信息

底层保存事件轨迹，在 Layer 1 实际允许读入新观察的边界采样训练决策。160ms 是前端发布步长，不自动等于 LLM 调用或训练样本步长。长段无变化等待可稀疏抽样，complete、续说、附和机会、取消和恢复附近提高密度；自然频率的开发／测试集不作这种重采样。

| 记录 | 内容与可见边界 |
| --- | --- |
| 来源与分组 | 原始对话、说话人、任务模板、派生关系、语言和数据来源 |
| 当前输入 | 已联合提交的在线 X2 正文、SoulX 状态及有效性、批次／观察截止、用户片段身份 |
| LLM 读取 | 本次实际读取的快照和边界；已经构造的输入不能事后加入新状态 |
| 交互历史 | 真实生成历史、输出是否活动、preparing／playing、取消／关闭确认和事件级已播信息 |
| 表达输出 | 等待、系统附和、正式表达及其正文；`output_id`、片段身份与实际提交记录 |
| 回放执行 | 合成开始／返回、首个实际已播采样、取消原因、实际停播、旧结果是否丢弃 |
| 标注与诊断 | 人工机会窗口、完整未来音频、最终参考转写、误判诊断；不作为在线模型输入 |

精确已播采样属于运行与评分账本；首版 Layer 1 仅需事件级取消和已播状态，不要求逐字播放对齐。离线训练轨迹的事件账本不意味着给在线 SharedContext 新增无限历史队列。短暂 complete 的可靠消费、去重和过期识别仍是下游接口待实现事项，不能只靠训练消除遗漏。

首阶段模型只使用转写、外部状态和交互事件，数据教师也采用同样可见信息。若附和需要语调、重音等信息，应单独研究声学特征接入，并单列数据、推理和训练成本；不得让教师依据音频作出学生从文本无法区分的确定标签。

## 4. 提前 complete 的监督原则

示例：用户说“帮我订周五的车票”，控制器提交 complete；Layer 1 开始组织回答；用户随后说“不对，是周六”，提交 nonidle，运行时关闭旧输出；之后新 complete 到达，Layer 1 根据周六恢复。各条消息何时可见与实际播放分别记账。

| 情况 | 建议监督 |
| --- | --- |
| 新 nonidle 在 Layer 1 本次读入前已经提交 | 使用最新合法快照，不能重放过期 complete 来训练新回答 |
| 已读到 complete，尚无续说证据 | 可以依据当时前缀生成合法回复；不能因为未来续说，反向标成模型本应知道要等待 |
| 当前前缀已有明确续说或未完成信号 | 由前缀审核等待是否合理；不新增独立语义否决模型，也不修改原始状态标签 |
| 已生成、首音前取消 | 保留真实生成历史与“未播即取消”事件；将续说并回同一用户片段，后续根据合并输入响应，不写成助手已说过 |
| 已播出部分后取消 | 保留实际已播事实，按现有合同处理后续新用户片段；恢复表达使用新条件，必要时明确纠正已说错误 |
| 取消后的旧文本／TTS 迟到 | 运行时禁止其再次播放；模型在后续合法边界学习结束旧表达方向，不自动续播旧回答 |
| 新有效 complete 到达 | 学习恢复并正常回应，避免训练成看见任何 complete 都等待 |

同一可见前缀应覆盖“用户确实结束”和“稍后继续”两个分支；在二者尚无可见差异时，不得赋予相互矛盾的确定动作标签。后续已播与取消标签可以不同，但只能在对应事实到达后作为模型条件。

被取消文本不是天然负例：语义合理且在当时合法生成的前缀可以保留正监督；仅作恢复条件的模型错误历史可保留在输入并屏蔽损失。取消后尚未发生的续写不补造为目标，也不在取消点伪造模型主动输出 EOS。先整理因果监督，再考虑是否需要偏好优化，首版不依赖 RL。

## 5. 系统附和的标注

从保留双说话人时间和重叠信息的自然对话中寻找听者短回应，再人工判断它属于附和、正式接话、澄清还是打断。历史存在附和是候选正例，历史没有附和并不能直接证明当时不适合附和。

标注建议采用事件窗口，区分“适合但可不发”“不应发”“不确定”，并标明承担的交流功能。不要给同一机会的所有相邻窗口反复标正，也不要将窗口内每个时刻都要求发声；一个机会内成功表达后，后续输入应看到已经附和的历史。强负例覆盖：刚附和过、用户即将交接、已有正式输出、否定或风险内容中附和会被理解为赞同，以及明显没有听者回应必要的连续语段。

在可靠窗口内选择可执行的训练边界，生成简短、符合上下文的附和正文；相邻位置提供等待负例。模糊机会采用允许动作集合、软标签或不进入硬监督集，不能为了确定性强迫教师猜出唯一“最佳毫秒”。

另需冻结运行合同：系统附和允许用户继续说话，不能将持续的 `user_nonidle` 机械当作附和后的新打断。需要说明附和输出生命周期中何种新观察构成有效取消，并保留真正打断的停止路径；这是接入前的协议问题，不是标注能修好的问题。本文不自动更改现有取消合同，也不新增语义否决模型。

## 6. 构造流程与质检

1. 先按原始对话、说话人／来源和任务模板分组划分训练、开发、测试，所有裁剪、改写和同前缀分支跟随母组。FDB、SoulX-Eval 及其改写都不进入训练或选阈值。
2. 训练源混合自然对话与任务型合成对话。可考察 [SwDA 标注](https://github.com/cgpotts/swda)中的听者行为及 [DuplexGen](https://huggingface.co/datasets/DuplexGen/duplexgen-corpus)的结构化对话作为候选；SwDA 话语级标签不等于已具备音频逐词时标，需要取得匹配音频并另外对齐。二者均须在实施前核对具体文件、对齐与来源条件。不采用删除附和和口语不流利片段的清洗版本，也不直接把它们的协议当成本项目协议。
3. 用冻结的当前前端重放训练源音频，采集真实在线 X2 文本、SoulX 状态和联合可见顺序。参考转写只用于核验。优先使用真实控制轨迹，另外加入有依据的短暂 complete、重复状态、ASR 滞后等扰动；不能只给模型无噪声金标控制。
4. 教师只读取当前可见前缀，生成动作与表达目标；标注者可看未来用于诊断，但必须复核当时标签是否可知。系统附和机会与控制器状态标注分别完成，不把用户附和当作系统附和目标。
5. 通过有界运行时或明确标记的模拟执行器形成取消恢复轨迹。合成／播放延迟从试采分布取值，加入更快首音条件；实际模型生成和流式 TTS 只对代表性子集闭环，不为所有训练片段合成音频。
6. 先 SFT，再在训练分区做一轮模型实际回放，采集模型自己的错误与取消历史，针对性补标。不能只在人工完美历史上训练；开发／测试错误不回流训练。
7. 机械检查可见顺序、输出身份、重复 complete、片段分组和正文边界；分层人工复核附和正负例、取消前后、教师通过及拒绝的样本，记录分歧与接受率。

首轮可按训练采样窗口采用等待 45%、系统附和 15%、普通回答 25%、取消恢复 15% 的场景配比起步；这是采样建议，取消恢复窗口也可能输出等待或回答，不是四个互斥的模型动作。自然分布开发集用于检查过度附和和过度等待。真实／合成比例及扰动概率须由试采决定，不照搬固定诊断集的提前 complete 比例。

## 7. 训练协议与目标

等待必须有可监督的内部表示，例如一个已支持的窗口结束／等待符号；附和与回答也需要可解析的用途边界。这里的 WAIT、BACKCHANNEL、ANSWER 仅表示逻辑动作，不宣称 tokenizer 已存在这些 special token。优先复用确实具有对应语义的既有协议，不复用用户状态 token 表示助手行为。

输入中的用户正文、外部状态、运行事件与后续 CoT 屏蔽目标损失；监督模型自己的动作、边界和允许表达的正文。动作／边界损失与正文损失分别统计，避免长回答掩盖等待和附和学习；权重在开发集选择，不直接复制其他模型数值。损失屏蔽不免除输入 token 的前向计算。

当前 [layer1_model.py](../../scripts/runtime/layer1_model.py) 训练入口仅开放已有 q/v LoRA，冻结 embedding 与 lm_head，并严格恢复已登记权重。SoulX 和 Layer 1 使用不同 tokenizer，不能复制 token ID 假定共享词表。若新增 token，需先设计词表映射、必要的新行训练和重载检查；当前加载器并未实现这条路径。量化训练、扩大 LoRA 范围等同样属于后续实现，不能当作现成能力。

建议先训练基础状态消费、正常回答与取消恢复，再混合加入系统附和；同时保留普通任务回答，防止模型为了降低冲突而永远等待或只发短附和。Layer 2 请求与 CoT 利用留到下一训练阶段，分别计数和消融。

## 8. 建议数据规模

以下是试验规模建议，不是达到某项准确率的保证。对话／任务片段是独立来源单位，决策窗口是相关样本；重复前缀、分支、多个延迟版本不重复计独立场景。

| 阶段 | 独立训练对话／任务片段 | 采样决策窗口 | 单 epoch 实际处理 token 目标 | 目的 |
| --- | ---: | ---: | ---: | --- |
| 试标与小训练 | 300—500 | 5千—1万 | 2M—5M | 验证可见性、等待协议、附和标注与恢复 |
| 第一版基础能力 | 5千—1万 | 10万—20万 | 30M—80M | 建立可复现的附和／回答／取消恢复能力 |
| 扩展 | 2万—5万 | 30万—100万 | 150M—500M | 根据学习曲线扩大语言、任务与扰动覆盖 |

主版另留开发和测试各至少 500 个来源分组，覆盖足够的独立附和机会和取消事件；实际数量随试标事件密度决定。训练池可先规划 50—200 小时音频，最终以事件覆盖和来源多样性验收；这不代表源语音时长能直接换算成模型训练 token。

30M—80M 假设同一对话按连续因果序列组织、多个决策共享前缀后，平均每个决策摊销约 300—400 token。例如 10 万 × 300＝30M，20 万 × 400＝80M；若实际每个视图重放 2K 历史，则分别是约 200M／400M，不能继续沿用小预算。普通独立样本 packing 只减少 padding，不自动消除重复前缀，也不表示可跨参数更新复用旧训练 KV。打包须隔离不同会话注意力，长会话不能静默截断。另记监督目标 token、重复前缀和 padding 的计算量。

主版争取至少 5千—1万个人审附和机会及 1万—2万个取消恢复窗口；后者可含模拟扰动和同源分支，须单列真实来源数，不能宣称都是自然误判。可选附和机会的“不发”不自动计遗漏。

## 9. 成本模型与资源边界

### 9.1 模型训练

以 7B 参数级表达模型的 LoRA 为起点。BF16 权重理论存储为每参数 2 字节，7B 约 14GB；当前加载器还保留 embedding／head 副本，不能将这个理论下界当作实测占用。LoRA 减少可训练参数与优化器状态，但仍须经过冻结主干作前向与相应反传。新增 token 的新行训练另计。

24GB 4090 上先在远端试测短序列、micro-batch=1 和梯度检查点；不保证现有 BF16 加载器在 22GiB 停止线内可训练。若不足，再单独实现并验证 QLoRA 或修改部署条件。QLoRA 使用冻结 4bit 权重和 LoRA 降低存储需求，见[原论文](https://arxiv.org/abs/2305.14314)；量化可能增加反量化开销，不能直接承诺更快。

训练时间按以下方式复算：GPU 小时＝单 epoch 实际计算 token × epoch 数 ÷ 实测每 GPU token/s ÷ 3600。吞吐须包含真实长度、padding、损失 mask、梯度检查点、累积、优化器步和数据读取。多卡报告总 GPU 小时，不能只报告墙钟。

下表 q 均为纯假设敏感性参数，不是本项目或 4090 的已测吞吐。以主版低端 30M、2 epoch 为例：

| 假设有效吞吐 q | 核心训练 GPU 小时 | 加 30% 评估、保存与启动预留 |
| --- | ---: | ---: |
| 300 token/s | 55.6 | 72.2 |
| 600 token/s | 27.8 | 36.1 |
| 1000 token/s | 16.7 | 21.7 |

试标 3M、1 epoch，在同样假设下含预留约 1.1—3.6 GPU 小时。80M、2 epoch 是 30M 示例的 2.67 倍；若实际吞吐为 150 token/s，30M 示例也需约 144.4 GPU 小时含预留。不能将一个适配器训练预算冒充完整研究成本。

先做未训练基线和试标训练；主版再比较“无取消轨迹”“无系统附和训练”“完整混合”三种配置，主配置复核至少两个随机种子。按上述 30M 示例估算，4 次同规模训练约 87—289 GPU 小时，另加试标、数据准备和闭环回放；消融实际 token 不同则分别计账。

### 9.2 数据准备与闭环

| 项目 | 估算方式与边界 |
| --- | --- |
| 在线前端轨迹 | GPU 小时＝音频小时 H × 离线处理 RTF。若 H=100、RTF 假设为 0.5—1，则约 50—100 GPU 小时；必须先试测，不能从单步 P50 推算保证 |
| 教师生成 | 若 10 万视图各输入 1000、输出 50 token，即约 100M 输入和 5M 输出 token；按实际教师本地吞吐或接口单价另算，不假定免费 |
| 人工复核 | 3000—5000 个窗口，每个 30—60 秒约 25—83 人时；双标、听长上下文和裁决另计 |
| 闭环回放 | 不对所有样本作真实 TTS；例如 500 条 × 30 秒＝4.17 小时输入，一次实时回放每张占用 GPU 都需分别计时 |
| 音频存储 | 16kHz、mono PCM16 每小时 115.2MB，100 小时约 11.52GB；float32 翻倍，优先复用既有文件与引用，不复制整池 |
| 训练文件 | 输入 token、标签 mask、事件表与少量回放产物分别限额；保留有界检查点，不保存每步 logits 或全量重复快照 |

大规模前端重放若被刻意限制为实时送音，其墙钟接近 H；离线快速重放与真实时延评测须分开。闭环内若 LLM、前端、TTS 不能同卡共存，应串行采集或单列多卡部署，不能把三种模型显存简单塞进一张 4090。

本轮没有新建训练作业额度。现有前端 1800 秒／128MiB 等限制只约束原任务，不能默认为授权扩展成长时训练。正式实施时另外冻结：远端 conda、单活动 GPU 作业、有界 worker、显存／RSS／磁盘／单次和累计 GPU 时间，训练需支持分段保存及恢复。候选训练设置可从 1 GPU、micro-batch=1、数据 worker≤2、CPU≤4 起步，RSS 和输出容量按试测明确；资源不足不自动加卡或放宽停止线。

## 10. 外部控制与 LLM 自行控制的比较

| 维度 | 外部 SoulX＋Layer 1 | LLM 替代 SoulX 预测用户状态 |
| --- | --- | --- |
| 新增训练内容 | 消费含噪状态、附和、表达、取消后恢复 | 相同表达能力，再加连续话轮判断、用户附和与打断区分 |
| 输入条件 | 已有音频状态能力；Layer 1 可先只读文本与事件 | 纯文本缺少声学信息；同信息比较需增加音频输入或等价特征 |
| 数据 | 真实预测轨迹与表达目标 | 还需时序对齐的用户状态监督及覆盖声学难例 |
| 优化难度 | 主要风险是控制噪声、过度等待和恢复泛化 | 状态与表达联合学习，稀少转移标签易被正文损失淹没，需防遗忘并处理错误反馈 |
| 调度与评测 | 状态预测可独立及时执行，表达在合法边界更新 | 需在生成期间保持观察／状态决策频率，不能等待长回复结束再判断 |
| 新增训练开销 | 现有控制器冻结时通常较低 | 从当前文本表达底座起步，通常较高；绝对比值须实测 |

增加几个输出 token 的词表成本通常很小；真正增加的是状态识别能力、输入表示、时序样本和闭环优化。即便只有少量标签，重复处理长上下文和音频仍有成本。

说明性计算：100 小时按 160ms 窗口为 225 万个状态观察；若每个观察都重新处理 512 token，则约 1.152B token 次计算。它不是 B2 必须采用的训练方法：增量输入、会话打包、缓存或降低频率都能改变预算，也各有训练或时延限制。仅用于说明高频决策的调度成本可能远大于几个状态标签。

如果两方案训练相同底座、相同输入和相同数量的处理 token，计算量不会仅因“标签叫状态”就成倍增加。若从零培养两个方案，A 也要计入控制器训练；若 B2 已有可靠的全双工音频预训练，继续微调未必比 A 更贵。本文结论针对当前已有冻结 SoulX、表达底座尚未适配新状态输入的增量成本。

SoulX 原论文第 5.1 节使用千小时级英文及万小时级内部中文状态数据，控制器有自己的预训练投入；这不能直接换算为本项目需要同样规模。AdaptDuplex 则采用分阶段交互训练和动作／正文损失区分，说明联合方案需要专门课程；其模型、音频训练和硬件与本项目不同，不能用论文卡数或样本量作成本倍率。

## 11. 验证顺序与判定

先检查数据和运行协议，再做小训练。开发集同时看普通回答成功率与首音延迟、附和机会上的准确性和错误赞同、过度等待、重复回答、首音前取消比例与浪费生成量、实际抢话与停播延迟、取消后恢复正确性、旧 ID 泄漏。取消率低不一定更好，可能只是模型永远不开口；最终未出声也不证明早期生成合理。

固定同一控制轨迹，重放实测 TTS 时延与更快首音条件，报告实际可听行为。协议模拟、headless 播放和设备实播分别标记，不能将合成完成或音频入队当作用户听见。附和时机先在表示足够的子集验证，再判断是否值得增加声学输入。

建议当前路线先完成 A／B1 的基础交互训练，再在相同来源划分、表达预算和输入条件下研究 B2；不同时更换控制来源、TTS 和 Layer 2 训练，以免无法解释收益。
