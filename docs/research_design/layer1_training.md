# Layer 1 工程接入、窗口与训练方案

更新：2026-11-04。NTF-047 按用户要求仅保留路线 B：协议适配后的 7B Layer 1＋可取消运行时。依据为[研究范围](../research_design.md)、[架构合同](architecture.md)和 [SoulX 提前 complete 行为分析](../dev/SoulX-Duplug/completion_runtime_analysis.md)。用户资源为 8×RTX 4090；本文的窗口、训练配置和资源分配均为待验证建议，不表示已经接入 LLM／TTS、生成语料或开始训练。

## 1. 方案结论：先验证运行时与训练协议，再逐步微调表达层

目标是微调现有 Qwen2-7B／DuplexCascade Layer 1，使其消费外部状态，学习等待、系统附和、正式表达和取消恢复。运行时的取消、播放管理与账本先用确定性执行器验证；模型通过协议适配训练学习新状态与动作编码，再接入真实闭环并逐步训练目标行为。

唯一技术路线为协议适配后的 7B Layer 1＋可取消运行时。先学习外部状态与目标动作协议，再逐步学习含噪状态、取消恢复、附和及 thinking 利用；通过同底座的协议适配检查点、后续行为训练检查点与消融验证收益。

目标实现遵循当前合同：普通回答只有在 Layer 1 正常输入边界实际读到当前话轮已联合提交的有效 `user_complete` 及当前正文后，才能在当前 turn 内生成；不因 complete 另建回答会话或旁路调用。底层可能有多次有界解码执行，但属于同一会话调度。

首阶段冻结 SoulX、X2、TTS；Layer 2 暂不接入训练闭环。原 Layer 0 已并入 Layer 1，不新增独立附和模型。SoulX 提供外部用户状态，Layer 1 决定自己的表达；`user_backchannel` 不表示系统应当附和。训练是参数高效微调，不是从头预训练 7B 模型。

### 1.1 工程前置：先确定模型实际能读取的协议

第一份交付应是输入／输出协议和可取消运行时合同。明确用户正文、SoulX 状态、播放事件的来源边界，以及等待、附和、普通回答的编码和结束条件；先核查现有 checkpoint 的 micro-turn 序列、词表与训练语义，再确定可复用部分。SoulX 状态在 Layer 1 tokenizer 中重新编码，不直接搬运 token ID，也不把名称相似视为语义相同。

本地[加载器](../../scripts/runtime/layer1_model.py)校验并恢复的是 DuplexCascade 既有标记，如 `<|user finish talking|>`；这只确认符号与权重的恢复路径，不能证明模型已学会将 SoulX 外部状态作为条件，也不能证明已学会本项目的等待／附和／回答动作协议。WAIT、BACKCHANNEL、ANSWER 目前只是逻辑名称，没有据此确认新的目标 token 已注册或已训练。

协议编码优先复用训练语义兼容的已有 token，或采用现有词表组成的可解析短序列，并通过协议适配训练学习目标行为；新增 special token 时必须设计相应参数训练，不能仅注册词表后期待模型理解并正确输出。16 token 解码检查点本身也不构成外部观察输入边界，需另行定义和验证。

运行时先用确定性回放验证取消、迟到结果失效和首音竞争，再接真实模型与 TTS。SharedContext 的可靠消费仍待实现，详见第 3 节；本次仅明确前置依赖。

### 1.2 路线 B：分阶段训练协议、表达与恢复

从同一现有 checkpoint 出发，先训练协议：状态作为外部条件输入，目标动作与允许表达的正文作为模型输出。使用已有词表时可先验证现有 q/v LoRA 的适配效果；新增 token 时须同时设计并训练相关词表参数，不能继续无条件沿用 embedding／lm_head 全冻结配置。先保存协议适配检查点，检查无 complete 时等待、有有效 complete 时回答，以及动作与正文边界。

随后用 300—500 个独立来源、约 5千—1万个决策窗口验证含噪状态与首音前／后取消恢复；协议适配可使用同一小规模数据中的基础子集，分阶段保存，不要求另造一套数据。采用第 6 节的因果监督，不能用未来续说反推此前必须等待。有效后再扩大到基础主版的 5千—1万个独立来源。

普通回答与恢复稳定后，明确附和用途和取消规则，再加入系统附和数据；与协议适配检查点使用同一输入协议和运行时复测。最后才加入思考请求、异步 CoT 利用、递进回答与自我修正。该阶段另需设计 SoulX 的 CoT 条件化与主动澄清边界，继续保留 SoulX 控制职责。

每阶段与同协议的已适配检查点比较回答质量、过度等待、实际抢话、停播延迟、恢复成功及计算成本。重点记录提前生成正文、重复回答、沿用已取消条件，以及把未播内容当作已说等模型失败；运行时拒绝无效输出后的结果不能掩盖模型违规。若小训练只学会不开口，或取消恢复没有改善，应先检查协议、可见信息和数据目标；附和所需信息不足时先限制场景，再评估接口扩展，不能直接靠扩大数据量或用满八卡解决。

## 2. 行为分析对方案的约束

分析报告第二节的日志案例中，1.7396s 启动回答，1.9544s 请求取消，约相隔 214.8ms；取消确认 `played_samples=0`。该日志说明首音前取消机制存在，不能把自写运行时日志当作官方系统的实测结果。报告后续对官方服务交接、取消和消息整理的说明，与此案例的证据来源分别看待。

需要分别记录原始预测、规则后状态、服务交接、联合发布、模型实际读取、生成及实际播放。官方规则会参与 complete 的产生；服务 `speak` 也不等同于本项目 Layer 1 的普通回答指令。不能从最终未抢话推断 complete 准确，更不能把一次案例推广成自然部署概率。

[NTF-019](../reports/soulx/20261103-ntf019-fdb30/README.md)中 48 次 complete 快照有 38 次之后继续追加正文，只是固定诊断集现象。历史 Git 提交 `e80c05b` 保留的 672 条、2036 次启动、1368 次取消，包含混合取消原因；67.2% 不能解释为 complete 误判率或首音前取消率，也不据此决定训练配比。

设计有三项直接要求：

1. 输出必须可取消，且取消不依赖 Layer 1 再生成一个正确的停止 token。
2. 恢复必须区分未播与已播，不能把已生成内容写成用户已经听过的话。
3. 测试必须包含更快首音条件。生成或 TTS 加速可能将同样轨迹从首音前取消变为实际抢话，不能故意拖慢首音换取较低抢话率。

## 3. 工程接入与职责

### 3.1 先交付可取消的普通回答闭环

| 部分 | 建议实现 | 验收要点 |
| --- | --- | --- |
| 联合状态消费 | 在下游设计有界提交事件通知、批次身份和消费位置；模型仍读取最新合法快照 | 无重复回答；有效打断不因慢消费者漏读；过期 complete 不补执行 |
| 会话调度 | 单会话单个在途表达解码，在明确边界纳入新观察 | 160ms 发布不触发无限请求，不向在途 KV 随意插入新消息 |
| 输出生命周期 | 唯一 `output_id`，区分 preparing、playing、取消中和关闭；块携带 `chunk_id` 与用途 | 同一停止幂等，取消与首音并发可判定 |
| 唯一输出运行时 | 从已联合提交的信息取得有效打断，撤销输出资格，再尽力停止解码、合成和播放 | 不等待当前生成结束，不增设前端停止旁路 |
| FIFO、TTS 与播放器 | 在入队、返回和播放前复核输出身份，关闭后迟到结果失效 | 旧音频不复活、不重标为新输出 |
| 事实账本 | 分开保存生成、提交、合成、取消、实际播放及模型实际读取记录 | 可还原当时可见信息及实际可听后果 |

当前 SharedContext 主要保存最新联合快照，尚未实现上述可靠消费协议。事件通知、去重和容量溢出策略是待实现项，须先更新接口合同，再改代码；本文不将其记为既有能力。正文可合并为最新值，但关联活动输出的有效取消不能被后续状态覆盖。缓冲溢出必须显式报错并停止受影响的输出，不能静默丢事件后继续播放。

可靠消费不等于锁存旧 complete 作为永久回答许可。如果 Layer 1 读入前已有更新的 nonidle，应使用最新状态，不补执行旧回答；如果有效打断已经针对活动输出成立，后续 backchannel 也不能恢复该输出。联合发布不保证 X2 尾词已齐，不能额外等待整段转写或加入语义否决模型。

### 3.2 上下文恢复与缓存

| 最终播放事实 | 下一次输入组织 |
| --- | --- |
| 取消回执确认已播采样为零 | 续说并回原用户片段；保留真实生成及“未播取消”记录，不写成助手已说消息 |
| 已有实际播出采样 | 保留此前用户片段和已播事实；后续用户输入形成新片段，恢复时使用新条件 |
| 首音与取消并发 | 等待播放器最终已播回执完成分组，不能用合成完成或音频入队代替 |

官方按时长比例估计已说字符前缀，可作工程参考，不能作精确已听文本真值。首版建议关联文本块与音频块：完整播放块可确认，部分播放块保留采样位置与文本范围的不确定性。Layer 1 首版主要消费事件级“未播／已播／取消”信息，不强行提供伪精确逐字对齐。已听内容不能删除，完整生成账本也不因消息整理而销毁；不同视图须明确来源且不重复注入同一文本。

KV 只复用 token 序列完全一致的前缀。取消、用户片段合并或上下文整理改变后续输入时，从变化位置重算；不能删除显示消息却沿用含旧消息的 KV。清理计算缓存不等于丢失逻辑会话与真实历史。训练和推理应采用同样的输入序列组织，先验证正确性再优化缓存。

## 4. Layer 1 的窗口建议

“窗口大小”至少包含发布周期、输入决策节奏、解码执行块与上下文容量四个不同参数。建议起点为：**前端仍为 160ms；普通倾听更新按 640ms 软节奏合并；有效 complete 与取消等关键事件不等定时窗口；解码每块先试 16 token；训练序列先用 2048 token。**这些数值不是已测最优值，也不是首音或停止时延保证。

### 4.1 时间窗口：640ms 是普通更新的合并节奏

| 参数 | 起步建议 | 解释 |
| --- | --- | --- |
| 前端发布 | 160ms，沿用既有合同 | 每批正文与状态共同提交；无新增文字也可能有有效状态变化 |
| 倾听时普通输入更新 | 640ms，即 4 个前端周期 | 有新信息时安排一次合法读取；读取最新完整快照，不仅看最近 640ms 的文字 |
| 关键事件 | 提交后尽快唤醒，进入最近合法输入边界 | 包括新有效 complete、取消回执；打断执行由运行时直接处理，不等待模型窗口 |
| 无新增信息且无待表达内容 | 休眠至新事件 | 不要求持续空解码，也不重复生成 WAIT |
| 表达期间读取机会 | 在有界解码块结束后检查新增观察 | 普通更新可合并；有紧迫事件时提前让出执行，不等整段回复结束 |

选择 640ms 是因为它与 160ms 对齐，也适合先降低 7B 处理普通增量的频率；不是根据 214.8ms 案例推导出的最佳时机。首轮比较 320／640／960ms，在相同输入和表达预算下观察过时输入、附和机会覆盖、恢复速度及计算量。既有底座 600ms micro-turn 与这里的建议不是同一配置，迁移时应显式记录，不能宣称已经切换。

640ms 不代表固定端点等待，不得把已经可用的有效 complete 故意压到下一计时点；也不代表必须在 640ms 内完成一次 7B 推理。实际读取可能受在途执行影响，应记录“联合发布→实际读入”延迟及 P50／P95。若长期跟不上，合并普通更新并优化执行，不堆积并发请求或反复执行过期窗口。

停止时延另行拆分为用户续说到联合发布、联合发布到取消请求、取消请求到实际停播。仅调小 Layer 1 的普通窗口，不能消除前端识别与播放器缓冲延迟。

### 4.2 解码块与播放块不是同一窗口

建议先以每块最多 16 个生成 token 作为调度检查点，试测 8／16／32 token。它是让出执行和检查新观察的粒度，不是完整回复长度，也不是必须发给 TTS 的片段长度。实际时间依赖模型速度；即使一块尚未结束，运行时也必须能够撤销播放资格，解码停止可随后完成。

块结束不能伪造 EOS、轮次结束或强制插入用户消息。无新输入时继续当前生成；需要纳入外部观察时，必须通过明确定义并在训练中出现的协议边界组织新输入，或结束旧执行并按可见事实重建输入。暂停 16 token 不会自动赋予现有 Layer 1 中途读取新观察的能力，协议适配须覆盖实际输入交错方式并单独验证。

TTS 应按可朗读的短语或分句组织文本，允许跨多个解码块收集，不把 token 调度块机械映射成语音块。合成与待播队列均有界；队列容量、单块音频时长和设备缓冲必须单独实测，它们直接决定取消后还会播出多少声音。

### 4.3 上下文长度：先 2K，再按覆盖情况扩到 4K

小训练先采用 **2048 token 的完整序列上限**，包含系统协议、用户正文、外部状态、历史、事件和目标输出；不是输入 2048 后再无限追加目标。在线容量与训练分布保持一致，可先预算约 1536 token 输入、最多 512 token 本次输出；实际按序列内容分配，512 是上限而非要求说满。

基础主版是否扩至 4096 token，由数据长度分布和显存预检决定。重点统计取消前后轨迹、当前用户片段和必要历史的覆盖率；若 2K 经常装不下，先评估 4K，而不是截掉取消原因或关键用户条件。8K 及以上留到长历史或 thinking 数据确有需求时再测。

2K 是起步预算，不是允许静默丢信息的规则。超长样本显式标记，进入长序列分桶或暂不纳入该轮；线上超限必须有已定义的历史管理或受控失败策略。若采用历史摘要，只能根据当时已知内容生成，并在训练中使用一致方法。不得截断当前用户关键信息，或用未来完整转写生成“在线摘要”。

窗口选择最终同时看质量、读取延迟、实际可听行为、显存和 token 成本。数据与运行日志必须保存窗口配置、真实执行时间和模型实际可见的快照，不能只保存名义上的 640ms／2K。

## 5. 系统附和的标注

系统附和放在普通回答与取消恢复闭环之后接入，仍属于同一个 Layer 1。它允许用户持续说话，因此不能把下一拍持续 nonidle 机械视为新的打断，也不能简单豁免所有附和取消。必须先明确附和用途、长度预算、重复抑制及何种新观察构成有效取消，再训练和验收。

当前五状态和文本是否足以区分这些情况尚未证明。若表示不足，先限制到可判定场景，并单独研究声学特征或接口扩展；不能只靠改标签修补缺失信息，也不在本文自动修改已确认的普通回答停止规则。

自然双人对话中的听者短回应是候选，须人工区分附和、接话、澄清和打断。以事件机会窗口标注“适合但可不发”“不应发”“不确定”；历史没有发声不等于负例，一次机会成功表达后，相邻窗口不能反复要求附和。强负例包括刚附和过、即将交接、已有正式输出、容易被理解为错误赞同，以及无回应必要的连续语段。

教师与学生使用同样的可见信息。若学生只有转写、状态与事件，不得要求它复现仅凭语调才能判定的精确时机。模糊机会可用允许动作集合或不进入硬监督；等待不自动计为遗漏。系统附和和用户 `user_backchannel` 必须分开标注。

## 6. 因果数据与监督

### 6.1 数据单位

数据以独立对话／任务片段为来源单位，以事件轨迹为基础，在真实合法输入边界采样决策窗口。160ms 前端批次不自动成为一个训练样本。长段无变化等待可稀疏采样；complete、续说、取消、恢复和附和机会附近加密。自然分布开发／测试集不做相同重采样。

每条轨迹包含来源与派生关系、联合快照及可见时刻、用户片段、模型实际读取边界、真实生成、输出用途和身份、取消与播放回执。完整未来音频、最终参考转写和误判诊断只用于离线审核，不进入此前模型输入。精确播放采样属于执行与评分账本，不要求全部编码进模型。

### 6.2 提前 complete 如何标注

| 当时可见事实 | 监督原则 |
| --- | --- |
| Layer 1 读入前新 nonidle 已提交 | 使用最新合法快照，不补执行过期 complete |
| 已读到 complete，尚无续说证据 | 可生成当时合理的回复，不能根据未来续说倒推必须等待 |
| 当前前缀已有明确未完成信息 | 审核等待是否合理；Layer 1 不改写 SoulX 状态，不新增独立否决器 |
| 首音前取消 | 使用合并用户片段恢复；未播生成不能变成已说消息 |
| 已播后取消 | 保留已播事实，响应新条件，必要时明确纠正 |
| 旧文本／TTS 迟到 | 运行时丢弃；模型学习结束旧表达方向，不自动续播 |
| 后续有效 complete 到达 | 正常回答，避免训练成永远等待 |

例如“订周五的车票……不对，是周六”：在“周六”可见之前，不能要求模型预知改口。同一前缀可派生确实结束与稍后续说两个分支，在尚无可见差异时不得赋予矛盾的确定动作标签。

被取消文本不是天然负例：合法且合理的已生成前缀可保留正监督；错误历史可以作为恢复条件并屏蔽损失。取消之后未生成的续写不补造为目标，取消点也不伪造模型主动 EOS。首版用 SFT，不依赖 RL。

### 6.3 构造与质检

1. 先按原始对话、说话人／来源和任务模板划分训练、开发、测试，裁剪和同前缀分支跟随母组。FDB、SoulX-Eval 及改写均不进入训练或阈值选择。
2. 采集自然与任务型对话，保留附和、口语不流利及双说话人时间信息。[SwDA](https://github.com/cgpotts/swda)与 [DuplexGen](https://huggingface.co/datasets/DuplexGen/duplexgen-corpus)仅为候选来源；实施前复核音频、对齐、语言及使用条件，不假定话语标签已有逐词时标。
3. 用冻结的当前前端重放音频，保留真实 X2 增量、SoulX 状态和联合可见顺序。以实轨迹为主，加入有依据的短暂 complete、重复状态、ASR 滞后等扰动。
4. 教师只看当前前缀，生成动作与正文目标；审核者可看未来诊断，但须检查目标当时是否可知。
5. 用实测分布或明确标记的模拟执行器生成首音前／后取消轨迹，加入更快首音条件。真实 LLM＋TTS 只对代表性子集闭环，不为全池合成音频。
6. 首轮 SFT 后在训练分区运行模型，补采它自己的重复回答、错误续写及恢复失败；开发／测试错误不回流训练。
7. 机械检查事件顺序、身份、可见范围、取消后输出资格和分组；人工分层抽查附和、恢复与教师拒绝样本，记录分歧和接受率。

加入附和后的采样可从等待 45%、附和 15%、普通回答 25%、取消恢复 15% 起步，再按试采调整。这是场景配额，不是四个互斥动作；恢复窗口也可能输出等待或回答。未接入附和的第一阶段不套用该比例，不能照搬 FDB 的提前 complete 频率。

## 7. 模型、协议与训练课程

### 7.1 先保持底座与加载路径可比

首轮沿用现有 7B checkpoint，不同时更换底座、控制器和 TTS。[加载器](../../scripts/runtime/layer1_model.py)目前只开放已有 q/v LoRA，冻结 embedding／lm_head，并严格恢复官方权重。已有 adapter 的结构与 rank 从 checkpoint 配置读取，不随意替换后仍声称等价恢复；新候选还需扩展[候选加载验证](../../scripts/runtime/layer1_candidate.py)的登记与重载检查。

WAIT、BACKCHANNEL、ANSWER 在本文只是逻辑动作。优先复用语义确实匹配的已有协议，否则先评估现有词表组成的可解析短序列；本项目目标实现仍安排协议适配训练，不以可解析或一次提示成功证明已具备持续执行能力。SoulX 与 Layer 1 tokenizer 不同，不能复制 token ID。若新增 special token，须设计输入 embedding 新行、输出头对应行及其共享关系的初始化、训练与保存重载；现有加载器会全部冻结这些参数，必须先修订训练与加载设计。可参考 [PEFT 的词表扩展说明](https://huggingface.co/docs/peft/developer_guides/troubleshooting#extending-the-vocabulary)，具体能力需核对项目固定依赖版本；不能新增词表行后仍宣称现有 q/v-only 配置已经覆盖其训练。

训练只监督模型自己的动作、协议边界和允许表达的正文；用户文本、外部状态、事件及后续 CoT 屏蔽目标损失。动作／边界与正文损失分别统计，权重由开发集选择，避免长回答掩盖稀少动作。屏蔽损失并不免除输入 token 的计算。

### 7.2 课程与初始配置

| 阶段 | 内容 | 进入下一阶段的条件 |
| --- | --- | --- |
| 工程验证 | 用确定性执行器验证可取消运行时 | 身份、分组、停止和恢复账本正确 |
| 协议适配 SFT | 外部状态消费、等待／回答目标与合法输入输出边界 | 基础协议可学，保存重载一致；形成后续行为训练的比较起点 |
| 小规模行为 SFT | 含噪状态、首音前／后取消恢复与正常回答 | 正常回答保持，恢复按新条件执行 |
| 基础主版 | 扩大噪声和任务覆盖；附和合同确定后加入附和 | 附和与恢复改善，过度等待及错误赞同可控 |
| thinking 适配 | 思考请求、异步结果利用、回答递进与自我修正 | 基础交互稳定，能单独检验 thinking 收益 |

远端单卡预检从 BF16、micro-batch=1、梯度检查点、2048 token 开始；学习率可试 `2e-5～1e-4` 的小范围，先 1 epoch，再依据开发集决定是否到 2 epoch。这是试验起点，不是已验证超参。梯度累积和有效 batch 按 token 量及长度分布记录，多卡比较尽量保持一致。

若现有加载器在单卡预算内放不下，再实现 QLoRA：冻结 4bit 主干、NF4、双重量化、BF16 计算是可考察配置，参见 [PEFT 官方文档](https://huggingface.co/docs/peft/en/developer_guides/quantization)。需验证官方 checkpoint 转换、既有 adapter、特殊词表、保存和推理重载，不能套用通用基座加载就默认保留原能力。量化改变数值，需与原精度配置复测，也不承诺更快。

扩大 LoRA 目标层与换更大底座分别作为后续变量；是否新增 token 必须在协议冻结时确定，若为必要项，其参数训练纳入首轮设计。基础训练期间保留普通任务回答，避免只学会等待或短附和。Layer 2 的 CoT 利用属于下一阶段；轮内主动澄清仍需对应控制器条件化及生成边界设计，不能伪造 complete 或仅靠 Layer 1 微调绕过架构。

## 8. 数据规模与实际 token 预算

| 阶段 | 独立训练对话／片段 | 决策窗口 | 单 epoch 处理 token 规划 |
| --- | ---: | ---: | ---: |
| 试标与小训练 | 300—500 | 5千—1万 | 2M—5M，按实际打包复算 |
| 基础主版 | 5千—1万 | 10万—20万 | 有效连续轨迹组织下争取 30M—80M |
| 学习曲线支持后扩展 | 2万—5万 | 30万—100万 | 150M—500M，非预先必须投入 |

这些不是达到准确率的保证。同源重叠窗口、分支和延迟版本不重复计独立场景。主版另留开发、测试各至少 500 个来源分组，按实际附和和取消事件密度补足。训练音频可规划 50—200 小时，以覆盖验收；不能由音频小时直接换算训练 token。

30M—80M 的前提是连续轨迹共享前缀后，平均每个决策摊销约 300—400 token。若每个窗口独立重放 2K 历史，10万—20万个窗口仅重复输入就约 200M—400M token，另加目标与 padding。第一版若先使用简单独立样本，应接受较高的真实预算，不能仍套小预算。

普通 packing 只减少 padding，不自动消除重复前缀；不同会话须隔离注意力。连续轨迹打包也须满足真实可见顺序和模型协议，不能让未来状态进入过去决策。不能跨参数更新复用旧训练 KV。统计输入、监督目标、重复前缀、padding 和全部实际处理 token。

附和阶段争取 5千—1万人审机会、1万—2万个恢复窗口；恢复可含扰动及同源分支，单列真实来源数，不称其为全部自然误判。数据量由学习曲线决定，不用扩大切片数代替增加来源多样性。

## 9. 8×4090 的安排与成本

### 9.1 按阶段用卡，先测单卡再扩展

RTX 4090 每卡 24GB、无 NVLink，见 [NVIDIA 官方规格](https://www.nvidia.com/en-us/geforce/graphics-cards/40-series/rtx-4090/)。八卡不能当作单块 192GB 显存直接使用；服务器是否同机、PCIe／NUMA 拓扑、P2P 与通信性能须实测，不由卡数推定。

| 工作 | 建议资源 | 判定依据 |
| --- | --- | --- |
| 正确性与显存预检 | 1 卡 | 完整前反向、优化器步、保存、恢复和最大长度峰值通过 |
| 扩展试测 | 依次 2 卡、4 卡 DDP | 同类长度和有效 batch 下测总吞吐及通信开销 |
| 主版训练 | 优先 4 卡，确认收益后再评估 8 卡 | 单卡能放完整副本时优先数据并行；不默认八卡线性加速 |
| 闭环运行 | 初步规划 2—3 卡，组件按显存拆分 | 前端、Layer 1、TTS 不强塞同卡；实际共存由预检决定 |
| 正式时延评测 | 独占相关计算资源 | 暂停其他重计算作业，避免资源竞争污染时延 |

LoRA 数据并行主要同步可训练参数，但每卡仍保留主干与相应激活。7B BF16 权重理论约 14GB，现有加载器还有 embedding／head 副本，不能当作实际训练占用。若单卡无法满足预算，比较 QLoRA 与必要分片；不先引入跨八卡的复杂张量并行，也不因有八卡立即换大模型。

首次预算可采用每卡约 22GiB 保护线，单卡预检 CPU≤4、数据 worker≤2；多卡 worker 必须按整机汇总，不将单进程额度直接乘八视为已授权。RSS、磁盘、单次和累计 GPU 时间在任务单中另定。采用远端 conda、单活动作业、有界进程与队列；一个多卡作业的 rank 属于该作业统一管理。本次不提交任何作业，也不放宽旧任务额度。

### 9.2 训练时间按总吞吐复算

设每 epoch 实际处理 token 为 T，epoch 数为 E，实测多卡总吞吐为 Q，卡数为 N：墙钟小时＝T×E÷Q÷3600；GPU 小时＝墙钟小时×N。Q 应覆盖真实长度、padding、损失 mask、梯度检查点、累积、优化器步、通信和读取，不能用纯解码速度替代。

以下均为假设，不是本项目 4090 的实测速度。以 30M token、2 epoch、4 卡为例：

| 假设总吞吐 Q | 核心墙钟 | 核心 GPU 小时 | 加 30% 评估／保存预留后的墙钟 |
| ---: | ---: | ---: | ---: |
| 1000 token/s | 16.7h | 66.7 | 21.7h |
| 2000 token/s | 8.3h | 33.3 | 10.8h |
| 4000 token/s | 4.2h | 16.7 | 5.4h |

80M 是该示例的 2.67 倍；若实际独立样本输入为 200M，成本至少按相应 token 量上调。8 卡的 Q 必须另测，不能把四卡时间直接减半。主版对照和多个随机种子分别计费，一个 adapter 的训练时间不是完整研究成本。

### 9.3 数据与运行成本也要计入

| 项目 | 估算与限制 |
| --- | --- |
| 前端重放 | 墙钟约为音频小时×RTF；若占用 k 张卡，GPU 小时再乘 k。实时送音与离线快速采集分开报告 |
| 教师生成 | 10万视图各输入 1000、输出 50 token，约为 100M 输入和 5M 输出，另计吞吐或接口费用 |
| 人工复核 | 3000—5000 窗口、每个 30—60 秒，约 25—83 人时；双标与裁决另计 |
| 闭环回放 | 500 条×30 秒约 4.17 小时输入；每张占用卡均计时，不为全池执行真实 TTS |
| 音频存储 | 16kHz mono PCM16 每小时约 115.2MB，100 小时约 11.52GB；优先引用既有音频 |
| 检查点与日志 | 保留最佳和最近可恢复检查点，轮换删除；限制回放产物，不保存每步全量 logits 或重复快照 |

前端旧任务的 1800 秒／128MiB 限额不能直接套用长训练，也不意味着已获准突破。正式任务须支持分段保存、恢复与资源超限退出，并记载整机峰值。

## 10. 验收、消融与交付顺序

工程硬要求是：关闭的旧输出不能重新开播，迟到结果不能换身份复活，同一有效完成事件不重复回答，取消与首音竞争后的用户分组正确。通过确定性回放和竞争条件测试验证这些不变量，再开展真实模型闭环；模拟、headless 和设备实播分别标记。

模型比较保留协议适配检查点、加入取消恢复的小训练、扩大后的基础主版及加入附和的阶段结果。使用同协议的已适配检查点比较恢复与附和训练收益。完整主版另做去除取消恢复、去除附和的消融，主配置复核至少两个随机种子。各组保持底座、协议、控制轨迹、TTS、来源划分和预算口径可比。

共同指标包括普通回答成功率、过度等待、首音延迟、重复回答、实际抢话、停播延迟、首音前取消比例与浪费生成／合成量、恢复时条件更新和错误续写、附和合理性与错误赞同、旧 ID 泄漏。取消率低可能只是模型不开口，首音快也可能暴露原先被取消遮住的抢话，两者均不能单独证明更好。

固定同一控制轨迹，在实测首音条件与更快首音条件下分别回放。窗口实验比较 320／640／960ms，解码块比较 8／16／32 token，上下文先比较 2K 与必要的 4K；分阶段控制变量，不一开始做全部笛卡尔积。先选择满足质量与恢复要求的配置，再权衡吞吐。

建议实施顺序与阶段交付如下。运行时先模拟验证，模型通过协议适配训练建立基础行为，再开展真实闭环与后续训练。

| 顺序 | 工作与交付 | 推进条件 |
| --- | --- | --- |
| 1 | 接口与协议：输入序列、动作编码、合法读取边界、词表及参数训练方案 | 可检查样例序列，普通回答边界与现有架构一致 |
| 2 | 输出运行时：确定性取消与播放验证 | 工程不变量通过，账本可还原 |
| 3 | 路线 B 协议适配及小训练：300—500 个来源试标，分阶段保存协议与恢复检查点 | 参数训练覆盖选定协议，正常回答保持，取消后使用新条件；保存重载一致 |
| 4 | 基础主版与附和：扩大来源覆盖，分阶段检查点和消融 | 附和生命周期已明确，错误赞同和过度等待可控 |
| 5 | thinking 适配：请求、结果利用与两组任务评测 | 基础交互稳定，CoT 输入与主动澄清合同已另行确定 |

训练先按第 9 节远端单卡 conda 预检，再测 2／4 卡扩展，确认吞吐收益后评估 8 卡。每个阶段只有在收到实施指令后再拆具体工作单；本文完成只代表设计文档交付。

## 11. 研究边界与参考

当前仅研究外部 SoulX＋Layer 1 下的协议适配与表达层微调。SoulX、X2 与 TTS 在基础比较中固定，已有预训练成本与本项目新增训练成本分开记录；后续 SoulX 的 CoT 条件化适配另计数据与预算。

现有目标保留 SoulX 后续读取 CoT 的控制器适配。基础 Layer 1 微调、系统附和和普通取消恢复不等于已经验证边听边想的主动澄清，或边说边想的持续推理收益；分别按[倾听任务](listening.md)与[表达任务](speaking.md)验证。

- [SoulX-Duplug](https://arxiv.org/html/2603.14877v1)：控制与表达分工的参考；实际行为以项目固定源码及本地分析为准，不外推日志比例。
- [AdaptDuplex](https://arxiv.org/html/2609.29217v3)：异步结果输入及分类型监督的参考；其层号不对应本项目，也不声称已公开可直接照搬的全部数据流程。
- [QLoRA 原论文](https://arxiv.org/abs/2305.14314)与 [PEFT 量化文档](https://huggingface.co/docs/peft/en/developer_guides/quantization)：支持量化主干上的适配器训练，不提供本项目吞吐保证。
- [NVIDIA RTX 4090 规格](https://www.nvidia.com/en-us/geforce/graphics-cards/40-series/rtx-4090/)：显存和互联规格；不能代替服务器通信与训练预检。
- [提前 complete 分析](../dev/SoulX-Duplug/completion_runtime_analysis.md)和 [FDB30 报告](../reports/soulx/20261103-ntf019-fdb30/README.md)：支持机制与固定诊断现象，不证明新 Layer 1 效果。
