# TT-010：非附和式ASR更新让轮与输出生命周期数据改造

状态：待实施。2026-10-25用户明确要求建立本工作单，替代已终止归档的[TT-009](../archive/TextTurn/tt_009_conditional_data_rebuild.md)。本次交付数据改造合同和实施工作单，不构造新数据、不重训、不注册新token、不修改现有模型或运行中的TT-008。改造无需等待TT-008质量结论。

## 问题与目标

旧构造把打断stop绑定到`trigger_text`首次出现，停止词尚未完整可见时仍监督keep；对不含停止词的普通续说／接管覆盖不足。该标签设计不符合用户现在明确的“Speak期间出现非backchannel式ASR更新就让轮”目标。短附和仍应保持keep，不能改成任意ASR变化都stop。修改依据是策略要求与现有标签合同冲突，不必先用TT-008证明模型失败；也不能仅凭现象断言模型已经学到哪一种内部捷径。

新目标：当前有效用户轮出现新的非空ASR文本变化时，若助手仍处于Speak，且当前可见更新不是backchannel，首个可判定该更新的控制决策监督stop；不等待停止词、完整句或显式停止请求。普通续说、补充、纠正、提问、改请求和明确停止请求均可让轮；短促、无接管含义的backchannel保持keep。stop仍只表示用户打断，正常结束保持独立。

这里的“立即”指不因缺少固定停止词而延迟，也不等用户说完整句；仍需依据当前可见前缀区分backchannel。默认480ms控制窗及既有ASR延迟仍然存在，应记录ASR发布→首个可见控制请求→stop返回→实际停播确认；本项不擅自改为ASR事件到达即同步推理，不增加VAD、阈值、固定等待或延迟补偿。

## 一、重新定义用户更新和监督

- 有效更新来自唯一Nemotron源、当前用户turn及新版本；模型必须看到本次文本变化。重复快照、纯版本递增但文本不变、旧版本、已提交旧轮的重复全文、控制标记和助手正文不作为新用户输入。当前流是追加前缀；不额外实现ASR回写协议，后续若支持修订，须明确文本变化与提交边界。
- Speak＋可判定为非backchannel的有效用户文本更新→stop；Speak＋可判定的backchannel→keep；Speak＋没有有效更新→keep，直到真实输出生命周期改变状态。模型生成结束而音频未播完仍是Speak，此时非backchannel更新仍为stop。
- Listen下仍学习keep/start及正常接话，不把任意ASR更新映射为stop，也不把no-voice固定映射为start。首个stop生效后，后续用户增量归当前用户轮，在Listen继续到达，不重复标stop。
- 保留短附和keep负例和误stop指标；backchannel按当前语境及可见前缀判断，不依赖固定词表或长度阈值。相同开头可先是附和，随着新词到达转成补充／纠正，此时新决策应stop。无法根据当前前缀区分的窗口保留unknown并屏蔽动作监督，不拿未来完整发言或后续标签倒推当前动作，也不把所有词内片段强标keep。此处保留未知是因果标注要求，不引入运行时等待阈值。
- 普通词、词内片段、含停止词及不含停止词都覆盖；stop监督锚点是当前前缀首个可判定为非backchannel的有效更新，不再使用`trigger_text`判定。另记录该用户段首次有效更新，以区分ASR可见、标注可判定与控制延迟。构造相近历史与正文下的“非附和更新／短附和更新／无更新／重复旧文本”对照，避免只凭停止词、assistant_visible非空、固定时刻或回答长度预测。
- 识别噪声可能被误判为非附和并导致让轮，应按已有来源属性单列；不将噪声统称附和，不在本项另加语义过滤器、规则词表或第二个仲裁器。backchannel与非backchannel由同一控制器依据输入学习区分。

## 二、`<finish>`的设计判断

**建议显式注入完成标记，但作为运行时输入事件，不作为模型新增可预测动作。** 本工作单用`<start>`、`<stop>`、`<finish>`表示逻辑标记；原动作实际编码仍是`<|tt_start|>`／`<|tt_stop|>`，新完成标记的实际拼写、特殊token注册及embedding处理在实施时统一冻结。

现有显式状态和播放完成事件已经能驱动状态转移，专用finish token并非必要条件；它能让训练轨迹区分“正常播完”和“用户打断”，便于检查输出闭环。与结构化完成事件相比，专用token是输入编码选择，不能代替真实播放确认。实施中需说明采用专用token的收益和新增词表成本，不把配对整齐本身当作质量改进证据。

| 事件 | 产生者和时机 | 模型处理及状态 |
| --- | --- | --- |
| start | 控制器提出，唯一执行点接受后建立output_id | 合法动作；建立待启动输出，实际开播后进入Speak；记录接受与开播时间 |
| stop | Speak看到非backchannel式有效ASR更新后由控制器提出 | 合法动作；撤销该输出的提交资格并请求停播，实际Listen与终态以执行确认记录为准 |
| finish | 运行时确认该output_id生成结束、无后续待合成／待播内容、最后音频播放完成后产生 | 注入上下文的外部完成事件；Speak→Listen，不参与动作argmax或动作预测损失 |

1. 生成EOS、最后文本入队、TTS返回、音频已发送、暂时队列为空均不能提前注入finish。生成完毕与播放尾窗分别可见，未播完时保持Speak。数据阶段若没有真实播放，只能使用明确标记的合成播放器完成事件，不能冒充实测音频证据。
2. 完成事件携带output_id、单调event_seq、发生／发布／消费时间及原因，立即写入共享上下文，下一实际输入边界可见；不依赖下一次ASR更新，也不每个控制窗重复追加。完成后状态和最近终态可在后续快照持续可见，防止一次事件遗漏。
3. 完成标记由外部注入，其token不算控制器输出，也不送TTS。输入事件和正文位置屏蔽损失，训练目标仍是当前状态合法的keep/start/stop。不得让模型在Speak中自主预测finish，避免尚有音频时提前让轮或凭未来长度猜结束。
4. 按**已被执行点接受的start及output_id**校验：正常闭合轨迹恰有一个终态stop或finish。stop请求／确认保留为同一次关闭的不同阶段，不重复计两个stop；已中断输出的迟到播放完成只记过期事件，不能再产生finish。重复回调、旧output_id和同刻用户更新／播放完成由单一执行点排序、去重。
5. 配对不是相邻token语法：一轮start与关闭之间可以有多个keep、ASR更新、生成完成和播放尾窗；被拒绝的start不建立输出。仍在播放或轨迹截断允许暂未配对，须标记open／truncated；播放错误或异常取消单列，不伪造finish凑闭环，也不在本项扩展第四个模型动作。
6. 播放确认先发生时，后续用户更新处于Listen，无需再stop；非backchannel用户更新先发生且仍Speak时走stop；若为backchannel则保持keep。真实停播确认前的停止请求状态和时序必须明确，不能拿模型stop返回代替用户实际听到的停止。

1. 使用训练／开发来源重建版本化数据；保留TT-001旧冻结集及旧候选，不原地覆盖。UltraChat test、FDB文本／音频／ASR trace及TT-008结果不得回灌、选参或挑选训练模板。维持来源／近重复组隔离。
2. 重建完整轨迹：用户增量→实际接受start→助手因果前缀→非backchannel式新增用户文本导致stop，或真实／明确模拟的播放完成导致finish→Listen等待及下一用户轮。每一动作保留决策前快照和接受后事件，不泄漏未来文字、未来音频长度、未来完成时间或参考标签。
3. 覆盖生成中打断、生成完但播放未完时打断、首次正文发布前打断、正常播完后下一轮、短附和keep及由附和前缀转为非附和更新后stop、无更新、重复旧文本、多次start/stop交替和未闭合片段。无更新时保留足够keep观察，但限制重复窗口，按来源及独立事件统计，避免冗长keep淹没stop。
4. 助手已提交用户轮、当前新增用户段、已生成正文、已播放位置和完整历史分开；stop保存已到达用户内容及真实发布／播放事实，不把中断回答记成完整播完，不回滚用户已听部分。
5. 默认沿用480ms及每窗8 token的训练合同；160ms重测仅为既有实验例外，不能擅自改变训练节奏。尾窗与轮后等待以毫秒冻结；采样、资源、最大长度和新增标记处理写入新版本说明，必要代码和少量测试配套同路径中文文档。
6. 更新后续验收：首个可判定非backchannel更新后的首个可见控制决策stop率、更新至决策及实际停播延迟、附和／无更新／重复旧文本的误stop、生成结束到播放完成之间的正确状态、start终态配对及去重；附和误stop保留独立分母，歧义前缀及观察不足单列，不以提高stop次数代替质量改善。旧评测保留旧合同名称，禁止新旧分数混算。
