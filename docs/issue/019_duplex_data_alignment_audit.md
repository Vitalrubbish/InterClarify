# Issue 019：DuplexCascade 数据生成语义对齐复核

状态：进行中（已完成只读复核；待处理句读视图空拍并重建受影响产物）。父任务：[004](004_training_data_and_annotation.md)。

## 工作单元

在 004 人工签署前，逐项对照官方论文与发布推理代码，检查特殊 token、micro-turn 切分、自然停顿、用户附和、打断和思考事件；对发现的语义偏差单独处理并重新审计。当前冻结的 r3 原件保留用于追溯，不将本次只读检查视为用户签署。

## 已核实

- 论文第 3.3 节的用户 1–7 token 随机切分、assistant 10 个内容 token、停顿 0.10 与 1–5 空拍、打断 0.30、用户附和 0.01、回答后思考 1–20 空拍，均在当前配置和事件生成器中有对应实现。
- 发布 `server.py` 的五类控制词面、`<|no voice|>`、raw ChatML header 与消息结束符，与当前配置及编码器一致。发布 tokenizer 的实际 ID 已在构建时逐项核验。系统附和关闭，符合本项目选用的无系统附和版本。
- 用户续说对应 talking，末片段配对 finish 与回答首片段；回答续写配对 no-voice，附和替换续写拍的 no-voice 并保持回答正文；打断先发 interruption、丢弃旧回答余段，再消费下一原始用户轮；停顿与思考为空拍。这些事件顺序符合论文描述的控制语义。
- 官方仓库仅发布推理代码，未发布完整数据生成器；本项目的边界冲突处理和精确随机序列不能宣称逐样本复刻作者训练数据。当前有效打断只在有下一用户轮且回答至少两片段时抽样；论文表述的 0.30 是每个系统长轮，本实现的条件分母更窄，需在报告中持续标明。

## 发现的偏差及后续工作

`MicroTurnPlanner` 先按原样文本冻结用户片段，去句读视图随后删除字符。若一个片段只有可删除标点，`SequenceEncoder.event_ids` 将空串编码为 `<|no voice|>`，但仍保留原控制目标。前 32 条完整材料中有 **49 个事件、涉及 28 条对话**：39 个 `response_start` 被监督为 `<|no voice|> → <|user finish talking|> + 回答`，10 个 `user_continuation` 被监督为 `<|no voice|> → <|user is talking|>`。例如审计 20 的 event 131 为原样 `.`、去句读空串，随后直接开始回答。后者可能与自然停顿混淆，前者尤其与无声接话控制冲突。机器审计只验证结构、ID 与重建一致性，未检查这种语义条件。

- [ ] 修改生成器和必要的语义审计，增加针对标点独占末片段及非末片段的回归；同步更新每个修改文件对应的 `docs` 文档。

## 修复设计（先于代码）

原样 tokenizer 仍先抽取 1–7 个基础 token 的初始用户片段。若某片段去句读后为空，将其原文与字符跨度合入相邻片段：有前片段时合入前片段，开头片段则合入下一个片段；重复直到每个事件在原样和去句读视图都含非空用户文本。合并在基础事件生成前进行，因此三视图仍共享同一事件、控制目标与原文跨度。合并片段可能超过 7 个基础 token，作为明确的边界例外计数；不声称严格逐拍 1–7。若原始用户长轮整体去句读后为空，则在来源过滤阶段排除整条对话，保留原因。机器审计须断言有来源跨度的用户事件在两个视图均非空，并报告合并次数及超过 7 token 的片段数。此次改变生成计划，必须重建全部正式产物及32条材料。
