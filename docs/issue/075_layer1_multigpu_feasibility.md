# Issue 075：远端多卡训练部署可行性与成本调研

状态：待执行，2026-10-21。可与073独立推进，正式3k成本估算依赖074。本单交付调研和可执行任务方案，不实现分布式训练器、不提交GPU作业。

## 已知基线与调研目标

[1k训练报告](../../reports/layer1_training/issue040-delayed-training-20261020/README.md)记录：单4090、2048长度、batch1/累积2、1epoch共2469序列/1235步，训练约40.7分钟，CUDA allocated峰值约19.11GiB、reserved约21.81GiB，RSS约15.63GiB。这是历史实测；按样本数线性外推3k约122分钟只能作粗估，实际依赖074的长度和序列分布、硬件与通信成本。

当前训练器明确要求`torch.cuda.device_count()==1`，协议固定1k、单卡和旧索引，尚无分布式数据分片与同步契约。现有脚本直接申请多卡不具备可运行依据。调研应回答：远端是否能提供合适资源、需要改哪些代码、是否比单卡更值得部署，以及如何验证训练目标保持一致。

## 工作范围

1. 在远端只读核查调度器可申请的同节点GPU数量、型号/显存、CPU与内存配额、排队约束和现役作业；核查可见互联拓扑、驱动/CUDA、训练conda中的PyTorch/PEFT及分布式支持。登录节点看不到的信息标为待调度验证，不冒充算力节点实测；不安装包或占用未调度GPU。
2. 检查模型加载、现有LoRA/冻结参数、梯度检查点、加权loss、数据加载、协议校验、恢复与候选导出对多进程的适配点；按实际安装版本查阅官方文档并保留版本及链接，区分代码审查、文档依据与远端实测。
3. 优先比较单卡与同节点2卡数据并行方案；按远端实际资源决定是否值得纳入4卡。FSDP/ZeRO仅在容量或实测瓶颈需要时作为候选，不能为扩至3k默认引入；多节点通信不纳入首轮部署范围。
4. 设计保留全局有效batch=2的对照：单卡batch1/累积2，2卡每卡batch1/累积1。若采用4卡或改变全局batch，单列优化目标、步数和scheduler变化，不能当作纯吞吐对比。
5. 明确全局有效目标权重和归一化，并核对分布式梯度平均的缩放；不直接平均各卡不同分母的loss。单epoch尾批不得由分布式采样器重复补齐或丢弃，需提出各rank同步退出与尾批处理方案，避免挂起及重复曝光。
6. 设计rank设备绑定、无重复数据分片、随机状态、断点游标、rank0日志/保存/候选导出、异常与预算统一退出。固定输入的单卡/双卡loss与梯度允许数值误差，提出容差依据；不要求BF16逐位一致。
