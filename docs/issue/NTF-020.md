# NTF-020：仅 complete 的回答交接同步

日期：2026-11-02。状态：待实施。依赖：[NTF-015](NTF-015.md)—[NTF-017](NTF-017.md)；执行顺序在NTF-018远端预检之前。本轮按用户确认补充设计与建单，不实现代码或提交作业。

## 目标与变更原因

用户确认：只有complete对应的正式回答交接需要等待独立X2解码；其余四类状态、有效nonidle直接停止和整词正文都及时发布。此前设计完全取消complete等待，可能使Layer 1用滞后正文开始回答；本单负责单个话轮交接同步，不合并两路结果发布；另由NTF-016实施新增的每160ms计算推进屏障。

原始五状态、SoulX内部反馈／reset保持；新增数据就绪检查，不新增语义判断模型。准确合同见[设计第4.1节](../dev/SoulX-Duplug/independent_streaming_frontend.md#41-仅-complete-的回答交接同步)与[Context接口](../dev/SoulX-Duplug/shared_context_interface.md)。

## 工作范围

1. 原始complete立即记录，固定其实际音频观察截止C、可用时间和来源，创建pending候选。每话轮最多一条当前交接记录，不保存正文历史或历史complete队列；重复complete不得移动目标或延长截止。
2. 消费NTF-016的真实解码进度，含WAIT无新增文字步骤。等待X2完成覆盖C的步骤及所需真实前瞻，已有DECODE实际EOS闭合且截至该进度的闭合组全部提交后，才置ready；领先时立即ready，不强求新字或下一个EOS。
3. 在Context锁内原子检查进度、正文提交和候选有效性，记录ready时间与对应提交组数。原始state_token=complete和state_accepted不能绕过此条件；模拟消费者按completion_id去重，供后续Layer 1当前turn输入接入，不新建独立回答调用。
4. 全过程非阻塞，两路持续计算与收音，四类非complete状态正常交付。后到有效nonidle／incomplete取消旧交接；有效nonidle即时停止，idle／backchannel及内部reset不自动取消。取消后迟到结果不能复活；关闭及解码错误显式终止。
5. 沿用既有800ms过载保护：completion_wait_timeout_ms首轮800，实际deadline与原始complete主块到ready的800ms总延迟线取更早者，不串接成1600ms预算。重复complete不续期；超时标timed_out、保留证据并使验证样本失败，不以半词或旧正文强制放行。
6. 现有开放组须真实闭合，尚未发射的尾词仍为unknown；不新增空步、固定等待160／320ms或强制EOS启发式。EOF真实观察不足时记录未完成交接，合成drain不能作为在线ready依据。

## 交付与验收

- 提供交接同步实现、配置和有针对性的契约检查，docs按实现文件树同步中文说明；更新架构图中的原始状态与可用交接路径。
- 必须覆盖：X2已领先立即ready、落后追齐、WAIT无新字仍能追齐、DECODE到EOS前不放行、多组发布顺序及正文写入先于ready。
- 必须覆盖：pending期间nonidle即时取消及停止、不完整状态取消、idle不误取消、内部reset不误清候选、重复complete不续期、取消与ready并发不产生旧交接复活。
- 必须覆盖：ready同ID不重复触发回答探针、下一帧idle不抹掉交接、话轮关闭拒绝迟到、无新输入时也能定时超时、EOF不足／开放组未闭合不伪造ready。
- 分开保留原始complete、pending／ready／cancelled／timed_out、各路进度与正文提交时刻。ready只承诺计算同步，不宣称尾词必齐；晚到文字可追溯。

## 与160ms推进屏障的边界

complete交接状态与模型推进屏障分别管理。两路当前步都已完成就可释放推进屏障，即使交接仍pending；若目标C或真实前瞻需要下一周期处理，继续按正常屏障推进后再判断ready，不能等待ready才允许下一步。补查这一跨周期路径、WAIT无新字及取消／超时，保持nonidle即时停止和同一800ms总延迟线。屏障释放不自动生成ready，也不保证此前所有词已发射。
