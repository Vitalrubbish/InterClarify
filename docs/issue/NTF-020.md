# NTF-020：仅 complete 的回答交接同步

日期：2026-11-02。状态：待实施。依赖：[NTF-015／016本地交付](../reports/soulx/20261102-native-independent-frontend/README.md)及[NTF-017](NTF-017.md)；执行顺序在NTF-018远端预检之前。本单仍未实现，不提交作业。

## 目标与变更原因

用户最新要求由NTF-017在每160ms两路完成后联合提交正文和五状态token，不设置前端专用停止钩子。本单以已提交批次为输入，只为complete增加回答交接条件。共同屏障不保证真实观察目标已被X2处理覆盖，也不保证尾词齐备，因此保留有界交接；不使用任何未发布单侧结果提前ready或取消。

原始五状态、SoulX内部反馈／reset保持；新增数据就绪检查，不新增语义判断模型。准确合同见[设计第4.1节](../dev/SoulX-Duplug/independent_streaming_frontend.md#41-仅-complete-的回答交接同步)与[Context接口](../dev/SoulX-Duplug/shared_context_interface.md)。

## 工作范围

1. 原始complete在内部记录实际可用时间，在其所属160ms批次联合提交时固定实际音频观察截止C、原始可用时间和来源，创建交接候选；条件已满足可同次ready，否则pending。每话轮最多一条当前交接记录，不保存正文历史或历史complete队列；重复complete不得移动目标或延长截止。
2. 只消费NTF-017已联合提交的真实解码进度，含WAIT无新增文字批次；NTF-016内部80ms回调不能直接更新交接。等待X2完成覆盖C的步骤及所需真实前瞻，已有DECODE实际EOS闭合且截至该进度的闭合组全部提交后，才置ready；领先时立即ready，不强求新字或下一个EOS。
3. 在Context锁内原子检查进度、正文提交和候选有效性，记录ready时间与对应提交组数。原始state_token=complete和state_accepted不能绕过此条件；模拟消费者按completion_id去重，供后续Layer 1当前turn输入接入，不新建独立回答调用。
4. 全过程非阻塞，两路持续计算与收音，后续批次正常联合提交。后到已联合提交批次中的有效nonidle／incomplete取消旧交接；不通过内部回调提前取消或执行前端停止，idle／backchannel及内部reset不自动取消。取消后迟到结果不能复活；关闭及解码错误显式终止。
5. 沿用既有800ms过载保护：completion_wait_timeout_ms首轮800，实际deadline与原始complete主块到ready的800ms总延迟线取更早者，等待两路及联合提交的耗时包含在内，不从提交时重新起算，不串接成1600ms预算。重复complete不续期；超时标timed_out、保留证据并使验证样本失败，不以半词或旧正文强制放行。
6. 现有开放组须真实闭合，尚未发射的尾词仍为unknown；不新增空步、固定等待160／320ms或强制EOS启发式。EOF真实观察不足时记录未完成交接，合成drain不能作为在线ready依据。

## 与160ms推进屏障的边界

complete交接状态与模型推进屏障分别管理。两路当前步完成并成功联合提交后即可释放推进屏障，即使交接仍pending；若目标C或真实前瞻需要下一周期处理，继续按正常屏障推进后再判断ready，不能等待ready才允许下一步。补查这一跨周期路径、WAIT无新字及取消／超时，保持统一快照消费和同一800ms总延迟线。屏障释放不自动生成ready，也不保证此前所有词已发射。
