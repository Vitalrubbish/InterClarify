# NTF-011：X2Streaming-ASR 单帧流式可行性门槛

日期：2026-11-01。状态：实施中。用户已确认把教师文本源由 Nemotron 切换为 X2Streaming-ASR，本单是切换前的第一道门槛。

## 背景

NTF-010 的 `r6` 复测把 Nemotron 路径的能力边界测清楚了：固定 FDB30 30/30 完整、退出 0、主块 P50/P95 208.5/219.6ms、无 800ms 触发，但“一个空 ASR 增量即提交尾词”产生 `post_pause_extension=17`，分布在 13 条用例上（两次停顿时为 4 次）。这说明**「解码器这一步没吐 token」不能证明词已完整**，我们缺的不是更严的启发式，而是一个由模型给出的词完成信号。

X2Streaming-ASR 的官方自适应协议每80ms进行一次LISTEN决策：`[P]`（32）表示等待，`[W]`（33）触发DECODE，随后连续输出文本直至EOS（2）闭合发射组。仅闭合组可提交；一组可能含多个词，不再把空步当作词完成证明。

本单只回答一件事：**4B 的 X2 能否在 16kHz、80ms 一帧、12.5Hz 的节拍下稳定跑满实时，并留下足够余量给同卡的 SoulX 0.6B。** 不接 SoulX、不改状态规则、不跑 FDB，结论只有“能”或“不能”。

## 范围

1. 新增独立探针 `scripts/remote/x2_streaming_probe.py`：单进程加载模型，按实时节拍喂音频，逐帧记录 token、帧号、墙钟时间和累计文本。不启动 SoulX。
2. 首块合同自检：用 3.36s 合成音（沿用既有预热口径的时长）先跑一次，断言首块 mel 帧数、之后每块增量帧数、以及 `padding_cache` 形状三者一致；不一致立即失败并打印实际形状。
3. 三条冻结 FDB 用例：最长一条（按 `duration_seconds` 取最大）、`candor_pause_handling-16`（r6 在该条产生尾词扩展）、`candor_turn_taking-102`（接话）。音频读入与增益归一化沿用教师链路口径 `min(0.05/rms, 0.9/peak)`，并逐条校验冻结摘要。
4. 一条 60s 连续流：把同一批 FDB 音频顺序拼接（不带标注），用于观察积压是否随时间单调增长。短用例会把 RTF 略大于 1 的情况藏起来，这条是专门用来暴露漂移的。
5. 逐帧导出并计算：
   - `x2_rtf`：该条 X2 计算总耗时 / 音频时长；
   - `frame_lag_ms`：音频覆盖该帧的时刻 → 该帧 token 产出的时刻，给 P50/P95/max；
   - `backlog_ms`：墙钟时间相对音频时间的超前/滞后，给 P50/P95/max 与**首尾漂移**；
   - `group_close_delay_ms`：词最后一个子词帧 → 组闭合帧，给分布；
   - `peak_gpu_mib`：进程峰值显存；
   - 组闭合数、`[W]` 数、未闭合尾组、文本乱序/回改次数（应为 0）。
6. 用EOS闭合发射组做一次追加完整性抽检：任一组闭合后其解码文本不得在后续帧被改写；若发生，记录位置与前后文本，作为“X2 是否真 append-only”的实证。

## 验收标准

1. 合成音合同自检通过，且报告首块与后续块的实际帧数。
2. 四条（3 用例 + 1 连续流）全部跑完并如实记录退出码；失败保留 traceback 与当时形状。
3. `x2_rtf`、`frame_lag_ms`、`backlog_ms`、组闭合延迟、峰值显存给出数值；60s 流的积压漂移必须单列。
4. 整词完整性抽检：组闭合后被改写的次数给出实数；非 0 时必须逐例列出。
5. **门槛判定**（同时满足才算通过）：
   - 单进程 `x2_rtf ≤ 0.6`（给同卡 SoulX 留出余量）；
   - 实时节拍下 `backlog_ms` P95 ≤ 320ms，且 60s 流首尾漂移 ≤ 160ms；
   - `peak_gpu_mib ≤ 12288`（12GiB，留出 SoulX 与 KV 的空间）；
   - 无未捕获异常。
6. 不通过时写明不通过的量与位置，本单以负结果收口，不进入 NTF-012。

## 执行前合同修订（2026-11-01）

核查官方冻结源码 `0aca80597bb1399c0be4002de5bc62c0a779c542` 的 `models/voxtral_asr/interleaved.py`、`demo/engine.py` 和 `demo/engine_adaptive.py` 后，修正上述草案：

- 官方自适应协议为 LISTEN（每80ms一帧）→ `[W]` 发射 → 连续文本解码 → EOS闭合。文本token不占用新的音频帧；闭合依据为EOS，不是下一帧的`[P]`或`[W]`。一个发射组可能包含多个词，不宣称模型提供逐词完成证明。
- 默认处理器的9000样本／56帧只是原始音频部分；加入32个左填充token后，CPU实测特征为`[1,128,312]`、提示39个token。旧切片`[:, :56]`截断了mel通道，必须沿最后一维处理。
- 探针采用官方自适应协议固定的80ms封装（首块2600真实样本／16mel帧，另加256mel左填充，总特征`[1,128,272]`；之后1680样本／8mel帧），按官方要求关闭AdaRMS固定延迟条件并恢复英语language-tag。此举纠正推理协议，不调节识别阈值或模型权重；`default_num_delay_tokens=6`仅记录为基础配置，不作为实际观察时间偏移。
- 32帧左填充经同一流式编码器预热；真实流每1280样本前进一次，STFT窗口额外观察200样本（12.5ms）。逐帧同时记录实际观察边界与80ms覆盖边界，时延计算不扣除假定的6帧。
- 组闭合延迟改为同一LISTEN帧内最后一个文本token至EOS的墙钟差；记录每帧的完整生成token序列。仅EOS闭合组进入累计文本，超长组报错，不强制伪造EOS。

所有资源、四条测试、实时节拍及RTF≤0.6等门槛保持。NTF-012同步采用EOS闭合发射组；若本单失败，不进入适配与FDB30。

再次CPU实测：官方80ms封装输出提示34token、首块272mel帧，随后8mel帧。预热首块用合成零音，流式编码后将前32个左填充帧送入LM；多出的2个合成帧不作为真实流帧。预热结束后以真实PCM覆盖边界逐帧计时；首帧实际输入为200个左侧零样本及1480个真实样本，之后每次前进1280样本。EOF仅补齐STFT窗口，不追加排空帧，不把合成补零当作真实观察。
