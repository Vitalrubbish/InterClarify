# Nemotron ASR 与 XTurnix：FLEURS 质量测试计划

更新：2026-10-23。状态：XTX-001 已完成 FLEURS 输入与历史 ASR 基线冻结，XTX-002 已完成隔离环境、模型与协议冻结及 dev 验证，XTX-003 已完成真实时钟回放器与模拟契约验证并归档，XTX-004 已完成离线评分入口与合成 trace 验证并归档，XTX-005 已完成 A10 远端作业入口与 5 条冒烟并归档；XTX-006 正式 100 条作业已提交。本次验证“真实音频 → Nemotron 在线转写 → XTurnix 控制动作”，主测最后一个 ASR 词汇 token 到 `<|start|>` 的增量延迟，再结合历史 ASR 测量估计音频到 start 的链路延迟。总安排见[工程实施计划](../../engineering_implementation.md)。

## 1. 测试范围

使用现役 Nemotron EN 0.6B、160ms 配置和 XTurnix-PT，单条真实时钟回放、batch=1。ASR 转写原样保留，XTurnix 按官方规则去除最后用户消息的末尾标点。不运行表达模型、thinking 模块、TTS 或播放器，不注入参考转写，也不训练或调参。

本轮主要报告末端 start 覆盖和增量延迟，辅助保留转写 WER、提前 start 与运行失败。FLEURS 是朗读集，不包含完整自然对话的让轮、附和和打断监督，末端 start 输出率不能称为话轮准确率或 FDB TOR。

## 3. 在线回放与控制触发

1. 串行预热 ASR 与控制器，再以 dev 做协议验证，不计正式成绩。每条正式录音新建 ASR 会话与控制历史，状态设为 Listen。
2. 按真实时钟连续送音频，独立接收 ASR 增量；不等音频全部结束才查询，不等待句末标点，也不按 600ms 表达 micro-turn 额外延后控制。
3. 每次 ASR 文本更新触发一次 XTurnix 判断。单会话最多一个在途请求，后续观察按有界策略保留最新快照与事件顺序，记录合并、排队和丢弃；不能用无限并发掩盖吞吐不足。
4. 如采用官方 `<|pause|>`，只由真实上游分段或因果 VAD 的停顿事件插入，并触发重判。Nemotron 当前服务不保证提供该事件，实施前须冻结独立停顿观测器及阈值；它只提供控制输入，不暂停/重启 ASR，不拥有执行权。不从 EOF、文件时长或事后选出的最后 token 生成 pause；新增词汇到达后按冻结规则结束停顿状态。
5. 文件发送结束后继续发送 5 秒静音并接收两组件输出，再发送实际 EOF 做排空。最后输入包、静音尾窗、实际 EOF 和排空阶段分别记录。EOF 后新增词和动作只作诊断，不并入在线主指标。

本轮采用 Listen 条件下的影子决策：记录每次 start/keep，但不实际让系统开口，不因 start 关闭 ASR或切换至 Speak，便于完整采集。应显式报告这是前端测试协议；多次 start 不代表系统真实重复接话，后续真实状态转移需完整链路另测。

所有原始 start（包括最后 token 前的 start）均保存；不能只展示末端命中，掩盖前面已经提出过开口动作。静音时完全相同输入不无限重复推理；若最后请求返回 keep 且没有新词或真实停顿事件，保留未命中结果，不加“超时自动 start”兜底。

## 4. 时间点与主指标

### 4.1 ASR 最后一个 token 的定义

`t_asr_last` 是完整在线观察结束后，离线选定的**最后一次 ASR 词汇内容增加或词内补全被测量客户端收到的时刻**。它表示本条录音在线可见的最后一个词汇 token／末次词汇增量，不是文件末端、句号、空白、ASR EOS 或 EOF 排空的完成事件。

Nemotron 可能以词内增量交付，如 `D → Don → Don't`；以最后一次补全的实际可见时间为准，多 token 同批到达使用该批接收时间。优先保留原始 token ID、delta 与累计解码文本；若服务只交付文本，明确报告为末次词汇增量时刻，不冒称获得逐子词模型发射时间。

新增标点或空白不重置 `t_asr_last`。同一时刻存在先后事件时按事件序号区分。若 ASR 发生回写、为空或没有可靠的在线词汇记录，标记异常，不以文件 EOF 替代；最后一个正确参考词缺失时也不能声称该锚点代表真实发声结束。完整转写错误由 WER 与逐例标记说明。

此锚点只能事后从 trace 确定，**不能用它通知在线控制器“用户已经说完”**。在线模型始终只按第 3 节的真实事件运行。

### 4.2 start 时刻与时窗

`t_start_after_last` 定义为 `t_asr_last` 之后，测量客户端完整收到的第一个有效 start 决策。该请求的输入必须已包含最后一次词汇增量对应的前缀版本，不能把旧前缀的在途结果延迟返回算作末端命中。

主窗口为 `[t_asr_last, t_asr_last + 5s]`，同时受在线采集截止和实际 EOF 限制。同时间戳按事件序号确认最后词汇先可见、控制后返回。若采集未覆盖整个窗口，标记窗口不完整；已命中结果保留，未命中不冒称已经完整等待了 5 秒。不能在回放中提前知道最后 token 后延长特殊时窗。

单条主延迟为：

```text
L_control = t_start_after_last - t_asr_last
```

该时间包括客户端收到 ASR 后的预处理、停顿等待、调度/排队、请求传输、模型推理及结果返回，正是新增控制阶段的可见延迟。另存请求发送到返回的耗时作为诊断，不将其冒称整个控制增量。所有相减时间取同一测量客户端的单调时钟，服务端时钟不直接参与跨机相减。

### 4.3 提前 start、缺失与汇总

| 结果 | 处理 |
| --- | --- |
| 有可靠锚点且窗口内有效 start | 记录命中及非负主延迟 |
| 最后词汇前出现 start | 单列首次原始 start 的有符号相对时间及提前发生情况，负值不归零 |
| 旧前缀请求在锚点后返回 start | 单列过期观察结果，不计末端命中 |
| 只在窗口外或 EOF 排空后 start | 分别记录，主窗口视为未命中 |
| 没有 start、空转写、ASR 回写或调用失败 | 主延迟为 null，保留计划分母及失败原因 |
| 窗口未采满 | 明示覆盖不足，未命中与完整窗口未命中分开 |

主报告给出 100 条计划输入中的末端 start 命中数/比例、ASR 锚点覆盖、完整窗口覆盖、提前 start、未命中与失败数量。增量延迟给出命中条件下的均值、P50、P95、最大值和样本数；缺失不填 0 或 5,000ms。提前 start 的诊断不是句内误打断准确率，FLEURS 没有相应逐时刻金标。

辅助计算同集语料 WER：参考和 EOF 排空后的最终假设采用 `whisper-normalizer==0.1.12` 的 `EnglishTextNormalizer`，汇总 `(S+D+I)/N_ref`；在线结束转写另存。正常空转写计删除，运行失败为 null 并报告可评分覆盖。WER 不参与控制时序计算，也不能用参考答案选择在线请求时机。

## 5. 结合历史 Nemotron 延迟估计链路

### 5.1 历史依据

历史 Nemotron EN160 在同一 100 条 FLEURS 上两轮有效回放、共 200 样本次，估计逐词交付延迟为：

| 指标 | 历史值 |
| --- | --- |
| 逐词延迟 P50 | 413.582852 ms，报告可取 414 ms |
| 逐词延迟 P95 | 1,032.668798 ms，报告可取 1,033 ms |
| 可测正确且可对齐词 | 3,068 / 4,324 个参考词 |
| WER | 7.68% |

来源为固定提交 `f6ad9d9ba04e4e046dcfcdd480b5343165466046` 的[选型报告](https://github.com/Vitalrubbish/InterClarify/blob/f6ad9d9ba04e4e046dcfcdd480b5343165466046/docs/asr_selection_report.md)及[重复轮次汇总](https://github.com/Vitalrubbish/InterClarify/blob/f6ad9d9ba04e4e046dcfcdd480b5343165466046/reports/asr_selection/20261016-results/component_repeated.json)中 `nemotron_en-160.summary.estimated_word_latency_seconds`。

历史定义为“正确且可对齐词的首次交付时间减去 CTC 估计参考词结束时间”，覆盖全部可测词，不是每条录音的最后词专项分布，也不是 160ms 模型配置值。历史可测词覆盖约 70.95%；不能把缺失词的延迟补为 0。

### 5.2 两段组合

若同一条录音拥有匹配终点、同一客户端接收锚点的末词 ASR 延迟，则两段可以逐例相加：

```text
L_asr_last = t_asr_last - t_last_spoken_token_end
L_audio_to_start = L_asr_last + L_control
                 = t_start_after_last - t_last_spoken_token_end
```

本轮按用户要求复用历史 ASR 测量，不新增声学末词对齐。现有历史汇总只有逐词分位数，因此先采用历史 P50 作为典型 ASR 开销：

```text
L_chain_estimated[i] = 413.582852 ms + L_control[i]
```

例如本轮某例增量为 120ms，则典型链路估计约 534ms。报告同时列出原始增量、采用的历史常数与估计值，字段明确标为 `estimated`。只有 start 命中且锚点有效的样本才有估计；其分母与主延迟一致。

加上常数后的均值或分位数是“采用固定历史开销的估计”，不是此次音频末词到 start 的实测均值/P50/P95。不能把历史 ASR P95 和本轮控制 P95 相加声称整体 P95；也不能把历史 P50 当作 ASR 均值或严格的末词时延。两轮历史与当前环境、服务轮询和共享 GPU 的差异须说明。

本轮的“整条链路”仅指**音频到控制 start**，不包含 Layer 1 正文生成、TTS、播放缓冲和实际开口。今后若取得逐例匹配的末词 ASR 时间，可按上式另报配对总延迟；不据此扩大本次执行范围。

## 6. Trace、报告与远端实施

每例至少保存：输入 ID/哈希、采样时序、ASR 会话/版本、原始 ID/文本 delta 与客户端接收时间、词汇变化标记、停顿事件及来源、XTurnix 请求 ID/输入版本/状态/发送时间/返回时间/动作/分数、在线截止与 EOF 阶段，以及失败、排队和资源记录。

建议结果根目录为 `~/interclarify-xturnix-fleurs/<run_id>`，包括冻结配置与 manifest、原始 trace、逐例 CSV、汇总 JSON 和中文报告。逐例列出末词可见时间、首个原始 start、末端有效 start、窗口完整性、主延迟、提前/过期标记、WER 及链路估计，全部 100 条均留记录。

模型只在远端 conda 作业执行。只读复用 Nemotron 资产，XTurnix 独立环境；最多 1×24GiB GPU、8 CPU、32GiB RAM、1 个推理作业和 1 条活动录音，下载并发≤2，CPU 评分 worker≤2。新增资产≤10GiB、trace/结果≤2GiB、启动空闲盘≥30GiB，单推理作业≤4 小时，不自动加卡。共卡部署记录峰值、排队及对 ASR 时延的可能影响。

实施前先核查资产与 manifest，固定停顿观测方式、阈值、轮询周期和合并策略，再完成 dev 预热、5 条冒烟及 100 条正式回放。冒烟只修协议、资源和日志，不用正式子集选阈值。少量可手算模拟 trace 验证末词、标点变化、提前/过期 start、时窗边界和失败记账；模拟不替代真实模型测量。

完成条件是输入和组件可追溯、在线时序可复核、全部分母与缺失可见、主增量和历史组合估计分开。进程退出 0 不等于模型质量达标；结果出现不佳也如实报告。XTX-001 已冻结 100＋1 条输入与历史基线，XTX-002 已冻结两组件环境/协议并完成 dev 预热，XTX-003 已交付回放器，XTX-004 已交付离线评分入口，XTX-005 已完成 A10 冒烟；XTX-006 正式 100 条正在执行，尚未产生正式成绩，也不恢复退役脚本。执行进度以[XTurnix 工作单入口](../../issue/XTurnix/README.md)为准。
