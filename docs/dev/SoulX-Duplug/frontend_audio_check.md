# SharedContext 前端实现与音频检查任务

2026-10-29，依据用户明确授权实施前端并用少量音频测试。范围为 SenseVoice 原始文本／标签、版本化话轮正文、SoulX 五状态及因果引用、SharedContext 消费者；不接入下游 LLM、CoT、实际播放或训练。本任务说明不新增 issue。

先在本地既有 conda 做少量契约测试，再在贵州 HPC 的独立源码快照中用既有 SoulX＋SenseVoice conda 和模型执行。仅一个活动作业，1×RTX4090、4 CPU、32GiB RAM，最长 1200 秒，PyTorch 单进程显存比例 0.83，设备显存停止线 22GiB；CPU 线程≤4、数据 worker≤1。启动空盘≥30GiB，新增结果≤128MiB，不复制模型，不修改共用环境。失败保留结果，修复后使用新 run ID，不自动扩大数据集。

输入在启动前冻结 manifest：现有 FLEURS 英文开发音频及短截断、同音频加已标记静音尾部、静音负例；若现有开发目录有第二条合适音频则同样纳入，总输入≤90 秒。只读取既有开发来源，不使用 FDB 测试标签、不做阈值搜索。原幅度与既有 RMS 标定视图分别注明，不以幅度处理掩盖远场过滤。

实际预检发现开发目录只有一条录音，但共用 SenseVoice 权重目录已有官方 `example/en.mp3`。修复后另加这条英文示例（最长10秒），独立冻结文件摘要、原采样率及标定增益，不下载新音频；其来源不同于FLEURS，无独立参考转写，不计算WER。r1首次识别因回调字段名错误退出，保留结果；修复版本使用新run ID。

r2实际捕获到首次ASR调用约4.86秒，接收队列触限停止。后续版本在开始接收测试音频之前，分别预热音频模型和一次3.36秒静音ASR调用，保存预热输出与耗时；不放宽800ms上限，不把冷启动计入稳态发布延迟。冷启动事实和失败仍保留。

r3预热后实际ASR仍约3.18秒并再次触限。后续检查先修复ASR输入被float64缓存提升的问题；若实时模式仍触限，另用明确标记的 `causal` 功能模式完成文本及状态写入检查：等待每包处理后才继续提供下一包，不提前给未来音频、不产生无界队列，也不据此宣称实时通过。两种模式使用独立run ID，报告保留实时失败与限速功能结果。

音频按真实时间分包送入，包内只含已经到达的采样。模型一个在途请求，队列最多 800ms，触限明确失败。EOF 后只排空已收到音频，补齐或尾部静音都显式标记为合成音频，不生成 complete 金标。每条音频一个稳定 turn，内部 reset 不关闭话轮。

采集独立源头审核记录，并在每次 Context 提交后由两个独立只读消费者读取。核对来源原文、标签顺序及字符跨度、正文 patch 重建、原始／修正状态与源 ID、状态依据先于状态、complete 先于后到整轮转写、reset 后历史保留、关闭前最后文本不丢失。逐条保存实际转写与状态序列，不要求每条都出现五类状态；缺失类型由契约测试补足，但不能冒充音频实测覆盖。

报告区分写入正确性、正文拼合覆盖、识别内容与状态语义质量。无独立人工逐时标注时不宣称 WER 或五状态准确率；现有开发参考文本可作辅助核对，截断样本不套完整参考计算 WER。报告每种状态的观察次数、正文缺口、实际消费者一致性、在线更新时刻、ASR 返回至发布延迟和队列峰值。只测管道通过不能写成识别或控制质量全面达标。
