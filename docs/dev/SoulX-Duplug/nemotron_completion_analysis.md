# Nemotron 适配后的句中完成：原因与修复方向

2026-10-30 撤回说明：用户已指令停止 Nemotron＋SoulX 路线，转向官方 SoulX＋SenseVoice 的160ms当前值写入。以下为历史调研／实验记录，不再作为执行计划；专用适配器和入口已移除，源码由 Git 提交 `9fb5319` 追溯。现役独立 Nemotron ASR 服务不属于本次组合回退范围。


2026-10-30，按用户要求分析。本文仅复核已有源码与轨迹，不修改推理行为、不启动远端作业、不建立 issue。结论是：**当前问题主要涉及外部文本的交付节奏与 SoulX 的状态推断、兜底规则及 reset 衔接，不能仅用 ASR 最终识别准确率解释。** 哪一因素解释了相对 SenseVoice 的质量差异，仍需同条件对照。

## 1. 已确认的证据

复核对象为 [FDB 30 条实测](../../../reports/soulx/20261030-nemotron-fdb30/README.md)的全部 3196 帧，以及[四视图探针](../../../reports/soulx/20261030-nemotron-integration/README.md)。原始事件在 `artifacts/soulx/20261030-nemotron-fdb30-r1/evidence/probe/*.events.jsonl`，逐帧控制输入在同目录报告对应的 `analysis/*.trace.csv`。

| FDB 30 条的 complete 来源或输入现象 | 数量 | 含义 |
| --- | ---: | --- |
| 最终发布 complete | 65 次，涉及 25 条样本 | 事件计数，不是误完成率 |
| 模型原始预测 complete | 40 次，涉及 21 条样本 | 不能通过只取消兜底规则全部解决 |
| 原始 nonidle 被上游规则改为 complete | 25 次，涉及 12 条样本 | 占 complete 事件的 38.5%，是明确的工程干预点 |
| complete 当前块的 `delta_token_ids` 为空 | 65/65 次 | 没有注入新的当前块文本 token，不代表 ASR 已完成或真实静音 |
| complete 时 Context 版本与实际消费版本不同 | 11/65 次 | 最新全文不能直接当作控制器输入；reset 后消费版本为 0 也计入 |
| complete 当前帧发生 token 重放 | 7/65 次 | 是共现关系，不足以归因于重放 |
| complete 的 generation 控制文本为空 | 1/65 次 | reset 后仍可能直接预测 complete |

其中，25 次规则生成的 complete 原始状态全部是 nonidle，因此对应原生“连续无文本 nonidle”分支，而非“nonidle 转 idle”分支。65 帧均有可选历史前缀，事件字段 `asr_status` 均为 `returned`；这个字段目前只说明存在候选，不能说明本块识别已经就绪、文字是新的或已被消费。

代表性证据：

- 接话 ID51：4.92 秒在 `California was` 后 complete，官方交接边界为 7.82 秒。原始预测为 nonidle，规则将其改成 complete；此前 3.32 秒也发生同类改写。
- 接话 ID83：3.80 秒在 `…did you like grad` 后直接预测 complete，交接边界为 6.32 秒。该例包含词内前缀，取消兜底并不能直接消除这个预测。
- 停顿 Candor ID161：4.28 秒 reset 后控制文本为空，原始预测已经是 complete。
- FLEURS 完整录音：4.44 秒在 `…improve your chances` 后完成，后面仍有 `of moving…`；整条录音 token 重放次数为 0，说明重放不是所有提前完成的必要条件。

这些证据能够确认存在严重提前完成及异常上下文；不能把每个官方边界之前的 complete 都当成错误，因为部分前缀本身已构成独立语义句子。

## 2. 原因分析

### 2.1 原生兜底把“没有新文本”用作结束判断的触发条件

冻结上游 `service/model.py` 的 `_state_predict()` 有两个强制分支：上一个发布状态为 nonidle 而本次原始预测为 idle；或者连续 `max_mistake_num=3` 帧预测 nonidle 且 `delta_text` 为空。触发后只比较 complete 和 incomplete 的 logits，强制选择一个。

后一条件对应约 3 个 160ms 控制块，但不是可靠的 480ms 声学静音检测。即使全词表最高概率仍是 nonidle，只要 complete 的分数高于 incomplete，也可以发布 complete。25 次这类转换已经由真实轨迹确认。

Nemotron 适配中的空增量可能来自不同原因：原生识别尚未交付新字、尚无符合保守音频观察上界的新版本、门控关闭、已有前缀未增长，或文字修正全部落在历史缓存。当前这些情况都可能返回空 `delta_text`，而上游计数器没有相应的就绪信息。

因此，源码已证明存在机制上的混淆；它是否比 SenseVoice 更频繁，以及修正后能降低多少误完成，需要对照验证。25/65 不能当作可直接消除的错误比例。

### 2.2 音频与文本的输入分布发生变化

SoulX 不是只对累计字符串作分类。其训练和推断采用交错的音频、文本、状态序列；文本出现在哪一个音频块之后，会影响当前及后续判断。论文描述英文训练使用词级对齐，推断使用 SenseVoiceSmall 提供 teacher forcing 文本；不能据此声称模型只见过 SenseVoice 识别错误。

SenseVoice 原路径在门控触发时同步识别当前滑动音频窗口，再差分注入文字。Nemotron 则独立持续识别，控制器按当前可见且满足观察边界的版本取数。即使最终全文相同，也可能经历“音频继续推进、文字停留旧版本”，或者一次补入多个先前词的轨迹。名义分块同为 160ms 不保证文本对齐一致。

例如英文探针 Context 最后已有 `gold`，控制器仍停在 `pieces of`；打断 ID20 在消费到 `tom` 时完成，Context 已是 `tomorrow`。这里的问题是用于决策的在线输入，而不是事后全文是否通顺。

这是较强的机制解释，但现有日志没有逐词声学对齐和完整 logits，不能量化其独立贡献。

### 2.3 词内前缀与缓存重放改变语义出现位置

当前适配原样发布词内前缀，控制器可能读取 `grad`、`tom` 等尚未完成的词。后续字符到达时，即使原文只追加，归一化和 tokenizer 编码仍可能改变旧 token。适配器通过重放修正 KV，保证 token 历史可以重建选定文字。

这一保证不等于状态语义等价：修正后的文字与过去已经输出的状态共同组成新缓存；无法精确切分时，部分文字可能进入较早的缓存位置。它没有改变过去实际发布的事件，却改变了后续推断所依据的历史表示。应独立核查该因素，不能因重放有 54 次就认定其是主因。

### 2.4 complete 触发 reset，放大首次误判

原生完成分支会 reset，清空状态 KV、音频历史及相关计数。适配器虽保留 Nemotron 会话、连续 PCM 和 Context 正文，新 controller generation 仅在收到新增字符后从旧尾词起重建控制文字。

因此，Context 全文连续不代表控制器仍拥有完整句子历史。一次提前 complete 可以导致后半句在缺少原句上下文的 generation 中预测，产生更多 complete 或漏掉真正结束。Candor ID161 的空控制文本 complete 是异常实例；保留一个尾词不足以保证恢复语义。

reset 是误判后的放大机制，不能解释最早一次误判。提前完成后才在 Context 层过滤，也不能恢复已丢失的控制缓存。

## 3. 修复优先级

### 第一优先：修正异步就绪语义和强制完成规则

将文本状态拆为：解码未就绪、无符合音频边界的版本、门控暂不消费、解码已完成且无新增文字、已有新文字可消费。保留原始预测、最终状态、强制原因及计数器，记录五类状态分数和 complete 相对其他状态的分差。

“无新文本”不能单独累计成结束证据。先针对异步未就绪导致的计数作修正；另作消融检查不启用强制 complete 的行为，保留真实声学与语义判断。若修改强制规则，需同时检查写回的状态 token、KV 和 reset 分支，不能仅修改对外事件字符串。阈值及计数不直接按这 30 条结果搜索。

直接预测的 40 次 complete 仍需处理，不能承诺这一步即可恢复 SenseVoice 水平。简单增加 `max_mistake_num` 只会推迟部分强制判断；`max_wait_num` 主要控制 incomplete 后的 idle 兜底，不直接修复句中 complete。

### 第二优先：增加完成候选确认，并在确认前保留上下文

保留模型原始五状态记录，将完成候选与正式回答许可明确区分。候选应联合检查近期声学活动、可解释的文本消费进度、词尾状态和语义完整性；有新发声或新词到达时允许取消。短暂静音也可能是句中停顿，因此不能只加固定 VAD 静音门。

确认前保留 controller 状态或可恢复检查点，避免候选一出现就 reset。若改用多个后续块确认，也需要先解决 reset，否则无法在同一段完整上下文中取得确认。确认窗口带来的延迟与漏检必须实测，不能用无限等待换取低误完成率。

这一步涉及原生状态发布、回答许可和 reset 合同，实施前应按项目约定先更新相关设计。有效 nonidle 的打断路径仍应即时处理。

### 第三优先：调整控制文本的词边界和交付时序

Context 继续即时发布 Nemotron 原始字符；控制视图可试验只提交已确认词边界之前的文本，并暂留可增长尾词。词边界应结合模型输出及后续分隔符判断，不能靠插空格把词内片段伪装成完整词。最后一个词可能没有后继空格，需要有界收尾设计，不能等整轮 EOF 才交付。

完整词提交会增加控制文本等待；若不先修正“无增量”计数，反而可能增加强制 complete。它可以缓解词内语义不稳定和部分重分词，但不能解决完整短语后误判结束。

进一步应核查 Nemotron 特征预取与真实解码依赖，保留可靠因果边界，减少不必要的保守滞后。需要等待时，对整条音频／文本控制轨迹作有界同步，而非单独冻结文字却让音频不断前进。上界和实际资源需远端实测，不直接把名义 step 当作精确依赖，也不将晚到文字回填成早先已知。

### 后续：按真实 Nemotron 在线轨迹适配状态模型

若上述工程修正仍不足，再考虑小规模状态 LoRA。训练输入应保留 Nemotron 的真实交付时间、词内片段、空更新、延迟及重放方式，并覆盖句中停顿、可独立成句但随后续说的前缀和真正让轮；不能仅用最终正确转写替代在线轨迹。

训练按来源划分，当前 30 条作为已接触诊断数据，不冒充独立测试。短期仍可沿用已部署的 SenseVoice 前端作为运行基线；是否替换由同条件质量与延迟决定。

## 4. 如何验证修复而不掩盖代价

远端同一套调度、同一 PCM／增益、同一冻结权重、同样的输入尾部处理，比较 SenseVoice 基线、现有 Nemotron、修正异步兜底后的 Nemotron，再分别加入完成确认和词边界策略。逐项增加行为，避免一次改变多个因素后无法归因。词边界策略尤其需要与第一优先修正一起评估。

至少同时统计：

- 原始 complete、规则转换 complete、候选被取消、确认完成，以及各自 reset 的位置。
- 有人工核查边界的句中误完成、停顿误完成、真实结束召回及首个正确完成延迟；官方边界前事件继续作为时序诊断，不全部自动贴错标。
- 实际控制文本、消费字符及版本、ASR 真实解码进度、词尾等待和音频排队；包含没有完成和失败的样本。
- nonidle 检测延迟及资源峰值，避免通过延迟整条前端损害打断能力。

已有 SenseVoice 历史实录也存在较早 complete。例如同 ID51 的历史记录在输入包截止 1.60／2.88 秒已有 complete。其增益、调度、reset 音频处理及完整系统路径与本次独立探针不同，只能用于发现线索，不能拼成公平 A/B 质量差值。当前尚不能给出“比 SenseVoice 差多少”的可靠数值。

取消规则或改变 reset 会改变后续输入与预测，不能通过离线删掉已有 25 个事件就宣称得到了修复后的准确率。真实组合验证仍需在远端 conda 作业进行；本文没有启动测试或训练。
