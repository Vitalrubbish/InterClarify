# SoulX-Duplug 的 ASR 低延迟适配调研

2026-10-30补充：用户已授权在现有SenseVoice独立前端基础上尝试Nemotron＋SoulX组合，执行边界与缓存方案见[适配试验](nemotron_integration.md)。下文“后续候选”是此前阶段记录；本次可实施小型组合探针，不代表已替换首版或完成LLM／播放接入。

更新：2026-10-29。首版选型按用户确认改为 SenseVoiceSmall，以先打通 SoulX-Duplug 语音前端与下游链路；Nemotron 适配留待后续评估。本文保留此前依据官方源码和已有服务完成的 Nemotron 可行性分析，没有运行组合模型，不代表端到端延迟验收。

SenseVoice 首版的具体接入已在[ASR 前端设计](asr_frontend_design.md)细化：须在后处理前采集原始结果与标签，在状态合并／reset 前采集五状态；服务增量仅作为控制视图线索，正文通过独立的原始字符映射与保守对齐维护。该设计不改变本页选型，也不将窗口调用宣称为原生流式 ASR。

## 1. 选型结论

**首版使用官方配套 SenseVoiceSmall，完整链路可运行后再评估 Nemotron。** SoulX-Duplug 与 SenseVoiceSmall 整体归入语音前端，包含音频编码、ASR 调用、文本整理和五状态预测，位于 Layer 0–Layer 2 输入侧。此次调整将快速验证框架放在前面，减少首轮持续 ASR 与 SoulX 的音频／文本及缓存适配工作；不能据此宣称 SenseVoiceSmall 的延迟或识别质量更优。

首版沿用已核查 SoulX 提交 `a0b9063843df69619b087b95b74597b2176910b8` 的 SenseVoice 调用、窗口识别、差分与缓存修正路径，英文使用 `language=en`；SenseVoiceSmall 权重和依赖版本须在实施前冻结。前端必须将中间文字整理为稳定 `turn_id` 下的版本化快照并持续写入 Context，不能只发布 `user_complete` 后的整句文本。官方 `asr_segment`／`asr_buffer` 是接入线索，窗口重叠、末词修订、重置和整轮重识别仍需验证，不能将窗口结果直接拼接，也不能将该路径标成原生流式 ASR。

第一阶段链路目标是：用户尚未说完时文字已进入 Context，Layer 1 可读取状态并请求思考，Layer 2 结果可回写，表达与有效打断走通唯一输出运行时。各模块细节按工程计划后续明确；前端 CoT 条件化适配与训练不作为首版链路的先决条件。本次只更新设计，不启动这些实现或测试。

后续 Nemotron 评估保留项目锁定的 `nvidia/nemotron-speech-streaming-en-0.6b` revision `ebe59e5a817142986528bbbee5dba8db7b38ed50`、FP32、lookahead 1，不因当前模型卡更新而升级现役权重或依赖。此前分析未发现必须依赖 SenseVoice 特有输出的接口，但尚无组合延迟或状态质量证据。以下 Nemotron 路径均为后续候选设计，当前研究仍限定英文。

## 2. 官方实现说明了什么

| 核查对象 | 事实 | 对选型的含义 |
| --- | --- | --- |
| SoulX 的 `TurnModel._asr` | 先执行音频条件下的检查，再按需调用外部 ASR；归一化文字经 SoulX 自己的 tokenizer 编码后参与状态预测 | 不要求外部 ASR 使用相同 tokenizer；替换识别器在结构上可行 |
| SoulX 的文本历史 | 对最近约 3.2 秒音频重识别，计算文本差分，并用 KV 检查点处理前次文字修正 | 不能把持续累计转写直接当作滑动窗口识别结果，必须修改适配逻辑 |
| SoulX 的完成与等待兜底分支 | 还会识别累计话轮音频，取得最终文本 | Nemotron 路径应直接读取相应在线版本，避免完成后再做整轮识别 |
| 官方 `SensevoiceASR` | 加载 `iic/SenseVoiceSmall`，每次 `generate` 使用新的 `cache={}` | 官方组合采用窗口式调用；不能把 SenseVoiceSmall 的单次计算耗时当成整体话轮延迟 |
| Nemotron 官方模型说明 | 使用 cache-aware FastConformer-RNNT，支持低延迟分块及持续转写 | 可以并行处理音频并复用缓存，无须随 SoulX 每次查询重识别窗口 |

依据：[SoulX 服务源码](https://github.com/Soul-AILab/SoulX-Duplug/blob/a0b9063843df69619b087b95b74597b2176910b8/service/model.py)、[官方 ASR 封装](https://github.com/Soul-AILab/SoulX-Duplug/blob/a0b9063843df69619b087b95b74597b2176910b8/model/asr.py)、[Nemotron 官方模型说明](https://huggingface.co/nvidia/nemotron-speech-streaming-en-0.6b)。当前模型卡用于核对模型系列的流式能力；旧 revision 的完整说明本轮未能下载，锁定部署的具体行为仍以本项目源码和已有运行证据为准。

## 3. 项目已有基础与实际缺口

[现有 Nemotron 服务](../../../scripts/remote/nemotron_asr_service.py)已经保持单次原生 `generate` 和 RNNT 缓存，提供原始累计文本、前缀版本、有序文本事件，以及包含无新增文字步骤的解码完成事件。消费者可以独立读取结果，不必等下一包音频或整轮结束。现有服务拒绝已交付原文的回写，不应在适配中假定它支持任意修订。

这些接口提供了适配所需的基础，但尚未证明与 SoulX 每块输入正确配对。必须核查特征预取、真实解码完成和 streamer 回调的顺序；`consumed_samples` 需要结合对应事件解释，不能仅凭最新快照或名义 `step_seq × 160ms` 断言某版本只观察到该时间点。

Nemotron 会发布词内增量。即使原文仅追加，SoulX 的分词与归一化视图也可能需要修正末词。例如前次是 `inter`，后次增加 `net`，不能自行插空格得到 `inter net`。需要按完整可见快照生成控制视图、追踪消费位置，并在必要时从有效检查点有界重放；不能为省事等待整句话，或重复注入整个前缀。

## 4. 后续 Nemotron 候选路径

若后续开展 Nemotron 适配，前端内部可采用以下数据流，尚未实现；它不改变前端位于 Layer 0–Layer 2 输入侧的职责归属：

```text
持续用户音频 ──→ Nemotron 原生流式解码 ──→ Shared Context 原始转写
       │                       └──────→ 带版本和观察边界的控制文本
       └──────→ SoulX 音频编码 ─────────→ 状态预测
```

1. Nemotron 与 SoulX 接收同一持续音频，识别不受 SoulX 门控或完成判断暂停。转写一到就写入 Context，Layer 1/2 的后续读取不等待 SoulX 对齐。
2. SoulX 保留音频路径和原生五状态预测。替换外部 ASR 取数、差分及缓存衔接，不将 Nemotron 改成每 160ms 重新识别最近窗口，也不直接删除 SoulX 的文本门控。门控暂未消费的更新必须保留，具体消费时机通过协议探针验证。
3. 按对应解码完成事件和真实观察边界配对输入。有界等待 ASR，不额外聚合成 480ms，也不等待标点、整词稳定或整轮结束。词内增量通过文本与缓存适配处理。
4. 解码完成且无新增文字，可以形成空增量；ASR 尚未就绪则不能伪装成空增量。无新增文字不等于声学静音，判断仍须保留 SoulX 音频信息。
5. 不把较晚观察产生的文本回填成较早块已经可见。保留每次实际使用的音频范围、ASR 版本和可用时间；文本校正重放不回写成过去已经发生的在线判断。
6. 完成判断直接读取当时可用的权威转写。控制器重置不自动重置 Nemotron 会话或创建新用户话轮；两者生命周期由运行时分别管理。

潜在收益来自省掉重复窗口识别，并让 ASR 与 SoulX 音频计算并行。收益大小取决于文本交付、同步等待、共享 GPU 调度和文本重放开销，需要组合实测；不能将所有阶段耗时简单相加，也不能把并行解释为没有 ASR 等待。

## 5. Nemotron 延迟证据与后续替换条件

160ms 是现役 Nemotron 的名义分块，SoulX 另有 40ms 音频前瞻；两者都不是端到端延迟承诺，也不能作为 SenseVoice 窗口调用参数。项目[既有历史记录](../XTurnix/quality_test_on_fleurs.md#51-历史依据)给出 Nemotron 估计逐词交付延迟 P50 413.58ms、P95 1032.67ms，可测正确且可对齐词为 3068/4324。它不是本次组合实测，也不是末词专项分布，只说明文本延迟及覆盖缺失不能忽略。

正式采用前，需要在远端 conda 调度作业内核查：配对正确、词内增量不损坏语义、无未来文本与重复消费、单请求在途时能够持续跟上实时音频。组合延迟、文本就绪等待、状态质量和失败覆盖一起报告。沿用既有计划的待处理音频队列 800ms 上限作为过载保护；该上限不是用户已经确认的延迟质量门槛，绝对延迟目标及可接受质量差异仍待讨论。

SenseVoiceSmall 是首版起点，不再以 Nemotron 适配失败为启用条件。后续只有在输入正确性验证完成、并获得文本交付延迟、状态质量和运行资源的组合实测后，才决定是否替换为 Nemotron；不能单凭原生流式能力宣称更优。替换时独立冻结配置与来源，不在活动话轮中热切换，也不同时保留两份权威 ASR。Context 对下游继续提供版本化转写，保留来源与修订事实。

本轮只更新设计与文档，不创建 issue、实现适配、提交 GPU 作业或恢复旧训练。此前 617 条公开英文测试方案保留为 Nemotron 历史设计，首版配置须另行冻结，执行仍待重新确认。用户已确认保留音频 token、转写文本 token 与 CoT token 联合决策的目标，当前不实现；当前五类状态 token 全部送入 Layer 1，由 LLM 决定自身行为，仅有效用户打断额外直接停止活动输出，见[架构第 2.2 节](../../research_design/architecture.md#22-前端状态与系统附和)。其他状态不进入输出运行时，不存在状态到 start/keep 的映射。状态输入编码和 Layer 3 定位继续逐项讨论。
