# SoulX＋X2 长尾与 TOR 修复方案

2026-11-05，NTF-051原始方案。依据[逐例归因](../../reports/soulx/20261105-fdb30-half-duplex/control_backlog_analysis.md)、历史CPU剖析和FunASR 1.2.6发布包源码；新增证据见[源码摘要](../../reports/soulx/20261105-fdb30-half-duplex/long_tail_source_audit.json)。后续用户授权的NTF-052／053已完成[执行线程、资源与complete重识别修订](runtime_execution_update.md)的本地实现与146项回归，尚未远端复测。本文其他候选方案仍未实施，包括服务层交接许可恢复、缓存释放／dtype调整和历史识别分离。

建议先修运行时的执行线程和资源设置，再恢复本轮半双工评测适配器的原生服务交接。160ms 联合发布暂时保留。当前证据足以确定 TOR 漏答的若干行为原因，但没有当前 30 秒调用内部的完整 profile，不能把某个底层机制写成已确认根因。

## 1. 长尾的成因：证据与推断

### 1.1 首要排查 CPU 特征提取与线程执行环境

旧项目实际保存的 `asr-profile-r1-first.txt` 显示：一次 SenseVoice 调用总计 5.297 秒，`extract_fbank` 占 5.250 秒，模型 `forward` 约 0.033 秒。主要时间花在 Kaldi fbank 的窗口、log 和矩阵乘法。这证明同一运行栈曾出现“CPU 前处理很慢、模型本身很快”的情况；不等于当前 34.978 秒全部花在 fbank。

当前代码在每次 `DualAudioFrontend.advance()` 内创建并销毁一个 `ThreadPoolExecutor(max_workers=1)`。默认顺序使 SoulX 在辅助线程执行，下一批又重新创建线程。直接长度预热在主线程完成；两轮联合预热又交换模型所在的线程，因此“已经预热”没有保证正式执行者保持不变。

本次正式运行的预热证据：

| 条件 | 第1轮：SoulX 在临时辅助线程 | 第2轮：SoulX 在主线程 |
| --- | ---: | ---: |
| 59 批总耗时 | 16.681s | 5.228s |
| 控制调用最大耗时 | 8.469s | 129.18ms |
| 53760 采样识别最大耗时 | 8.406s | 44.06ms |
| 97280 采样识别耗时 | 2.275s | 36.80ms |

NTF-019 也存在同方向差异：两轮控制调用最大分别为 3.742 秒与 125.29 毫秒。但线程安排与先后顺序一起变化，没有排除进程首次初始化，故这只是将“固定执行线程”列为第一修复候选的依据，不能称作线程因果实验。

还有一项确定的资源配置问题：入口先 `torch.set_num_threads(2)`，随后 FunASR `AutoModel.build_model()` 又调用 `torch.set_num_threads(kwargs.get("ncpu", 4))`。本项目加载器没有传入 `ncpu`，入口的 2 会被默认 4 覆盖。加上 X2 设置 2、LLM 与 TTS 各设置 4，潜在 intra-op 并行预算为 14，高于作业的 12 CPU；这不表示已经观测到 14 个线程同时满载，但值得修正并记录实际值。PyTorch 说明应在执行算子前设置线程数，[MKL 配置也优先于 OMP](https://docs.pytorch.org/docs/2.15/threading_environment_variables.html)。

### 1.2 float64 会进入特征提取，值得单独对照

官方随机缓冲为 float64，拼接后的原生识别输入保持该类型。FunASR 1.2.6 使用 `torch.from_numpy` 接入数组，在 `frontend(...)` 之后才把输出特征转成 float32。因此，不能因为模型权重是低精度就认为 CPU fbank 已按 float32 计算。旧项目的识别适配器在入口统一转换为 float32，存在实际路径差异。

不过，同为 53760 采样的当前识别有 870 次，只有 39 次超过 1 秒；其他 82 次不同长度识别仅有 1 次超过 1 秒，且一些更长片段只需几十毫秒。证据不支持“片段越长导致数十秒计算”或“float64 必然慢数百倍”。dtype 与执行线程／调度交互是待验证假设。

### 1.3 两层逐次清理 CUDA 缓存是另一处具体候选

冻结 SoulX 的 `TurnModel.infer()` 每个主块调用一次 `torch.cuda.empty_cache()`；FunASR 1.2.6 的 `AutoModel.inference()` 每次识别结束也调用它。默认一张前端 GPU 上又有 SoulX、SenseVoice 与独立 X2 两个进程的工作，频繁清理可能增加显存重新分配和同步开销。

PyTorch 将 `empty_cache()` 定义为释放未占用缓存，不会增加 PyTorch 本身可用的显存；因此不能把逐步清缓存当作必要的实时性保障。[官方说明](https://docs.pytorch.org/docs/2.15/generated/torch.cuda.memory.empty_cache.html)

当前长尾还包含三个“最后已计时事件结束后”的空白区间：打断104／84为 16.956 秒，停顿50／44为 5.590 秒，停顿161／39为 2.566 秒，均发生在 complete 或等待兜底服务调用。本区间包含未细分的 reset、对象释放、同步和回执构造。仅凭位置不能认定是 reset 或 `empty_cache()`；其中打断104的服务层识别已经结束，不能再把后面的 16.956 秒算成那次识别。

### 1.4 共享识别锁会放大部分长尾，但不是全部起因

当前取消后的助手尾音识别和控制器共用同一个 FunASR 实例及锁。历史任务先拿到锁后，实时控制会等待它；后台线程不代表没有资源依赖。FunASR `inference()` 还会修改实例的 kwargs／cache，不能通过直接去锁让两个调用并发来解决。

40 次超过一秒的原生识别中，有9次发生在该样本第一次回答之前，故共享历史锁不能解释全部长尾。需要分别记录锁等待与持锁执行，才能判断它贡献了多少。

## 2. 为什么这些问题导致积压

输入按真实时钟持续到达；当前批次必须等待两路回执后才能推进。几次数秒至数十秒阻塞叠加后，控制器消费的是很久之前的音频：complete 晚到使回答错过评分窗，nonidle 晚到使取消错过实际续说时刻。

X2 增加额外计算和共享 GPU 争用，也增加屏障上的等待来源。但最大控制长尾对应的 X2 内部计算通常只需几十毫秒，联合提交本身也只有约半毫秒。先移除屏障不能修好控制路自身的 30 秒停顿；第一轮修复应保留联合发布，以便分离性能修复与语义变化。

## 3. TOR 下降的直接原因及修复

| 问题 | 已有证据 | 建议处理 |
| --- | --- | --- |
| 回答晚于评分窗 | 接话51首段播放36.107s，输入仅13.200s | 修控制长尾，继续按真实时钟评分 |
| 原生等待交接未消费 | 当前29次wait_fallback；接话76零回答且最大延迟仅315ms | 在本轮半双工适配器接收服务层speak，将交接来源单独记录 |
| complete时X2正文为空 | 接话54第一次complete正文为空 | 将这次交接记为待正文就绪；由后续联合快照消费，不丢掉事件 |
| 早期回答取消后没有后续有效回答 | 接话54、83、91均有取消及后续服务层兜底 | 保留正常nonidle取消，恢复后续交接；区分启动、取消和回答完成 |
| 仅凭TOR看不出时机准确性 | 接话17、3的成功首词提前约3秒 | 同报提前首词、首音前取消和评分窗内有效输出，不把取消关闭作为修复 |

### 3.1 用独立 handoff 字段恢复原生服务交接

本轮半双工评测适配器应接受两类许可：已提交的有效 complete，以及原生服务已经返回 `speak` 的 `wait_fallback`。等待兜底仍必须满足官方的先前 incomplete、等待监控、连续 idle 和已检测到语音等条件，不能把任意静音变成回答许可。

建议在 joint snapshot 增加单独的 `handoff`，包含 ID、来源、所属批次、控制 generation 与音频截止。原始五状态保持真实值；例如 idle 触发服务兜底时，state仍是idle、handoff来源为wait_fallback。仅由半双工消费者把 handoff 转成一次启动许可，不增加前端停止旁路。

当前研究设计仍规定普通回答的 complete 边界。本项是对独立半双工评测的兼容修复提案；实施前应先修订 `fdb30_half_duplex.md` 与对应接口合同，明确服务交接许可和五状态的区别，不能悄悄扩展 Layer 1 训练协议。

### 3.2 正文晚到时保留待交接状态

已有新增 X2 正文时立即消费交接；正文为空时保存 `pending_handoff`。后续联合快照出现新正文且期间没有新的有效 nonidle，才使用这次许可启动。初始可采用两个160ms周期、最长320ms的等待预算作为待开发集验证的配置，过期记录 `handoff_text_timeout`，不补造EOS或强制尾词。

新的有效 nonidle 撤销旧待交接，避免把已经失效的 complete 用来回答续说；内部正常 reset 不自动撤销已产生的 handoff，因为有效 complete 本来就会 reset。通过外部 `activity_epoch` 区分用户重新开始说话与内部模型 reset。

### 3.3 用生命周期去重，分别记录正文消费与回答完成

当前 `consumed` 在请求启动时就前移，它只表示正文已经交给过 LLM，不表示回答已播放完成。建议分开记录正文已追加到消息历史的位置、当前请求与取消状态、已完成回答的用户活动代次，以及待交接许可。

同一 handoff ID 最多启动一次；同一用户活动代次内的重复交接不能反复启动回答。用户新活动使旧请求取消后，后续合法交接仍可生成回答，不能只因新增字符串为空就永久跳过未完成的请求。已交给历史的用户文本不重复追加；未播助手文本不进入历史，已播文本继续按真实实录保留。已有5条失败中，没有证据表明这项是每条的独立根因，它主要保证恢复兜底／待正文后的行为正确。

## 4. 具体修改顺序

以下均是待实施设计，文件名与方法用于限定改动范围。

| 优先级 | 文件／方法 | 修改内容 | 验证重点 |
| --- | --- | --- | --- |
| P0-1 | `scripts/runtime/dual_audio.py`：构造、advance、close；`native_frontend_probe.py`：full_warmup | SoulX固定在回放主线程，X2 IPC使用生命周期明确的常驻辅助线程；所有直接预热、联合预热、正式推理使用同一SoulX执行线程；记录原生线程ID | 两路仍并发、只发布完整批次；取消后等待工作收尾，不残留线程或迟到回执 |
| P0-2 | `native_soulx_loader.py`：local_sensevoice；运行入口与启动脚本 | 显式传ncpu并统一OMP／MKL及实际PyTorch线程数；建议先比较前端1与2，LLM／TTS各2、X2为2，确保总预算有余量 | 加载前后记录实际值，不能只记录环境变量；每个实际执行线程内进入inference_mode |
| P0-3 | 原生控制／SenseVoice观测适配器 | 补锁等待、load_data、extract_feat、模型执行、empty_cache、reset和最终同步计时 | 完整包围一次控制调用，嵌套阶段不重复相加；同时记录线程CPU时间与墙钟 |
| P0-4 | 固定来源的SenseVoice适配器；原生infer适配 | 对照逐次empty_cache与会话边界清理；确认后移除两处热路径清理 | 分别核对allocated／reserved、分配重试和每卡22GiB上限；不全局替换torch.cuda.empty_cache |
| P1-1 | SenseVoice输入适配 | 单独比较float64与float32入口；候选方案只在识别入口转连续float32，保留控制音频及原生padding语义 | 比较转写、状态、规则反馈、reset和完整TOR；不能直接宣称逐位等价 |
| P1-2 | `shared_context.py`及`fdb30_half_duplex.py`：JointReplyConsumer | 增加handoff来源、服务兜底消费、pending_handoff与生命周期去重 | 接话76应消费服务交接；正文晚到、同批重复许可、取消竞态分别检查 |
| P2 | `duplex_replies.py`与历史识别执行路径 | 若锁等待显著，将历史尾音识别移到独立实例／受限后台进程；实时控制不等待历史识别持有的模型锁 | 新实例需单独核算CPU／显存；历史版本仍可回填，已发出的LLM请求不回写 |

`inference_mode` 是线程局部状态，在外层进入不能自动覆盖另一个执行线程；FunASR 已有 `no_grad`，所以不能将当前问题解释为完全没有禁用梯度。这里统一执行上下文是减少差异的措施。[PyTorch说明](https://docs.pytorch.org/docs/2.15/generated/torch.autograd.grad_mode.inference_mode.html)

`empty_cache` 与 dtype 修改先通过显式候选配置对照，再决定默认值；原生冻结源码保持不变，用可审计适配器实现，更新来源摘要和真实权重对照的预期。特别是float32可能改变识别和后续状态，不能沿用旧的严格等价性结论。

暂不优先删除交接时的整段SenseVoice识别：它确实与X2正文职责重叠，但82次非53760采样识别仅1次超过一秒，首先省去它不足以解释或消除全部长尾。绕过该识别还会改变原生服务结果，应作为性能稳定后的独立优化。

## 5. 如何验证修复是否有效

### 5.1 先做受限开发诊断

真实模型仅远端conda调度，建议最多一个作业、单卡4090、8CPU／32GiB、1800秒、输出256MiB、每卡显存22GiB；这是后续诊断的建议预算，本单没有提交作业。输入使用既有FLEURS开发音频，覆盖真实音频和原生padding组合，不用FDB低分样本调阈值。

固定执行线程／临时执行线程、float64／float32分别做对照；保持其他条件相同，并交替运行顺序，避免重演“两轮先后与线程安排混杂”。线程数1与2、缓存清理策略在选定线程方案上分别比较，最后验证组合。每个条件都区分冷启动和充分预热后的重复调用，记录库版本及实际安装源码摘要。

已有FunASR metadata提供load_data和extract_feat；另加fbank和encoder的边界，以及缓存释放与同步的边界。记录进程／线程CPU时间、允许CPU集合、cgroup限额及throttling增量、上下文切换、GPU显存和分配重试，用来区分计算很忙与线程被阻塞／抢占。重型profiler仅运行少量开发片段，吞吐结论再用低开销计时复核。

该阶段需要回答：稳定执行线程是否消除重复冷路径；线程预算是否引起CPU限额等待；长尾在fbank、锁、GPU还是缓存清理；16.956秒空白具体在哪个调用。未测到就保留未知，不用历史profile替代本轮计时。

### 5.2 再验证交接与完整系统

先用已有轨迹和模拟ReplySession检查：wait_fallback正好消费一次；complete无正文后在后续快照启动；nonidle撤销pending；正常reset保留合法许可；同一handoff不重复追加用户正文；首音前取消不写入助手文本、首音后取消保留已播部分。这些是行为检查，不由模拟调用推算修复后的TOR。

随后使用相同的三卡、12CPU／64GiB、7200秒、输出2GiB及每卡22GiB边界，顺序运行固定FDB30的三组：旧适配器＋性能修复、服务交接修复单独启用、两者组合。每组均保留完整30条和失败现场，实际播放按原输入时长裁切评分，继续仅评价TOR／延迟，不启动相关性judge。

性能建议目标是充分预热后不再出现秒级识别长尾，批次耗时P95低于160ms，控制主块延迟P95约400ms以内、最大约800ms以内，并检查长输入积压不持续增长。这些是待验证的性能目标，**不恢复曾取消的800ms前端停止线**。超过目标应如实记录。

TOR按相同ID与旧纯SoulX比较，接话／打断各10条保留固定分母。重点检查51不再因长尾错过窗口、76收到服务交接、54的空正文许可得到正确处理，以及83／91后续交接是否形成有效声音；同时报告两组停顿误接话、提前首词和取消时序，避免仅提高接话数。既有轨迹无法承诺修复后直接回到10/10。

## 6. 来源与分析边界

FunASR源码来自官方PyPI的[1.2.6发布包](https://pypi.org/project/funasr/1.2.6/)，wheel SHA256为 `74f339fa92d252e17616758bc94666908d02356281690e1e242110ac6676800c`。只下载并读取，没有安装依赖；版本与当前日志一致，但尚未与远端安装文件逐字节比对。4个源码文件、当前两轮预热及历史profile的摘要和摘录已留在机器可读证据中，原文件副本保存在本地artifacts的`long_tail_source_analysis/`。

本单完成的是更具体的成因判断与可实施方案。尚未证明固定线程、float32或缓存策略分别能解决当前长尾；也未修改研究设计中的现行交接合同。实际实施应先更新相应设计与同路径说明，再改代码并进行远端验证。
