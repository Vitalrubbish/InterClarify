# SoulX-Duplug 下的可靠增量转写方案调研

2026-10-30，按用户要求核查官方实现，讨论如何取得可供 Layer 1／2 理解的持续转写。本文是候选设计，不替换现行合同，不新增 issue、不修改运行代码、不启动作业，也不恢复已撤回的 Nemotron 组合。

结论：应让正文转写拥有独立的连续音频、当前识别假设与生命周期，避免使用 SoulX 的控制 delta 或 controller reset 定义正文边界。保留 SenseVoice 的最小验证采用固定起点、逐步扩展音频重识别，并用每次返回的整段假设替换当前段；面向长时间无停顿和严格低延迟的目标，应另行比较原生流式 ASR。两者都需要独立测量识别质量和实际交付延迟，不能承诺识别永不出错。

## 2. 原生增量的实际含义

`infer()`先将160ms音频块加入`cascade_buffer`并编码音频。`_asr()`先运行一次SoulX前向，只有预测不为`asr_eos`才调用外部SenseVoice。得到窗口文字后做去标点、文字规范化、去开头附和和中英文切分，再与前次窗口文字比较。

比较长度均足够时，`get_lcs_substrings()`从最大公共子序列起点截取两个后缀；它没有输出完整编辑对齐或音频时间。随后按长度及上一条delta位置提取新增文字。需要修正时回退一个KV检查点，替换上一条delta并重算该处缓存。这不等于可以修订任意更早的词。

每步还向`delta_text`列表追加一项，包括空项。音频超过3.2秒后截去旧音频，再按最近20项delta的词数保留`cascade_text`尾部。词数仅用于估算文字缓存，不能保证与音频窗口逐词对应。数字和英文撇号等还可能受到控制视图的切分影响，原始识别正文不宜从此视图反推。

因此需要区分三种值：

| 值 | 含义 | 不能推断的内容 |
| --- | --- | --- |
| `asr_segment`／原生delta | 给当前控制步骤使用的文字增量 | 不是可直接拼接且永不回改的转写片段 |
| `asr_buffer`／`cascade_text` | 最近窗口的规范化文字，可能已裁尾 | 不是完整话轮，也不是未经处理的SenseVoice全文 |
| 完成分支的`text` | 对当时`buffer_for_asr`重新识别的结果 | 不保证从逻辑话轮开始，也不保证等到真人说完 |

论文的“streaming”包含连续状态预测和ASR辅助交错输入；部署中的SenseVoice调用是反复识别音频窗口。通过窗口政策也可以构建流式服务，但必须额外解决音频范围、假设替换、长话裁剪与收尾，不能只依赖delta字段名称。

## 3. reset 与完成识别为什么不能管理正文

远场拒绝、部分backchannel、complete及等待兜底等路径均可能reset。`buffer_for_asr`主要按nonidle／incomplete等状态接收音频，必要时回补此前最多5块；它不是与逻辑话轮等长的原始连续录音。原生complete调用它之后reset，等待静音兜底也可以识别并返回speak，而当前块原生token仍是idle。

本轮原幅度视图16次reset均对应被far_field拒绝的nonidle。原始窗口先后出现`In many cases,.`、`I.`、`I.`，我们跨reset保留草稿后得到`In many cases I I`。这是原始识别错误和草稿管理共同导致的累积，不能只用字符串去重修复。

标定完整录音虽然有两次整段覆盖，仍被切成`...your chances.`与`I moving into...`。重复录音最后一次有效覆盖后还新增了`I`。因此“存储覆盖成功”“没有gap标志”“触发了整段ASR”都不足以说明输入可读、完整或语义正确。

## 4. 可选路线

| 路线 | 能解决什么 | 主要代价或缺口 | 本次建议 |
| --- | --- | --- | --- |
| 继续拼delta并去重 | 可掩盖部分表面重复 | 无法恢复漏词、改正早期错词；真实重复也可能被误删 | 不作为可靠正文方案 |
| 直接用asr_buffer覆盖 | 保留窗口内部修订 | 超过3.2秒会丢掉话轮开头；跨窗仍需定位 | 只作控制诊断或局部展示 |
| 固定起点的SenseVoice增量重识别 | 当前段任意位置可被修订；避免重叠窗口文字拼接 | 重复计算；需要独立音频、分段与长话限制 | 保留当前模型选择的最小验证 |
| 原生流式ASR维护连续解码 | 缓存复用，适合长时间连续输入 | 需重新验证SoulX的文字节奏、词内增量与状态质量 | 长时方案候选，不能直接恢复旧适配 |
| 让SoulX自行生成ASR正文 | 利用其训练过的ASR能力 | 官方部署采用外部teacher forcing；质量与耗时未验证 | 当前不优先 |

SenseVoice官方提供长音频分段推理示例；这不意味着只保留`cache`对象就能把本项目冻结模型变为原生流式。上游当前依赖和示例也已变化，本调研不升级现役FunASR1.2.6。

## 5. 推荐先验证的具体设计：独立连续音频＋固定起点全文替换

### 5.1 输入与状态分工

同一份16kHz单声道float32输入交给两条内部处理路径：SoulX继续官方音频、控制ASR和五状态路径；正文整理器保留按真实采样编号连续的音频，用同一个SenseVoice实例及固定权重识别。正文路径不受SoulX的ASR门控、远场reset或complete截断。

这不是两份权威正文。Context只有独立正文整理器维护的一份当前全文；SoulX内部控制文字留在诊断中。虽然都来自同一SenseVoice权重，两者可能观察不同音频、得到不同文字，必须记录实际控制输入，不能声称SoulX已经读到了Context最新全文。暂时保留原生控制路径，是为了单独验证正文改善，仍须检查新增计算是否影响状态延迟。

```text
连续PCM ─┬─→ SoulX原生音频／控制ASR → 原生状态
         └─→ 独立连续音频 → 固定起点SenseVoice → 当前话轮正文
                                                 │
                      每160ms处理步由单写者联合覆盖Context
```

### 5.2 当前段假设如何更新

维护已结束声学片段的当前正文`P`、活动音频起点`a`和已处理截止`b`。每次识别使用同一起点的连续音频`[a,b)`，得到`H(a,b)`。全文始终是`P + H(a,b)`；下一次返回`H(a,b2)`后，直接替换活动段全部旧文字。不能计算两段识别的“新增词”再追加。

例如第一次为`And many cases the rolling...`，下一次变为`In many cases, enrolling...`时，整段活动假设被替换，先前错词可以撤回。用户真的重复同一句时，由不重复的音频范围确定归属，不在整轮正文中搜索相同句子去重。

先做同步、串行的受限验证：每个160ms步骤完成原生状态处理后，再对有新增有效语音的活动段请求正文识别，最后联合发布。状态／打断钩子仍先执行。模型共享实例不并发调用，不加固定320ms或1秒发布定时器；不要求每块都产生新字。

同一步需要收尾时只执行覆盖当前截止的那次正文请求。原生ASR结果只有音频范围与请求完全相同、配置和后处理相同，才允许复用；通常不能直接拿原生3.2秒窗口代替活动段全文。重识别增加的真实GPU时间必须单独计量。

若同步方案跟不上真实音频，则该候选在当前资源上不达标。后续可另议单模型串行调度、合并过期请求和异步结果，但不能在未测量时直接宣称与原生状态路径并行没有代价。异步结果还会引入音频截止与联合发布配对问题，应单独设计，不在首个验证中混入。

### 5.3 段边界与长时间连续发声

候选增加独立的流式声学VAD，例如固定版本的FSMN-VAD，只用于识别音频空隙和限制转写计算。它不判断语义complete，不发起回答，不替代SoulX五状态。默认不能使用简单RMS阈值丢弃低音量语音；输入削波、低电平与VAD漏检另行测量。

初步探针参数可设：累计至少320ms真实无语音后，在已确认静音内部选择声学切点。320ms在这里仅是待测声学端点候选，不是正文更新周期，也不要求正文等待320ms才可见。切点之前最后识别一次并替换当前段，下一段从相同采样边界开始；识别区间不得重叠或漏采样。短停顿切段只管理正文与音频，不关闭逻辑turn，后续片段仍属于同一条Context用户消息。

首个有界探针可限定活动识别段最长12秒。这是拟议的计算保护参数，不是已测最优值。16kHz float32下12秒PCM约0.73MiB，须将活动段、原生缓存、切片副本等合计纳入现有4MiB上限；不能只核算主缓冲。

没有可用静音而达到12秒时，停止并记录不支持的连续发声，而不能硬切词、丢开头或无限扩张。若要覆盖更长连续发声，须引入可靠词级时间／声学对齐后有界滚动，或采用原生流式ASR。仅用文本LCS不能证明切点在词边界。此限制意味着该探针是质量修复验证，不是无限长转写的最终实现。

### 5.4 收尾与当前值合同

SoulX complete可以触发一次覆盖当前实际已处理连续音频的正文识别，但不能自行封存活动段或清空转写缓冲；用户继续说话时，仍可用同一起点的新识别替换活动段。这能防止一次提前complete永久固定错句，不能修正SoulX本身的提前状态判断。

最终识别在当前步骤联合发布之前返回时，以真实返回时间发布新正文及该步骤状态；不把较晚文字记成较早已可见。普通无新字或ASR异常时保留上一份正文，明确记录最近成功识别截止及当前未就绪范围。

独立VAD的声学结束只结束转写片段，不等于逻辑话轮结束。逻辑关闭前应处理已经到达的真实音频，确认对应结果已交付；不足160ms的尾音与ASR排空必须显式登记。按现行合同，EOF后和合成尾部识别仍仅诊断，不能回填关闭的Context。

如果产品要求断开连接／EOF后仍把最后一次识别交给下游，需要另行确认“正在收尾、延后关闭或独立最终结果”的接口变更；当前160ms联合发布合同没有自动提供这项能力。本候选不会偷偷新增状态锁存、历史事件、text-only写入或伪造音频步骤。

### 5.5 当前记录与读取

保持单写者、单份当前全文、每160ms步骤与状态联合覆盖；不恢复版本、patch或事件环。前端内部只保留当前音频与假设，外部诊断可以保存轨迹。

正文应保留SenseVoice原始词序、数字、标点及空格，只分离已知标签；不能沿用控制路径的去标点、去附和结果。错误与普通空返回不清空已知正文；有效新假设允许修订活动段任意位置，不能要求它始终是旧文前缀。

原始hypothesis存在短时末词修改是正常现象。若希望Layer2只接收较少变化的前缀，可以再比较相邻假设的一致部分；这会增加等待，且不是正确性证明。当前允许全文修订，所以不默认增加多次一致门槛。相邻假设用于当前比较不等于在SharedContext保存历史。

正文当前值不自动更改LLM已经读取的输入或KV；下游仍需在合法输入边界使用最新全文，后续接入另测。ASR正文来源、识别实际截止、状态实际控制输入必须可区分，覆盖标志不能冒充识别准确率。

## 6. 原生流式ASR何时更合适

如果要求长时间不停顿、持续低开销和较低交付延迟，优先评估保留跨块声学／解码缓存的原生流式模型，而不是无限扩大SenseVoice重识别段。[Nemotron官方模型说明](https://huggingface.co/nvidia/nemotron-speech-streaming-en-0.6b)给出cache-aware FastConformer-RNNT方案，可作为英文候选，但本项目仍固定既有revision，不据当前模型卡自动升级或换模型。

此前[四视图适配](../../../reports/soulx/20261030-nemotron-integration/README.md)说明连续正文和缓存消费可运行；[30条FDB试验](../../../reports/soulx/20261030-nemotron-fdb30/README.md)又发现提前complete、停顿误完成及打断检测延迟。后者不能全归因于ASR，也不能因正文连续就忽略。

若重新比较，分两项验收：先验证独立ASR的正文、词内增量、实际观察范围及末尾排空；再验证同一来源文本进入SoulX的时机、门控、词内重分词与KV修正。不能只替换`recognize()`返回值、移除文本输入或把累计全文反复当新delta注入。控制器reset与ASR会话的生命周期仍需分开。

该路线不自动获得“完整词、永不修订、准确率高”的保证；实际服务交付政策和模型错误须单独检查。并且它改变了当前SenseVoice选择，须在用户确认路线后再更新实施合同。

## 7. 验证顺序与达标依据

首先用已有六视图作回归，保留原幅度与标定结果；这些已接触样本不能承担独立泛化结论。比较三种正文：现行delta草稿、候选固定起点假设、对相同完整真实音频单次识别的离线参考输出。最后一项用于诊断分段损失，不作为金标或较早在线输入。

需要逐时转写参考、完整录音参考和声学词结束时间，才能评价在线正确词交付。以人工／数据集参考算WER、重复插入与漏词；有时间对齐时另报正确词交付延迟及覆盖分母，没有对齐则只报可核验的音频截止和模型耗时，不能伪称词级延迟。

| 维度 | 必须回答的问题 |
| --- | --- |
| 正文质量 | 什么时候出现了可理解输入，重复、漏词和早期错词何时修复 |
| 生命周期 | controller reset／提前complete是否仍会切断或固定正文 |
| 末尾 | 最后语音是否已经过识别；截断、正常静音、EOF各有什么未交付内容 |
| 合法重复 | 用户重复一句话是否原样保留，有没有被字符串去重误删 |
| 计算 | 段越长时单次ASR耗时、实时处理比、队列及显存是否可接受 |
| 控制状态 | 新增计算是否推迟nonidle／complete，控制输入是否如实记录 |
| 长话 | 超过12秒不间断语音是否明确触限，没有偷偷硬切或丢音频 |

首个探针沿用单远端conda调度作业、1×4090、4CPU、32GiB、显存22GiB、结果128MiB、积压800ms等上限。12秒段的每步重识别是否能满足这些限制目前没有证据；触限判失败，不能靠限速送音或丢包通过。具体提交仍需后续实施任务，不由本调研启动。

后续再使用未参与调试的英文材料评估质量与延迟，并增加真实低音量、长停顿、重复、改口、名字数字、持续发声等覆盖。数据集和数量另行确定，不恢复旧取消任务，也不因本文创建issue。

## 8. 本轮建议与尚待选择的内容

建议先保留SenseVoice与SoulX原生控制路径，做独立连续正文和固定起点替换的有界质量探针。它能直接验证当前问题有多少来自窗口差分和reset，新增的计算代价也容易归因；不同时改控制输入、状态规则和ASR模型。

若目标必须立即包含长时间不停顿与低延迟，那么原生流式ASR更符合计算结构，候选重识别路径只能作为诊断基线。最终选择取决于允许的正文等待、连续发声范围及实测资源，不把“160ms更新”解释为160ms内识别完每个词。

两条路径共同要求：连续音频不随controller reset丢失，正文以ASR当前假设替换，控制文字与实际正文可追溯，收尾真实计时，质量与状态分别验收。这些是具体方案的基础；当前实现仍是已记录的delta草稿加controller片段覆盖，直到实施合同另行确认。

补充参考：[Whisper-Streaming论文](https://arxiv.org/html/2307.14743)说明非流式ASR转为在线服务时，缓冲、时间切分和假设提交均需额外政策。其局部一致性思路可比较，但它的质量和延迟数字不能移植到SenseVoice；本候选不默认使用两次一致后才发布。
