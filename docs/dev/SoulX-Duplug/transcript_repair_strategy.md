# 转写拼接缺口的修复策略

2026-10-30，按用户要求分析稳定修复方案。本文为候选方案，不修改模型或在线代码，不新建issue，不启动训练或远端作业。继续采用SoulX＋SenseVoice、每个160ms音频步骤联合覆盖SharedContext的已确认合同。

## 1. 已核验的具体失败

来源为`artifacts/soulx/20261030-current-context-r1/evidence/replay/`的原始来源与快照，冻结源码`da5064e`。

- 英文示例第16／17次识别，窗口从单词内部开始，返回`ible chieftain…`和`chiefhieftain called…`；当前规则只取新结果开头两个词，在旧可修改尾部精确匹配，拒绝了含有新增文字的结果。
- 英文示例第19次为整段识别，实际连续音频范围0.76—5.56秒，返回`The tribal chieftain called for the boy and presented him with 50.`。此时旧正文尾部可修改位置已经移到`Chieftain`附近，搜索范围内没有开头的`The tribal`，导致有效修订被拒绝，旧正文仍为`…presented him the.`。
- 重复录音第63次整段识别覆盖7.48—15.16秒，实际是第二个controller generation之后的一段较完整音频；旧规则仍只搜索旧正文最后的`Of moving…`附近，无法匹配新结果开头`In many`，同样拒绝修订。
- 重复录音第64次窗口为15.16—15.32秒，返回`I.`。其音频范围恰与旧截止相邻，但前次失败已将全局覆盖标志置为false，相邻拼合分支因而拒绝；后续缺口状态未恢复。该短结果本身也可能是误识别，不能把它自动追加当作修复。

重复录音的两遍主体已经写入，最终gap不能直接解释成后半段全丢。英文示例则确有识别已经返回的修订未进入正文。新方案需要分别验证二者。

另有独立尾部问题：英文示例最后一次ASR所见真实音频只到5.56秒，最后在线联合快照处理到7.00秒。其后是否还有未识别文字不能由拼接代码推断；修复拼接不会自动补出未经过识别的音频。

## 2. 稳定策略：明确文本归属，有界重新识别作为恢复路径

建议以“音频片段与对应当前文字”为内部组织单位，不再让一个不断前移的字符尾部位置承担所有识别结果的归属。每段保留明确音频起点、实际覆盖范围、对应全文位置及当前识别假设。它们是前端当前状态，不是SharedContext的历史正文版本。

同一固定音频起点下，识别范围向后扩展时，重新得到的该段全文可直接替换该段旧文字。SharedContext继续只接收整理后的最新话轮全文和状态，允许修订覆盖。

短窗口结果仍可用于低延迟更新，但应在音频允许的当前片段范围内做多个词的序列对齐，容忍开头残词、少量替换／插入／删除，并保留原文输出。匹配字符只在派生比较视图中归一化，不能修改正文。不能将搜索放宽到整个对话，否则重复语句可能对到第一遍。

只有音频起止时间而没有词级时间，不能据此准确决定正文应从哪个字符截断。对于无法确定映射的重叠窗口，应回到一个已经明确的片段起点重新识别连续原始PCM，再整体替换这段文字；不能声称已经按时间精确裁好了字词。

## 3. 识别类型必须区分

窗口识别和官方完成／等待兜底分支的整段识别要分别处理。后者应按真实音频范围和所属片段确定替换区域，不能继续复用“新结果开头两词匹配”的单一规则。

`call_kind=turn`不代表覆盖整个逻辑话轮。官方`buffer_for_asr`会按状态筛选并回补音频，可能从话轮中间开始、也可能包含多个不连续片段。当前失败中的整段结果恰好连续，但不能推广为所有输入都连续。只有可证明覆盖相应片段的结果，才允许直接替换；无法证明时重新识别该片段的连续原始音频。

有待修复的片段应按自身覆盖情况管理。某次失败不应永久阻止后续合法扩展、重识别或新片段接入；修复成功后重新计算覆盖标志，不仅继承旧gap布尔值。

## 4. 连续音频、reset与收尾

转写用的有界连续音频缓冲独立于SoulX内部controller reset，不因complete、idle或远场状态立即丢弃。controller generation可以作为诊断线索，不能单独作为“用户这一句已结束”的证据或正文封存边界。

收尾核对“实际已接收／已处理真实音频”和“正文所依据的识别覆盖”是否一致。需要补识别时，取当前确实到达的真实PCM，保留实际返回时间，再在后续输入边界更新。不能使用未来音频、通过EOF伪造较早在线结果，或把补识别称为原生complete。

## 5. 长音频与成本边界

不能无限保留整轮PCM，也不能每160ms从开头重识别整轮。优先复用已有识别，遇到无法可靠对齐、范围回退或必要收尾时，才触发有限长度片段重识别；重复请求合并，最多一个模型调用在途，重新识别的音频长度和调用频率必须设上限。

SoulX内部的SenseVoice窗口调用与控制文字暂时保持原路径，正文恢复复用同一个SenseVoice模型和权重，不增加第二个ASR来源。这意味着必要时仍有额外计算，必须测量是否触发800ms音频积压，而非宣称没有成本。

片段优先在真实静音／词边界结束。持续无停顿语音达到长度上限时，需要词级时间对齐等额外机制确定安全切点，或者明确记录当前能力边界；不能硬按秒切开后继续保证不重字、不漏字。本轮还没有为无限长、无停顿音频验证稳定解法。

“多次一致才提交”可以作为后续可选策略，但会增加等待；本项目当前允许直接覆盖正文，不应为修复拼接默认加入固定一秒或三次一致门。

## 6. 建议的落地顺序与验收

先根据原始轨迹建立最小失败复现，再补充片段归属、窗口与整段识别的不同替换规则，以及失配后的恢复路径。仅在有界PCM和调用预算明确后增加重识别；实现前同步更新前端与接口说明，不因本调研直接改变现有行为。

验收必须同时检查：英文示例`…with 50`实际可进入当前正文；重复录音第二遍整段修订不覆盖第一遍；开头残词和普通识别修改能够恢复；状态reset不切断转写；尾部真实音频识别覆盖可核账；长话内存、队列和新增识别延迟受限。保留难例和失败，不把“最终没有gap标志”当作正确转写。

已有六视图作为已接触回归材料，不冒充独立质量评测。远端同配置重放时分别报告存储写入、拼合覆盖、文字正确性、状态时机与新增开销。
